# 客户端 ⇄ 调度器 协议 v1（单一来源）

> ⚠️ **v2 增补已定名，尚未实现——见 `docs/design/R2-ENGINEERING.md` §二。**
>
> 那里定义了要**新增的字段与事件**（`scopeId` / `source` / `reRefs[]` / `catchUp` /
> `timeline/marker` / `step/summary|detail|reasoning`）以及**三条语义规则**
> （全局 `seq` 与 `sinceSeq` 不是一回事 / 同一时刻最多一条未收口 / `seq` 可选 + 排序要有兜底键）。
>
> **纪律**：协议字段**一旦上线就冻结**。上表在动工前定完，之后**只加不改语义**——
> 改一次就要多背一个兼容分支（旧客户端还在跑）。这正是本仓库那条
> "**当场不记，以后永远补不回来**"。
>
> **本文（v1）的 R1–R14 全部继续有效**，v2 只增补，不修改任何既有字段的语义。

> **v0 → v1 的根本修正**：用户**不是在跟某个 agent 聊天，而是在跟对话调度器聊天**。
> 所以这不是"你一句我一句"的问答，而是**两条独立的事件流**：
> ① 用户说了什么 ② 调度器说了什么。
> 两者之间**没有 1:1 配对关系**。

---

## 零、为什么必须去掉配对

旧模型（v0）假设 `用户消息[i] ↔ 回答[i]`。这个假设在下列情形**立刻失效**：

| 真实情形 | 旧模型会怎么错 |
|---|---|
| 调度器**主动开口**（任务完成、提醒、外部事件） | 没有对应的用户消息 → 无处安放 |
| 调度器**一次回应几条**用户输入 | 后一条用户消息被错配成新回答 |
| 调度器**只记不答**（被动聆听，见 speaker 设计） | 强行配一个空气泡 |
| 结论**晚到**（T4 任务几分钟后完成） | 被错配到用户后续的新问题上 |
| 用户**连续说几句**调度器才回应 | 配对错位，界面顺序全乱 |
| 用户说完**长时间没回应**（它在思考/决定不出声） | 界面无法表达"在工作但还没话说" |

**正确模型**：客户端维护**一条有序时间线**，
用户发言与调度器发言都是**独立事件**，按 `seq` 排进同一条流。

```
时间线（单一有序流；谁先谁后由 seq 决定，不存在配对）
├── 用户：接口偶发 500 帮我看看            ← UserUtterance (u_1)
├── 调度器：这个我熟，先看连接池…           ← DispatcherMessage (m_a1, reactive, re=[u_1])
├── 调度器：确认了，是连接池打满            ← 同一 m_a1 的 deep 块（同一气泡）
├── 用户：那怎么调                        ← UserUtterance (u_2)，可与上面的回答并行发生
└── 调度器：我把上次那条收个尾…             ← DispatcherMessage (m_a2, proactive, re=[])
```

## 一、传输

- **上行**：`POST /api/say`（用户发言）
- **下行**：`GET /api/stream`（WebSocket；断线重连带 `sinceSeq` 续传）
- `messageId` 由客户端生成（用户消息），服务端据此**幂等去重**

## 二、三段 ID

| 层 | 谁生成 | 含义 |
|---|---|---|
| `conversationId` | 客户端 | 一段对话的稳定标识（＝ 与调度器的会话） |
| `messageId` | 用户消息客户端生成 / 调度器消息服务端生成 | **时间线上的一个条目** |
| `taskId` | 服务端 | 异步任务（T4 可能几分钟）——**独立于消息**，完成后作为新消息出现 |

> ⚠ v0 的 `turnId` **取消**：它是一问一答时代的产物。
> 现在的对齐键是 `messageId`（说话单位），异步工作用 `taskId`。

## 二之二、什么时候"直接答"、什么时候"变成任务"

**判断依据是「要多久」，不是「简单还是复杂」。**
不存在"简单问题走快答、复杂问题走深答"这种分类 —— 那是实现视角，不是产品视角。

| 情况 | 调度器怎么做 |
|---|---|
| 现在就能给出反馈 | **直接答**（可以分两段：先应一声，再把想好的说完；在用户看来是一段连续的话） |
| 需要十几秒、几十秒甚至更久 | **把它变成一件独立的事**：告诉用户"这件事我单独去做，做完跟你说"，然后**不再占用当前对话** |
| 那件事做完了 | **主动发起**一条消息报结果；**如果有必要，可以打断当前话题**（"对了，我打断一下，前面那件事做完了"） |

所以对用户可见的只有三件事：**说一句反馈 / 说我拿去做了 / 我回来说结果**。
快慢、超时、降级、思考深度 —— 全是内部细节。

## 三、下行事件（全部带 `seq`，单调递增）

```jsonc
// ① 调度器开始一条消息
{
  "type": "message/start",
  "seq": 101,
  "messageId": "m_a1",
  "origin": "reactive",              // reactive=回应某人 / proactive=主动发起
  "re": ["u_7", "u_8"],              // 在回应哪些用户消息（可为空 = 主动）
  "interrupts": false,               // true = 打断当前话题（例如"前面那件事做完了"）
  "sources": [                       // 这条结论查证过的来源；[] = 没联网查（客户端就不显示）
    { "title": "DeepSeek 发布 V4.1", "url": "https://www.36kr.com/..." }
  ],
  "at": 0
}

// ② 文本块（流式渲染的唯一来源）
{
  "type": "message/text",
  "seq": 102,
  "messageId": "m_a1",
  "block": "quick",                  // quick=快速回答 / deep=深思回答
  "seqInBlock": 3,                   // 块内序号：乱序重排与去重
  "text": "先看连接池。",
  "final": false                     // true = 该块说完（服务端保证不停在半句）
}

// ③ 状态提示（不是消息，不进历史）
{ "type": "message/status", "seq": 110, "messageId": "m_a1",
  "state": "thinking" | "listening" | "handoff" | "working" }

// ④ 消息结束
{ "type": "message/end", "seq": 180, "messageId": "m_a1",
  "reason": "completed" | "aborted" | "failed",
  "sources": [                       // 这一轮**最终**查到的来源（权威版本）
    { "title": "上海当前天气", "url": "https://pc.weathercn.com/..." }
  ]
}

// ④之四 客户端回报"我什么时候看到的"（监控层据此算**感知延迟**）
// ⚠ 这些时间都是**客户端自己的钟**：同一个钟内部相减，不受两端时钟偏差影响。
{ "type": "message/seen", "seq": 191, "messageId": "m_a1",
  "clientFirstSeenAt": 1789335700258,   // 第一次看到这条消息的正文
  "clientEndedSeenAt": 1789335710000,   // 这一轮说完
  "clientAt": 1789335710001 }           // 回报时刻

// ④之三 服务端说：你该刷新自己了（**只在现场推，不进日志、不参与续传**）
// 前端是哑的 —— 它不猜"系统变了没有"，只听服务端说。
// 部署脚本写了新的构建指纹时，服务端侦测到就发这个。
{ "type": "client/reload", "seq": 190,
  "reason": "build-changed",
  "buildId": "3ea0d4ae71b58ae9" }   // 客户端拿它和自己的指纹比

// ④之二 这件事不现在答，改成独立任务（用户会看到"我拿去做了"）
{
  "type": "task/created",
  "seq": 181,
  "taskId": "task_1",
  "messageId": "m_a1",              // 说出"我拿去做了"的那条消息
  "title": "查一下你昨天那个接口的问题",
  "at": 0
}

// ④之三 任务做完了（随后会有一条主动消息报结果，可能带 interrupts: true）
{ "type": "task/completed", "seq": 300, "taskId": "task_1" }

// ⑤ 服务端确认收到用户发言（多端同步用；单端可忽略）
{ "type": "user/echo", "seq": 50, "messageId": "u_7", "text": "…" }

// ⑥ 错误
{ "type": "error", "seq": 111, "messageId": "m_a1", "code": "DEEP_FAILED", "message": "…" }
```

## 四、客户端必须遵守的六条

| # | 规则 | 为什么 |
|---|---|---|
| **R1** | **维护一条有序时间线，不做任何配对** | 配对在六种真实情形下都会错（见第零节） |
| **R2** | 同一 `messageId` 的 `quick` 与 `deep` 渲染成**同一个气泡** | 用户应感觉是一个人在一次回答里说了两段 |
| **R3** | `status` 与 `text` 不可互转 | 状态混进正文会进历史、被当成"说过的话" |
| **R4** | 中止**不擦除**（已显示的字撤不回来） | 擦除会闪、会丢信息；只能追加说明 |
| **R5** | `seq` 去重 + 断线续传（`sinceSeq`） | 移动端切后台/切换网络是常态 |
| **R6** | 有在做的任务时，界面要**可见地**告诉用户"还有件事在处理" | 否则用户以为忘了；但**不要**显示进度百分比（伪精确） |
| **R7** | 来源只从 `message/start.sources` / `message/end.sources` 渲染，**不塞进正文**；空就一个字都不显示 | 正文是"说给你的话"，来源是"你可以去核"；没查就别说查了 |
| **R8** | `message/end.sources` 覆盖 `message/start.sources` | agent 先说"收到，我先去查…"（那时还没有来源），工具跑完才拿到 —— 结束事件里的才是权威版本 |
| **R9** | 收到 `client/reload`：**手上没说完的话就先说完再刷新**；同一个指纹**只自动刷一次** | 不能让刷新把话从用户眼前抽走；也不能因为指纹对不上而无限刷新 |
| **R10** | 每次连上（含重连）都对一次 `GET /api/version` | 刷新令只在现场推，断线期间部署的新版本收不到 |
| **R11** | **每个事件都必须有时间戳**，由服务端在 `emit()` 统一加 | 没有时间戳就看不出"反馈和响应从时效性来说对不对"；放在一处加，将来新事件也不可能漏 |
| **R12** | 客户端只回报**连上之后产生**的消息的 `message/seen`（用服务端时钟划线） | 否则刷新时会把整段历史当成"用户刚看到"，算出来的感知延迟是假的（实测踩过） |
| **R13** | 下行不通时，界面**变灰且不可触达**（不是隐藏、不是只调透明度），恢复后自动变回来 | 服务重启的那几秒里点什么都没用；与其让用户戳半天没反应，不如明确告诉他"正在恢复连接" |
| **R14** | "服务重启过"这句话由**服务端**判断、由服务端说；客户端不自己判断、不自己编 | 判据需要服务端的历史（`sinceSeq` + 事件时间戳）；客户端没有这个视角 |

## 五、上行

```jsonc
// 用户发言
POST /api/say
{ "conversationId": "c_1", "messageId": "u_7", "text": "接口偶发 500 帮我看看" }

// 中止调度器当前的输出（全链路：处理层 + 接收层一起停）
POST /api/message/m_a1/cancel

// 会话列表
GET /api/conversations   // [{ conversationId, title, lastText, updatedAt, unread }]

// 客户端回报"我看到了"（见 R12：只报连上之后产生的消息）
POST /api/receipt
{ "conversationId": "c_1", "messageId": "m_a1",
  "clientAt": 1789335710001, "clientFirstSeenAt": 1789335700258, "clientEndedSeenAt": 1789335710000 }

// 监控层出口
GET  /api/debug/report?conversationId=c_1   // 时效性数字 + 规则发现 + agent 判断 + 变出来的任务
GET  /api/debug/tasks[?status=open]         // 任务簿
POST /api/debug/analyze { conversationId, force? }   // 手动跑一次审查
POST /api/debug/tasks/:id/done              // 关掉一条任务
```

### 五之二、开发事件是**附加**通道，不是替代通道

`GET /api/stream?...&dev=1` 表示"**除了**产品事件，我还想收后台在做什么"。

⚠ **`dev=1` 绝不能挤掉产品事件。** 踩过的坑（线上事故）：实现里把 dev 写成了
"单独订阅"，于是开发者模式一开，这条连接就只剩 `dev/step`，
用户能看见历史（补发不走订阅），但**之后说什么都没有回应** ——
而开发者模式是**默认开**的，等于整个应用对所有人都是哑的。

正确语义：**产品事件永远订上；`dev` 只是额外再订一条开发流。**
服务端有回归测试守这条（`services/core/test/subscribe.test.js`）。

## 六、设计含义（写给实现的人）

**调度器不是"回答者"，是"节奏控制者"。** 它决定：

- 现在说不说（**可以只记不说**）
- 由谁说（快速回答 / 深思回答）
- 分几段说（快答 + 深答合成同一个气泡）
- 什么时候说（可以等任务完成再主动开口）

**所以客户端不能假设"每句话都有回应"。**
用户说完可能长时间没有调度器发言（它在思考，或决定不出声）——
**这不是错误状态**，界面必须能自然表达"它在工作，但我还没话说"。
