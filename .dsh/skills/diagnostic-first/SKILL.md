# 先量，再改（这个仓库的诊断顺序）

> 这个仓库最贵的一种错是「**照着记忆里的老做法顺手改**」，第二贵的是「**没量就说根因**」。
> 权威出处：`AGENTS.md` §三/§六 · `docs/dev/07-…`（缺陷清单）· 手册 `07-APPENDIX.md` §一。

## 四步，顺序不能换

1. **把现象变成读数**：一句命令 ＋ **原始输出**（不是转述）。
   - 服务端：`journalctl --user -u hupo-core` / `v2/services/core/serve.log` / `curl -s http://127.0.0.1:8020/api/version`
   - 客户端：`flutter test` 的具体红行、`tester.getRect(...)` 量出来的矩形、截图（Flutter web 把字画在 canvas 上，**查 DOM 查不到**）
   - 盘上：`ls -l` / `cat /proc/<pid>/cgroup` / `pgrep -af`
   - ⚠️ **量之前先问"这个读数是从哪一端取的"**：线上那条链**大部分跑在租户容器里**（`/api/asr` 就是），
     中心这一侧读不到 ⇒ 别在错的地方找。
2. **找到"一行判据"**：根因通常能压成一行（一个条件、一个键名、一个 cgroup、一行 `if`）。
   压不成一行的，多半还没找到。
3. **写一个会红的复现**（在动手改之前）：
   - 单元/界面判据：`test/unit` / `test/widget`（⚠️ `test/widget` 里**只有 `accessibility_test.dart` 是硬闸**）
   - 或一条能重复跑出坏结果的最小命令
   - 🔴 修完之后要**做变异验证**：把修法**改回去** ⇒ 判据必须**当场红**（不然那条判据是空转）。
4. **改 ＋ 留痕**：随代码写 `docs/dev/NNN-*.md`（现象 / 读数 / 根因 / 修法 / 判据 / 在哪一端验的），
   并在 `docs/dev/00-PROGRESS.md` §〇 加一行。

## 三条"别交出去"的坏东西（都是这个项目真栽过的）

| 坏东西 | 形状 |
|---|---|
| **静默空转的修法** | 修了，但那段代码其实永远不会命中 —— 比如用 `pgrep -x node` 认 node 进程（它的 `comm` 叫 `MainThread`）⇒ **一个都认不到**。**修完要拿一个假对象/假进程真试一遍。** |
| **绕过被测那一行的闸** | 探针把 `wss://` 写死 ⇒ 客户端自己算地址那行永远不被验（判据 V13 就是为它加的）。**客户端自己算的东西，闸要打在客户端这一侧。** |
| **"端"搞混的结论** | 闸全绿、而用户看到的还是坏的（因为验的是另一端）。⇒ 结论里必须写清"**在哪一端验的**"。 |

## 收口前问自己三句

- 这个读数**别人能复现**吗（命令＋输出都在）？
- 我的修法**有判据**吗？把修法撤掉，那条判据**红不红**？
- 这个结论**有没有说满**（把"没验"说成"验了"）？
