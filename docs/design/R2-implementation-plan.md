## 〇、先说结论

**计划排得出来。但有一个前提**：四席一致确认，**有五件基础设施现在是坏的**，
而所有"第 1 批"的东西都压在这五件上。**先修这五件，别的才有意义。**

而且四席各自**独立**发现了**同一件最严重的事**（协议席和运行时席都点名）：

> **代码里的 `seq` 是"每会话"的**（`conversation.js:12` `this.seq = 0`，`restoreConversation()` 也只按单会话恢复）。
> ⇒ 两个作用域**都从 1 开始数** ⇒ 客户端的 `seq <= lastSeq` 会把**第二条会话的事件全部静默丢掉**。
> ⇒ **这正是 X1 要防的那个形态："服务端日志一切正常，用户屏幕一片空白"。**

## 八、内存账（运行时席算的，带算式）

```
overhead(调度器) ≈ 80MB，agent 195MB
不节流：floor((640−80)/195) = 2.87  → 2
硬顶  ：floor((1024−80)/195) = 4.84 → 4（第 5 个被杀）

1G 机：2 用户 ×(1 焦点 + 1 监视) = 780 + 80 = 860 > 640
   ⇒ 实际只能是：1 用户 2 作用域，或 2 用户各 1 焦点（470MB）
```

**容器之后**（每用户 1G cgroup）：`7.2G − 宿主 1G = 6.2G` ⇒ **≈6 用户/机**；
4 vCPU（每用户 2 进程、`CPUQuota 150%`）同量级 ⇒ **容量瓶颈是 CPU，不是磁盘（162G 非瓶颈）**。

> ⚠️ 运行时席的一句要紧话：**"容器不是 D4 说的'本轮不做'，它是第 2 个用户的开门条件"**
> ——因为 `2×(1焦点+1监视)×195+80 = 860 > 640`，**第二个用户上线就会把第一人的 agent 拖下水**。
