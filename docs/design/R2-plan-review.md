## 一、先认账：实施计划 §〇 的核心论断是**过度归因**

我在实施计划里写：

> "**五件基础设施必须先修，所有'第 1 批'的东西都压在这五件上。先修这五件，别的才有意义。**"

**三席一致不同意，而且给了代码级证据。**

### 被推翻的三条断言

| 我在计划里的断言 | 实现风险席逐条验的结果 |
|---|---|
| "`seq` 是每会话的 ⇒ **两 scope 都从 1 数 ⇒ 客户端会静默丢掉第二条会话的事件**" | 计数确实每会话（`conversation.js:14/150`）✅，**但"客户端丢第二条会话"今日不成立** ❌ —— 客户端一个 controller **只绑一个** `conversationId`（`chat_controller.dart:25-30`、`main.dart:146-150`），架构 §4.1 明写客户端只认一条 `chatId`、`scopeId` 只归调度器。**`grep -rn scope services/core/src apps/mobile/lib` = 0** ⇒ **今日根本没有把两条会话喂进一个 `lastSeq` 的路径**。它不是"现网静默 bug"，是"**多作用域客户端怎么接**"这个**未做决策的未来风险** |
| "`_armEviction` 遇 `running` 直接 return，timer 不重排 ⇒ **长跑 agent 永不再回收**" | **不成立** ❌。`agent-runtime.js:371` 那行在，但 running 先 `clearTimeout`（`:379`）、idle 再 `arm()`（`:380`），**只有"timer 恰在 running 中到期"这一竞态才不重排**。**真缺口是另一件事**：`agentMaxProcesses` **全库不存在**（`grep=0`），且 `agentIdleEvictMs` 是 **30 分钟**而 D4 说 **10 分钟**（`config.js:112`） |
| "客户端本地发言用 `lastSeq` 当 seq ⇒ `user/echo` 被丢掉 ⇒ **多端同步永久失效**" | 行成立（`chat_controller.dart:398`），**结论不成立** ❌。`say()` **不改 `lastSeq`**，服务端 echo 的号必然更大（`dispatcher.js:245-252`、`conversation.js:42`），**能过 `:249`**，之后再按 messageId 去重（`:314`）⇒ **V4 那条"先失败后修好"的用例根本写不出来** |

### 成本席的结论更直接

> **F1/F2/F3 不在 MVP**——单设备上用户看不见，它们只是**多作用域的正确性**。
> "§〇 第 1 批全压在这五件上"是**过度归因**。

### 但有一条确实成立，而且是唯一"会永久丢数据"的

| 断言 | 判定 |
|---|---|
| **`store.js:22-28` 的 `append()` 静默吞异常** | ✅ **成立，而且三席都把它列为"保三件"之一** |

⚠️ 而且它比我说的更具体：**真杀伤在重启**——`restoreConversation` 取磁盘 max（`conversation.js:150`）⇒ **号回退**，而见过 transient 的客户端 `lastSeq` 更高 ⇒ **丢下一条**（`chat_controller.dart:249`）。

⇒ **修正后的结论**：**"五件"应该降为"两件半"**——
`store.append` 上抛（真根）、`emitTransient` 的号（重启回退是真的）、以及**多作用域客户端怎么接**（**这是个待做的决策，不是一个待修的 bug**）。

## 二、五处工程事实错误（要改文档）

| # | 计划里写的 | 实际是 |
|---|---|---|
| **E1** | B1 的根在 `websocket_transport.dart:112-115` 的 catch，它"**清令牌**" | ⚠️ **那个 catch 并不清令牌**——`_noteUnauthorized()` 只在 `:110`（服务端明说未登录）时调；`main.dart:90` 只是落盘。**真正的洞是：WS 401（`server.js:87-90`）客户端不处理** ⇒ **坏令牌 = 每 2s 无限重连**（`websocket_transport.dart:216`） |
| **E2** | "`resend(messageId)`（**同 id 幂等**）" | ⚠️ **服务端做不到**——`/api/say` **没有去重**（`server.js:264-275`、`dispatcher.js:243-263` 每次都 emit + prompt）⇒ **重发 = agent 干两遍**。幂等要么加服务端去重，要么客户端不许重发同一 id |
| **E3** | "`message/status` 的 `messageId:''` ⇒ **状态永远挂不上**" | ⚠️ **过头了**：`pendingStatus` **收到了**（`chat_controller.dart:283`），只是 **working/thinking/handoff 全库没有 UI 读**（只有 `:114/:650` 读 `listening`）。⇒ 这不是"没载体"，是"**载体有了但没人看**"。而且修法漏了取号通道——那个事件**拿不到 messageId**，需要新增 `translator.current.writer.messageId`（`session-translate.js:148/209/288`） |
| **E4** | "`answer_bubble.dart:32` 限宽 **760**" | 现在是 **`maxWidth: 560`**，不是 760 |
| **E5** | V11 用 `agentMaxProcesses` 当判据 | ⚠️ **该配置全库不存在**（`config.js` 里没有） |

**另**：`D4.8` 的行号是 **143-147**（不是 142-146）；`C7` 只在 **600–900 那一档**成立。

### 计划做完之后**新引入**的失败模式（原来没有、现在有了）

| # | 新的失败 | 为什么 |
|---|---|---|
| **G1** | **F2 是一次"无过渡期的线上协议切换"** | 现网 APK 的 `seq <= lastSeq` 会对新全局 seq **盲目丢事件** ⇒ **上线瞬间旧客户端"屏幕全白"**，而 V2/V4 **只测新客户端** |
| **G2** | **F3 与 X1.5 打架** | `emitTransient` 不吃 seq，而客户端**排序键就是 seq** ⇒ 瞬态事件（含 R1.2 应声）同秒并发时只能按到达序排，**与"用发生时刻显示"冲突**。计划没写兜底排序键 |
| **G3** | **R1.2 的"无条件 200ms 应声"在无网时是假反应** | 先出"在处理"，2 秒后出"失败"——**正是 09 最恨的"看着像发出去了"的变体**。应声前必须先判 `connected` |

## 四、成本：**第 1 批装不下**

去代码里估的实际改动量：

| 步 | 改动行数 | 新文件 |
|---|---|---|
| 0（F1–F5） | 150–250 | 3 个测试 |
| 1（文案） | 80–120 | forbidden_words_test |
| 2（B1–B6） | 300–400 | timeline_store.dart |
| **3（R1+D7+D3+D4.8+拆 866 行）** | **900–1500** | 6–8 |
| 4（D2+D5 半件） | 100–150 | 0 |
| 5（R2/R3/R5） | 800–1200 | 3–4 |
| **合计** | **2500–4000 行 = 动全库 30–40%** | **15–20 个新文件** |

**工期：16–24 人日 ≈ 3–5 周单人。** 其中**步 3 是爆点（5–8 人日）**。

> 成本席的原话：**"`SOLUTIONS.md` 的'第 1 批 = R1 全部 + 7 条 bug'是对的。工程计划把它扩成六步 = 把一个迭代写成了一个发布周期。"**

### ⚠️ 计划里有一处自相矛盾

> §四 的六步里**根本没有完整性清单和 apply 工具**，而 §五 的 V9 却在测 `apply-change.sh`。

### ⚠️ 而"先用平板"被排到了最后

> D4.6 / D4.7 / D4.9 被排进**第 5 步（最后）**，只有 3 行的 D4.8 在第 3 步。
> 主人原话是"**先用平板**"（`R2-DECISIONS.md`），D4.1/D4.2 定"**平板宽屏是第 1 批首要验收场景**"。
> ⇒ **计划把它排到最后，直接违背 D4。这是成本席认为最要紧的一处。**

## 五、修正版：**最小可验证切片**

三席各给了"保三件"，而且**高度重合**。合起来就是一个能装到平板上、能验证一个假设的版本：

### MVP-slice（修正后的第 1 批）

| # | 做什么 | 为什么在最小集里 |
|---|---|---|
| **S1** | **`store.append` 上抛**（`store.js:22-28`）+ **落盘成功才推**（`conversation.js:41-44`） | **三席一致的"保三件"第一名**：唯一会**永久丢数据**的根 |
| **S2** | **F5 修 `message/status` 的取号**（`dispatcher.js:567` + `session-translate.js` 取 `writer.messageId`） | **R1.2 / R1.3 / D7 三件的共同载体**——不修，应声和四态都没地方挂 |
| **S3** | **R1 全部**：200ms 本地应声（**先判 `connected`**，见 G3）+ **四态** + **收起态重发** | **8/10 的放弃点压在这里**，且**零依赖** |
| **S4** | **失败必须可见**（`websocket_transport.dart:112-115` + `chat_controller.dart:420` + `chat_screen.dart:778`） | 09 的"看着像发出去了"；也是 03 的接住点 |
| **S5** | **B1（真根：WS 401 不处理 ⇒ 死循环重连）+ B5（退避）+ B6（先画本地一屏）** | 04 的 2.7–5.1s 死区 + 09 的冷启动 |
| **S6** | **D4 的三件**：`760` 内容列 + 宽 >900 两栏 + **助手消息 0px**（3 行） | **主人明说"先用平板"**，而平板是主开发设备 |
| **白送** | `auth.js:40` 的 TTL **30 → 180 天**（一行） | 一行拆掉登录页返工的紧迫性 |

**明确不在 MVP**：F2（全局 seq 分配器）、F3（transient 不占号）、D3 的字号/手势、D7 四档、R2/R3/R5、拆 `chat_screen.dart`、D5 语音。

**但两条要作为"前置决策"先定掉**（它们不是 bug，是没做的决策）：
- **多作用域客户端怎么接**（F2 的真实形态）
- **旧客户端兼容/灰度**（G1，否则上线瞬间白屏）

**一句话总览**：这一轮的价值不在"又发现了几个 bug"，而在**它把我上一份计划的核心论断拆了**——
我说"第 1 批全压在五件基础设施上"，三席各自去读代码后一致证明：**那五件里有两件的前提不成立**，
而真正压着 8/10 放弃点的东西**零依赖、就在客户端**。
**这就是"计划写完必须独立评审"的全部理由**：写计划的人和审计划的人，看的是同一份文档，
但只有后者会去代码里核对。
