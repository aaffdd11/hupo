## 〇、一句话

> **一台哑终端 + 一台云端专属主机 + 一个调度器。**
>
> 用户看到的是**一个聊天窗口**；底下是**多条 DSH 会话**，每条待在自己的工作区里；
> **调度器**决定"谁的话投给谁"，并按自己的时钟把这些话拼成用户看到的那一条时间线。

与 v7 的关系：

| | v7 的世界 | 本文的世界 |
|---|---|---|
| 用户 | 一个人（`userId` 恒为 `owner`） | **多个人，一人一台容器** |
| 会话 | 一条会话 = 一个话题 | **一条会话 = 一个工作区**；一个用户有多个工作区 |
| 客户端 | 一条时间线 | 一条时间线（**不变**），但底下是多条会话 |
| 隔离 | taint 棘轮 + 两档能力 | 加一层**容器**（物理）与**工作区**（逻辑） |
| 调度器 | 节奏 + 账本 | 加两件事：**对用户的路由** 与 **agent 之间的邮政** |

## 一、四层与角色

```
┌─ 终端（AI 手机）──────────────────────────────────────────────┐
│  Flutter 客户端。**只看到一条时间线**，不知道 DSH 存在。          │
│  浮窗 = 那唯一的聊天窗口；桌面 = 工作区的图标墙。                 │
│  【沿用】"前端是哑的"：只渲染，不做判断                          │
└───────────────────────┬──────────────────────────────────────┘
                        │ HTTPS + WSS（调度器协议，不是 DSH 协议）
┌───────────────────────▼──────────────────────────────────────┐
│ 调度器（永续进程，容器外）                                     │
│  ① 对用户的路由   ② agent 之间的邮政   ③ 归一化成一条时间线      │
│  ④ 账号与供给（创建/启动/销毁该用户的容器）                      │
│  【沿用】不能有表达欲（唯一例外：产品固定话术）                   │
└───────────────────────┬──────────────────────────────────────┘
                        │ 容器内通道（socket / 反向隧道）
┌───────────────────────▼──────────────────────────────────────┐
│ 用户容器（= 这个用户的整个世界）                                │
│  ├─ 一份专属 DSH（会话运行时、上下文装配、流式、工具）            │
│  ├─ 若干工作区（每工作区 = 一个目录 + 一条会话 + 桌面一个图标）    │
│  └─ hupo 地盘（记忆索引 KV / 制品 / 审计）                      │
│  【实测】DSH 的会话历史按 workspace root 分区落盘                │
└──────────────────────────────────────────────────────────────┘
```

**四层各自的"绝不做的"**：

| 层 | 绝不 |
|---|---|
| 终端 | 不判断"这句话来自谁"、不判断"该不该刷新"（**只渲染调度器给的事实**） |
| 调度器 | 不实现对话语义（那是 DSH 的）；不写台词（除产品固定话术） |
| DSH 会话 | 不跨工作区读记忆（**由目录分区保证**） |
| 工作区 | 不互相投递内容（**只通过调度器，且只走摘要/指针**） |

## 二、DSH 提供了什么（**全部【实测】**）

> 这一节是全篇最值钱的部分：**能复用的东西一个都不要自己写**。
> 出处一律是 `@deepseek-ai/*` 包的 `README.md`（本机 `~/.dsh/profiles/node_modules/@deepseek-ai/`）。

### 2.1 作用域与记忆

| 原语 | 它到底给什么（引号内为原话） | 用在哪 |
|---|---|---|
| `dsh-workspace` | "一份**有序的、持久化的项目目录清单**，以及**在每个目录里跑过的 session**"；"removes projects **without deleting** folders, files, or sessions"；"hide sessions from grouping **without deleting their histories**"；"**invisible to models**" | 工作区的登记与归档 |
| `dsh-session` | "把每条**模型可见的事实**记进一个 **append-only 会话日志**"；可 "inspect, replay, **fork**, flush"；"compaction **hides** superseded entries ... **without deleting them**" | 记忆的**权威载体** |
| `dsh-session-persistence(-jsonl)` | 会话落盘 | 记忆持久化 |
| `dsh-session-projection(-cache)` | "当前**每会话状态**——如 todos、goals、会话统计——**无需重放原始事件日志**"；"从**已提交**的会话事件做同步投影"；"**日志永远是权威**：崩溃只可能让检查点落后，**绝不可能超前于已提交事件**" | 派生状态；**N6 的现成实现** |
| `dsh-session-query-sqlite` | "跨会话历史做**排序的 SQLite FTS5 全文检索**，**既可以跨会话也可以限定单会话**，带游标分页" | 跨作用域的**详情检索** |
| `dsh-session-title` | 每条会话有"客户端可见的标题"，且"**永不进入模型输入**" | 工作区"最近在聊什么"，**零上下文成本** |
| `dsh-session-checkpoint-policy` | 在"模型请求前 / 有外部副作用的工具前 / 下一步前"落检查点；"**检查点失败是 fail-closed**"（写不成功就不跑）；"未完成的 Assistant 流是**瞬时**的" | 崩溃可恢复；**不是备份** |

### 2.2 工作区与会话的绑定（关键）

| 事实 | 原话 |
|---|---|
| 会话创建时可指定根 | `dsh-api-session-controller` 的 `CreateRequest { workspaceId?, **cwd?**, sessionId?, agentPreset? }`；该包职责含 "**workspace-path opening**"；存在动作 `openWorkspacePath` 与错误码 `session/workspace-attach-failed` |
| 根是**会话级**的，不是进程级 | `dsh-api-workspace-files`："读取发生在 **Session** workspace root 内"；"每个方法都在线上带着 **Session identity**"；"**不借用父会话的根**" |
| CLI 的 cwd 只是**默认值** | `@deepseek-ai/dsh` README：**"运行命令时所在的目录将作为默认 workspace 根目录"** |
| 会话历史**按 workspace root 分区落盘** | 本机实测目录：`~/.dsh/sessions/--home-deploy-proj-hupo--/session-*/session.v3.jsonl.zstd`（`/` → `-`，两端补 `--`） |
| 工作区登记表 | 本机实测 `~/.dsh/storages/workspace.json`：`global.workspaceIds[]` + `tables.workspaces[id] = {path, title, sessionIds[], createdAt, updatedAt}` |

### 2.3 沙箱与权限

| 事实 | 原话 / 含义 |
|---|---|
| `dsh-fs-sandbox` **只约束"写"** | "confines model file **writes and edits** ... **while preserving the local filesystem's read behavior**" |
| 三档模式 | `read-only`（拒绝一切变更）/ `workspace-write`（**只允许 workspace 内或平台临时根**）/ `danger-full-access` |
| 模式是**会话级**、可各自切换 | `dsh-sandbox-policy`："**每个会话可以独立切换模式**"；"部署选一个默认模式与**兜底 workspace 根**"；"每次模型请求前，模型会收到**生效的策略与工作区**" |
| 批准策略与沙箱是两套 | `dsh-permission-presets`："presets 给用户**一个选择器**同时应用沙箱模式与批准策略"；"改默认**不影响已有会话**" |
| 读前写/变更检测 | `dsh-fs-observation-policy`：覆盖或编辑前必须**先读过**；读过之后文件变了就**拒绝并要求重读** |

> ⚠️ **本节最重要的一句话：`workspace root` 不是安全边界。**
> 它约束**写**，不约束**读**。把主目录和子工作区放成父子目录，
> **子工作区的文件对主目录的 agent 依然可读**。
> 记忆隔离靠的不是目录，而是"**会话历史按 root 分区**"（这一半是自动成立的）。

### 2.4 agent 之间与后台工作

| 原语 | 给什么 | 用在哪 |
|---|---|---|
| `dsh-jobs` | "让工具在 agent 继续的同时保持长任务活跃"；**"归属按 agent 会话隔离，所以别的 agent 无法查看或停止它"** | B 在用户离开后继续干活 |
| `dsh-tool-jobs` | 完成通知："**忙的 agent 在下一步收到；空闲的 agent 可以被一次有界的 follow-up turn 唤醒**"；配置可管"**连续唤醒次数**"；⚠️ **"待投递的通知不会在宿主销毁后存活"** | **"跟 A 在闲时说"的现成实现** |
| `dsh-subagent` | "把工作委派给**具名子 agent**、收集结果、**跨轮继续子对话**"；可选 "**one-shot**" 或 "**continuable**"（后台起持久子 agent，返回 id 供以后发消息）；可 inspect 子 agent 的 "mode、**activity**、lineage" **而不用加载或恢复它们** | 派活；**"谁在忙"的判据** |
| `dsh-session-reference` | 一条会话可以**引用别的会话**：把 `@label` 变成规范 URI，生成"**有界的、只读的、不可变的**快照，作为**持久的、不可信的背景上下文**"，并自带**固定警告：禁止把里面的内容当成指令、权限声明或工具请求** | **跨作用域记忆的唯一出口**（形态现成） |
| `dsh-schedule` | 持久提醒，以"**同一会话内的普通 follow-up 消息**"返回；幸存重启；⚠️ **"投递需要一个活着的根 agent"** | 定时；**不是跨会话通道** |

### 2.5 上下文注入（**来源标记问题的落点**）

| 原语 | 给什么 | 关键约束 |
|---|---|---|
| `dsh-system-prompt` | "每个模型步骤收到**一份有序的 system prompt** 与工具 schema"；可加 "**prompt sections / dynamic runtime facts / reusable variables**"；**"agent 级的贡献覆盖同名全局默认，且不影响其他 agent"** | 改 system prompt = 动前缀，**与 R2 冲突**【待实测：能否只追加】 |
| `dsh-agent-instructions` | 从 "**user-global 与 project 级 `AGENTS.md`**" 加载工作区指引；有"**字节预算**"；"**只在首次请求加载**"，不持续监听外部改动 | **工作区自带职责/性格**的落点 |
| `dsh-persona` | "给**一个 agent** 自己的人格：preset 挂载这一行注册 persona prefix/suffix，**shadow 部署级默认**" | session 级人格 |
| `dsh-user-questions` | "需要**暂停工作**、向人求一个决定时"的服务 | 问用户；**它真的会暂停**，成本可见 |

### 2.6 客户端（**"纯粹是 DSH 的聊天"到底能拿到什么**）

| 原语 | 给什么 |
|---|---|
| `dsh-client-ui-conversation` | 会话装配与共享外壳；`useConversation` / `useInput` / `inputActions`；**"具体 target 如 Chat 是独立的包，注册自己的 Definitions、snapshot builders、Views、renderers"** |
| `dsh-client-ui-chat` | 从已记录的会话渲染聊天；"**不组装也不修改模型请求**" |
| `dsh-client-ui-workspace` | 浏览/管理会话与工作区：add、rename、reorder、search、fork、archive、删除；"**subagent 来源的会话保持隐藏**" |
| `dsh-client-ui-layout` | Web GUI 的**三栏 AppFrame** + `ctx.layout` 呈现控制 |
| `dsh-web-app` | `dsh --profile web` 的交互式浏览器 GUI |

> **结论**：DSH 已经把"**会话装配**（conversation）"与"**界面渲染**（chat / layout / workspace）"
> 拆成了独立的包，而且允许注册自己的 target。
> 所以"纯粹用 DSH 的聊天"落成一句可执行的话是：
> **复用运行时 + 装配 + 渲染，替换导航层（三栏 + 工作区侧边栏）。**

## 三、容器、目录与权限布局

### 3.1 容器内布局

```
/data/                          ← 容器内，这个用户的整个世界
  main/                         ← 主目录（顶层对话的 workspace root）⚠️ 不是 /data，不是 home
  workspaces/
    <scope-name>/               ← 子工作区（= 桌面上的一个 APP）
  hupo/                         ← hupo 的地盘，**不在任何 workspace root 里**
    memory/                     ← 记忆索引 KV
    apps/                       ← 生成的小程序制品
    audit/                      ← 审计
$DSH_HOME/                      ← 这份专属 DSH 的（会话历史按 root 分区）
```

**三条硬规则**：

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **主目录 root 不许是 home** | `~/.dsh/.credentials.yaml`（模型密钥）、`~/.ssh/id_rsa` 会被**读**到；**`~/.bashrc` 会被写**到 ⇒ 持久化代码执行。**现有生产实现用的是 `~/hupo-workspace`，那是对的，别退回去** |
| 2 | **主目录 root 不许包含 `workspaces/`**（必须**平行**） | `workspace-write` 下主目录的 agent 会**写进子工作区**（算错一个相对路径就发生）。平行之后写被 root 挡住 |
| 3 | **每个用户一份 `DSH_HOME`** | 会话存储的键是**绝对路径**（`--home-deploy-proj-hupo--`）。两个用户的工作区若同名，**共享 DSH_HOME 就会撞进同一份记忆** |

> 第 2 条还有个未来理由：**万一以后要收紧"读"，平行布局不用搬家。**

### 3.2 沙箱模式

| 作用域 | 模式 | 说明 |
|---|---|---|
| 主目录 | `workspace-write` | 只能写 `/data/main` 内 |
| 各子工作区 | `workspace-write` | 各写各的 |
| 读 | —— | ⚠️ **默认不受限**（见 §2.3）。靠"**KV 指针 + 检索**"让它没有理由去翻目录，而不是靠堵 |

### 3.3 状态清单（**备份 / 迁移 / 删除的唯一依据**）

```
容器内属于"这个用户的状态"：
  /data/main/                    主目录的文件
  /data/workspaces/*/            各工作区的文件
  /data/hupo/memory/             记忆索引 KV
  /data/hupo/apps/               生成的小程序制品
  /data/hupo/audit/              审计
  $DSH_HOME/sessions/            会话历史（记忆本体）
  $DSH_HOME/storages/            投影 / 检查点
  $DSH_HOME/.credentials.yaml    ⚠️ 含模型密钥 → 备份必须加密

容器内**其他一切**可抛弃（基础镜像、系统包、临时文件）。
```

**这份清单是一个零成本、但不许推迟的东西**：清单就是几行路径；等到做备份时再回头猜，就是在已经跑起来的系统上考古。

### 3.4 本机现状（**决定什么时候能动工**）

【实测】本机 **不是** 生产机，是仓库快照 + 一套新装的构建链：

| 项 | 状态 |
|---|---|
| 仓库 | 只有 `/home/deploy/proj/hupo`（`/home/deploy/projects/assistant` **不存在**） |
| 服务 | `concierge-core` inactive；无 timer / slice |
| Flutter / JDK / Android SDK | **已装**：`~/sdk`（Flutter 3.35.1 · Dart 3.9.0 · 修订号 `20f8274939`） |
| docker | 已装，但 `deploy` **不在 docker 组**（socket `root:docker 660`） |

> ⚠️ **A4 不是一个选择，是一个约束**（产品面板第二轮裁决）。
> 因为 **`sudo` 要密码**，所以 `usermod -aG docker deploy`（加 docker 组）**和**
> 装 rootless podman **两件当前都做不了**。
> 所以"先做权限与清单、容器往后放"**不是保守路线，是当前权限下唯一能走的顺序**。
> 产品面板一致永久否决"把 `deploy` 加进 docker 组"（那等于给一个跑着 agent 的账号免密 root）。
> 容器的定位因此从"第一步"降为"**开第二个席位的开门条件**"。
| rootless 路线 | **被 AppArmor 挡住**：`apparmor_restrict_unprivileged_userns=1`（Ubuntu 24.04 默认），`bwrap` / `unshare -U` 全部 `Permission denied` |
| podman | 未装（但 `/etc/apparmor.d/podman` 已存在 ⇒ 装了就能走无根） |
| 机器 | 32 核 / 62G / 162G 空闲 —— **比生产机（4 vCPU / 7.2G）宽裕得多** |

⇒ **凡是不需要 docker 的块，今天就能动工。**

## 四、身份与数据边界（块 8）

### 4.1 身份标识

| 标识 | 形态 | 谁看得见 | 变化 |
|---|---|---|---|
| `userId` | 字符串，**不再恒为 `owner`** | 调度器 / 容器 | ➕ 立起来（v7 标着"现在没有"） |
| `chatId` | = v7 的 `conversationId` | **客户端** | 语义**不变**（"我在跟哪一个聊天"） |
| **`scopeId`** | 一个工作区 = 一条 DSH 会话 | **只有调度器** | ➕ 新增 |
| `messageId` | `u_*` / `m_*` | 客户端 | 不变 |
| `taskId` | `task_*` | 客户端 | 不变 |

> **关键**：掩饰发生在调度器，所以**客户端协议几乎不用改**。
> `PROTOCOL.md` 不需要为多作用域做任何修改——客户端仍然只认一条 `chatId`。

### 4.2 三层实体与"谁拥有记忆"

| 层 | 实体 | 是什么 | 拥有记忆？ |
|---|---|---|---|
| 归置 | **workspace** | 一个目录 + 标题 + 排序 + 该目录下的会话清单 | ❌ **不拥有**（对模型完全不可见，零上下文成本） |
| 干活 | **session** | 一次连续对话；**自带 workspace root** | ✅ **记忆在这里** |
| 落盘 | `$DSH_HOME/sessions/<root 编码>/` | 历史文件 | —— |

⚠️ **"一个文件夹一套记忆"是结果，不是 workspace 这个实体在管。**
这条区别决定：改工作区名、归档、删图标时，动的是"归置"还是"记忆"。

### 4.3 v1 的简化

> **一个工作区 = 一条会话 = 一个目录 = 桌面上一个图标（1:1:1:1）。**

这条简化让整个模型干净：切换对话框 = 切换工作区 = 切换会话 = 同一件事。

### 4.4 作用域一致性（**不变量**）

> **界面显示的作用域，与 session 的 workspace root，必须始终一致；不一致就报错，不许继续。**

为什么单列一条：只切界面没切 root，会出现"**界面上我在小升初里，说话却写进了顶层**"。
这种 bug 最难查，而且它让隔离**静默失效**。

### 4.5 切换的本质

**【实测】** root 是**会话创建时**定下的（会话头里记着 `cwd`），**运行中改不了**。

> 所以"进入工作区" = **结束当前这条 + 开一条新的（带新 cwd）**。
> **是"换一条会话"，不是"改一个字段"。**

## 五、跨作用域转交协议（块 9）

### 5.1 Case 1：A 判断该转给 B（用户在场）

**时序**

```
A 正在回答（同一条 messageId，同一个气泡）
  │
  ├─ ① A 调用 handoff_to(scope, reason)            ← ⚠️ 工具调用，不是自然语言
  │
  ├─ ② A 那条 message **不 end**，状态置 handoff
  │      → 客户端显示「马上说完」（【实测】现有 StreamStatus.handoff 的文案）
  │
  ├─ ③ 调度器组装交接包 → 交给 B
  │
  ├─ ④ B 输出 → 写进**同一条 messageId**
  │
  └─ ⑤ B 输出完 → message/end → 用户看到**一条完整的气泡**
```

**用户看不到接缝，因为接缝没被画出来。** 一条 `messageId` 从 A 开始、由 B 收尾；
客户端只认调度器给的 `messageId`，不需要知道中间换了人。

而且这**不违反**"消息不许交叉"（v6 附九）：这不是"写回更早的气泡"，
而是**同一条气泡的正常追加**，只是作者换了。

**交接包**（沿用 `ARCHITECTURE-seamless.md` §2 的"交接包"）

```
【事实】用户原话 + 时间 + 出处（messageId）
【事实】A 已经说出口的全文                        ← 必需，否则 B 会重说一遍
【A 的判断，非事实】A 认为该你来处理，理由是 …     ← ⚠️ 必须标成判断
【系统提供】B 是哪个工作区、职责是什么             ← ⚠️ 不由 A 现编（见下）
【语气样本】A 最近 2–3 句原文                     ← 让 B 自己生成承接
```

**承接必须由 B 生成**——这是 `seamless` §2"**承接不是拼装出来的，是生成出来的**"在同一条纪律上的跨 agent 版本。
禁止调度器写"关于你的问题，B 认为……"这种断裂式开头（`seamless` §4.2 明令禁止）。

### 5.2 四条硬要求

| # | 要求 | 不做会怎样 |
|---|---|---|
| 1 | **挂起必须有超时，且必有合法收尾** | 用户看到一个永远写着"马上说完"的气泡——**v6 附八"还有件事在处理"从 15:31 挂到 16:39 的同一形态** |
| 2 | **B 必须拿到 A 已输出全文** | B 把问题重答一遍，同一条气泡里说两遍 |
| 3 | **A 与 B 人格差异要小** | 用户觉得"换了个人"（`seamless` §4.3：**voice 共用、role 分开**） |
| 4 | **失败要回退给 A** | 转交失败而 A 已"完成"，用户的话僵在半路（违反 N11"拒绝要给人话"） |

### 5.3 三条约束

| # | 约束 | 理由 |
|---|---|---|
| 1 | **转交必须是一次工具调用，不许解析自然语言** | 可审计 + 可授权 + 不靠猜。A 被污染后随便说一句不该能触发转交 |
| 2 | **一轮内最多转交一次，禁止回环（A→B→A）** | 否则用户被踢来踢去——与"不留人、不拖时间"直接冲突。B 答不了就说答不了 |
| 3 | **转交的前提是"目标工作区已经存在"** | 否则每遇到一个话题就临时造 agent = 无限增殖，违反"单次不生成、多次才生成" |

第 3 条展开：

| 情形 | 怎么办 |
|---|---|
| B 已存在 | ✅ 转交（收益：记忆 + 专业上下文） |
| B 不存在、这是第一次 | ❌ **不转交**，A 自己答完（省一次 2.7–5.1s 冷启动 + 一次交接损耗） |
| 反复出现（第 2~3 次） | 这时才**提议**建 B —— 频次当闸门 |

> **转交不是"换个更懂的人来答"，是"回到那个已经存在的专门地方去答"。**

### 5.4 "B 是什么"不由 A 现编

A 不知道 B 的真实能力，**它只能编**，而且每次编得还不一样。

**正确做法**：A 只说"该交给谁"；**"谁是什么"由系统查**
（`dsh-subagent` 可 inspect children 的 mode / activity / lineage，**不用加载它们**）。

这跟"AI 不能每次现编数据源"是同一条：**能力目录由系统维护。**

### 5.5 tainted 的 A 不许转交

A 读过网页内容 → A 被污染 → A 说"该交给 B" → B 是有权限的执行体 → **B 照做**。

这是"**网页 → A → B → 执行**"一条跨 agent 注入链，而 A 的转交决定就是扳机。

⇒ **A 处于 tainted 时，`handoff_to` 应被 deny**（或转交过去的内容仍带 taint，B 也走只读档）。
现有"来源分级 + taint 棘轮 + 清 taint 只在 host"正好覆盖，**不用新造**。

## 六、主作用域的记忆索引 KV（块 10）

### 6.1 原语选型（**不写 `kv.js`**）

| 要什么 | 用哪个 | 关键性质 |
|---|---|---|
| 精简、持久、可校验的 KV | **`dsh-storage-domain`** + `dsh-storage-json` | schema 校验；读同步；**写持久化成功才返回**；发 `domain/changed`；**对模型不可见** |
| "KV 是派生、事件流才是权威" | **`dsh-session-projection`** + `-cache` | 从**已提交事件**推导；"**日志永远是权威，崩溃只可能落后，绝不超前**" |

> **N6 不变量不是设计出来的，是这个原语的固有性质。**
> 落地位置：`~/.dsh/storages/<域>.json`（本机实测该目录已存在）。

### 6.2 "KV 精简"与"前缀只追加"是一对天生矛盾

- **KV 的本质是覆盖更新**（报名截止从 3/15 改成 3/20）
- **R2 的本质是只追加**（【实测】追加尾部 95.6% vs 插最前 18.5%，**18 倍成本差**）

解法是**分两层**：

```
索引层（常驻上下文，永远精简）
   实体/主题 + 一行 + 指针
   例：小升初 → "报名 3/20 截止，材料已备" → {chatId, scopeId, seq 范围}

详情层（不进上下文，按需检索）
   事实明细 + 原始会话
   工具：dsh-session-query-sqlite（跨会话 FTS5）
```

- 每轮只在**尾部追加**"本轮相关的索引条目"（v7 §4.5 已这么写）
- **完整 KV 留在 storage domain 里，当工具查，不当 prompt 注入**
- ⇒ 上下文不长、前缀不动、KV 可无限长

### 6.3 键的定义

**键 = 实体 / 主题**（不是会话）。因为要的是"记忆关联"，关联的是**事**。

```
key: 小升初
  facts:
    报名截止 = 2026-03-20   source:{chatId,scopeId,seq}   trust: owner-confirmed
    目标学校 = [A, B]       source:{...}                  trust: owner-said
    面试形式 = ？                                          trust: unknown   ← 空着比编好
  sessions: [ {scopeId, 一句话摘要, 时间} ]                ← 指针，不是内容
```

> **第三行的写法是关键**：让"**不知道**"成为一个**可表达的状态**，
> 而不是一个等着被填的空缺。这是"主目录不许替子目录编细节"的机械保障。

### 6.4 三个必须防的失败模式

| # | 失败模式 | 防法 |
|---|---|---|
| ① | **编造 → 固化 → 反复引用**：模型抽取 → 幻觉进 KV → 持久化 → 每轮注入 → **它变成"记忆"**，且比原始对话更难怀疑（看起来像结论） | **无出处不写**（N4）。每条必须带 source 指针；无 source 只能进"待确认"，不能进"受信" |
| ② | **KV 与真相冲突**（用户后来改了日期） | 冲突以**事件流为准**（N6，`-projection` 已保证"永不超前"）；每条带指针可回查 |
| ③ | **KV 成为"注入持久化"的落点**：被网页影响的 agent 写进一条假记忆，以后每轮都信 | **KV 由 hupo 持有，agent 只能通过工具访问**；写入过 **provenance 校验**（有没有出处、来自什么来源、要不要采信）。**不能让 agent 直接写文件**——那会绕过全部审计 |

> ③ 直接扩展了 v7 §10.2 那张清单："所有会自动进未来上下文的落点（人格/设置/profile patch/画像/手册）都进完整性清单"
> —— **KV 是这张清单上新增的、也是最值钱的一项。**

### 6.5 更新节奏（照监控层已有的分层）

| 部分 | 成本 | 做法 |
|---|---|---|
| 机械（谁何时聊过、标题、时间） | **免费** | 直接用 `dsh-session-projection` / `dsh-session-title` 算 |
| 语义（"报名截止 3/20"） | **花钱** | 快模型 + **关思考**（【实测】提炼换 flash/none：p50 12.0s→6.5s、降级率 100%→0） |
| 时机 | —— | **异步**。用户说话→看见第一句这条路上**不许有 KV 抽取** |

与监控层"机械规则免费 + 语义判断 60s 冷却"**同构**，节奏可直接搬。

## 七、焦点与投递（块 11）

### 7.1 Case 2：用户跟 A 聊到一半切走

**决定：A 继续做完，结果搁置，不投递、不触发。**

理由：**用户切走 ≠ 话题结束，而意图不可知**。
- 猜"切走 = 结束" → 误判
- 猜"切走 = 还相关" → 也误判
- **不猜，两端各自做完、互不投递** → 零误判

这是"**沉默优于编造**"从"答什么"搬到"投给谁"。

**精确表述**

> **A 照常做完，结果照常进 A 的会话历史、照常进统一时间线。不做任何跨作用域投递。**

于是出现一个很大的简化：

> **"搁置"不是一种新状态。它就是"A 的消息正常写完了"。**
> **"隐藏"不是"不投递"，而是"不实时提醒"。**

服务端只有一条时间线；"现在显示哪一段"是**客户端**的事。
用户切回 A 时，靠统一的 `seq` 补发，那段自然就在——**不需要为这个 case 写任何新机制**。

### 7.2 三件要做的小事

| # | 做什么 | 为什么 / 落点 |
|---|---|---|
| 1 | **A 要知道"用户当前不在我这一层"** | 否则 A 会说"**你看一下**"——对着空房间说话，进了历史还怪。落点：`dsh-system-prompt` 的 **dynamic runtime facts**（"当前焦点在 scope X"就是一个动态运行时事实） |
| 2 | **未读标记**（桌面上 A 的图标带小点） | "**动作可静默，事实不能静默**"最轻的落实。不加则"有东西可看"这件事被埋 |
| 3 | **A 被回收前结果必须落盘** | A 跑完就 idle、30 分钟后被回收；**回收前结果必须在盘上**。这条与"用户跑了"天然冲突——那正是最没人盯着的时候 |

### 7.3 已有机制正好收尾

`message/seen` / `POST /api/receipt`（客户端回报"我看到了"）。

⇒ A 能知道**哪些话用户看过、哪些没看**。用户切回 A 时，A 不会说"我刚才说了呀"
（它知道用户没看见）——**这就是"记忆说真话"**。

### 7.4 要盯的账

A 继续跑 = 一个活跃 session = **195MB**（**实测**，周慎第二轮量的；本文件早先引用的 172MB 偏低，**落地后必须再校准、只许往上调**）。
用户开几个工作区就有几个 ⇒ **idle 回收必须有，且回收前必须落盘**。

⚠️ **现有实现的缺口**：`agent-runtime.js` 只有 **per-session 的 30 分钟 idle TTL**，
**没有全局 LRU、没有按内存淘汰**（`grep -i lru` 在 `services/core/src` 与 `src/` 都是 0 命中）。
多作用域并行之后，这条从"优化"变成"不做就会 OOM"
（生产机 `MemoryMax=1G`，一个 agent 195MB ⇒ **3–4 个并发就撞上限**）。
**而且 30 分钟太长**：1G / 195MB ⇒ 3 个并发就满，30 分钟的回收等于没有回收 ⇒
非焦点工作区应 **10 分钟无事件即卸载**（收口后再卸，绝不许被卸载杀掉）。

## 八、调度器的三个职责

```
调度器（永续，同时持有 A、B、C… 每条会话）
 ① 对用户的路由
      当前焦点在哪条 → 它的输出投给用户
      其它条的输出 → 照常进时间线，但**不实时提醒**（§7.1）
 ② agent 之间的邮政
      B 干完了 → **调度器收下并落盘** → 按"A 闲时"投给 A
 ③ 归一化
      把 N 条会话的输出合成用户看到的**那一条连续时间线**
      全局 seq 由调度器分配（**不是 DSH 的 session 内 seq**）
```

**② 的两个要点**

1. **汇报必须由调度器收下并落盘，不能依赖 DSH 的 in-session notice。**
   因为【实测】`dsh-tool-jobs`："**待投递的通知不会在宿主销毁后存活**"，
   而 B 有 30 分钟 idle TTL。用户的场景恰恰是"用户跑了、B 还在干活" ——
   **调度器是永续的，它是唯一能保证"这句话不丢"的地方。**
2. **"闲时"有机械判据**：`dsh-tool-jobs` 明确区分 busy / idle
   （"忙的在下一步收到，空闲的可被一次有界 follow-up turn 唤醒"）。

**③ 的形状你已经有了**：`Conversation.emit()` + 全局 `seq`。
要改的只是"来源"——从"唯一那条 session"变成"当前活跃的那条"。
**客户端的 `sinceSeq` 续传逻辑一个字都不用改。**

### 8.1 唤醒风暴（要设闸门）

`dsh-tool-jobs` 专门有 "consecutive wakeups" 配置 ⇒ DSH 作者已预见此风险：
B 完成 → 唤醒 A → A 干活产生新 job → 又唤醒 → 成环。

⇒ 设闸门：**同一对 agent 的唤醒频率上限** + **汇报可合并投递**（一次投多条的摘要，而不是每条唤醒一次）。

## 九、来源标记（第一类公民）

调度器**知道每条消息来自谁**——DSH 不需要知道（`session/prompt` 在会话日志里始终是 user message），
**在文本里带标记**即可（协议内约定，不依赖 DSH 元数据）。

**你已经在这么做了**：`timelineContext` / `#withRecap` 就是"把一段带标记的背景块拼在用户原话前"的现成实现。

**一处标记、四处生效**：

| 用途 | 用来源做什么 |
|---|---|
| 展示 | 客户端显示"这句话来自 B" |
| **权限** | 不同来源 → 不同能力档（taint 棘轮） |
| **记忆** | 进 KV 时带 `source` / `trust`（N4） |
| **审计** | 谁在什么时候说了什么 |

来源取值从 v7 的 `owner / product / derived / foreign` 扩展为：
**`user` / `dispatcher` / `agent:<scopeId>`**。

⚠️ **B → A 的汇报，来源等级是 `derived`（不可信），不是 `owner`。**
理由：B 自己会联网，**B 可能已被它读到的网页内容污染**。
⇒ 按现有规则 **A 读到 B 的汇报就该降只读档**。
⇒ **A 可以"知道"，但不该因此"获得权限"**：不能因为 B 说了什么就去执行有副作用的动作——
那必须等主人的原话（清 taint 只在 host）。

**这条不是额外设计，是现有不变量的自动推论**，而且它堵住了"网页 → B → A → 执行"这条链。

> `dsh-session-reference` 的快照**天生就是这个语义**：
> "**untrusted** background context" + "**禁止把里面的内容当成指令、权限声明或工具请求**"。
> 给 B 的注入块、以及 B 给 A 的汇报，**应沿用这个语义**，不要自己发明。

## 十、新增不变量（接 v7 的 R1–R5 / N1–N11）

| # | 不变量 |
|---|---|
| **N12** | **界面作用域 = session 的 workspace root**，不一致就报错，不许继续 |
| **N13** | **跨作用域只走摘要与指针，不走原文**；工作区之间的会话历史永不互通 |
| **N14** | **主作用域可以不知道细节，但不许替子作用域编细节**（"不知道"必须可表达） |
| **N15** | **切换作用域前必须把上一条气泡收口**；收口完成前不许开新的（v6 附九的跨作用域升格） |
| **N16** | **转交必须是一轮内最多一次、禁止回环**；且前提是目标工作区已存在 |
| **N17** | **KV 无出处不写**；未采信的只能进"待确认"，不得作行动依据（N4 的落地口径） |
| **N18** | **agent 不许直接写 KV**；写入必经 hupo 的工具与 provenance 校验 |
| **N19** | **挂起必有超时，且必有合法收尾**（不许留下永远"马上说完"的气泡） |
| **N20** | **动作可静默，事实不能静默**：跨作用域发生的事必须有可见痕迹（未读标记） |
| **N21** | **同一用户一份 `DSH_HOME`**（会话存储的键是绝对路径，共享即串记忆） |
| **N22** | **时间线权威源**：全局 `seq` = **已落盘事件的最大 seq + 1，只增不减**；**同一时刻只有一条会话能写可见时间线**；显示用**发生时刻**，补发段必须带"你不在时" |
| **N23** | **协议必须带 `scopeId` 与来源**（客户端 v1 可以只显示"它"，但**字段现在就留**——协议一旦上线就改不动） |

## 十四、需要你审阅的点

按"非你拍板不可"排序：

1. **容器是"执行体"还是"资产"** —— 已定：**数据在容器里**（你说"容器就是用户的整个世界"）。
   连带要求：**"状态清单"（§3.3）现在就要写下来**，否则备份/迁移/删除都没有依据。
2. **备份推迟可以，但"加密"和"恢复演练"不能省** —— 压缩 ≠ 加密；
   `$DSH_HOME/.credentials.yaml` 在一个包里。没演练过的备份不算备份。
3. **§5.3 的三条约束**（工具触发 / 一轮一次禁回环 / 前提是工作区已存在）——
   这是我加的，直接影响用户体验（转交频率）。
4. **§6.5 的"KV 语义抽取"要不要做** —— 不做也能跑（只有机械索引），
   做了才有"主目录记得小升初的报名截止日"。
5. **转交时 A 与 B 的人格差异**（§5.2 第 3 条）—— 这决定用户会不会觉得"换了个人"。
6. **§11 待实测 7 条**里，第 1、3 条影响最大（前缀纪律 / 读能不能限）。

**一句话总览**：这套架构里，**DSH 提供"每一次对话"，调度器提供"这一个窗口"**；
用户以为在跟一个人说话，实际是调度器在替他换人——而**换人的接缝从来没被画出来**。
能复用的（工作区、会话分区、检索、投影、归档、任务通知、上下文注入）**一律不自己写**；
必须自己写的只有三件：**对用户的路由、agent 之间的邮政、归一化成一条时间线**。
