## 1. 三层架构：L1 终端 / L2 调度器 / L3 工作层

### 1.1 三层大图（〔v7〕一、三层 + 旁路）

〔v7〕§一 的原文图（节选原句）：

- **L1 终端层（Flutter：Web / iOS / Android）**：壳＝一条有序时间线（按 seq 排，**绝不配对**）；quick + deep 同气泡 ｜ status 与正文不互转 ｜ 来源独立通道；容器＝小程序运行时（H5 / 沙箱 / 独立 origin / 清单 / 版本 / 回滚）；桌面＝图标墙。**「只上报事实，不做判断」**
- **L2 调度层（`services/core`，永续，`systemd concierge-core:8091`）**：入口 `/api/say`（幂等）｜`/api/stream`（WS，`sinceSeq` 续传）｜`/api/receipt`；账本；节奏；策略；制品。**「不能有表达欲」（唯一例外：产品固定话术）**
- **L3 工作层（可死可重启：一个会话 = 一个真 agent 进程）**：主 agent（人格 / 工具 / 上下文装配 / 跨重启接记忆 / 说话画像）；子 agent（后做）；知识层（后做）KV `facts`；工作区 `~/hupo-workspace`。**「永不直接对用户说话」（话由主 agent 出口）**
- **旁路：监控层**（独立 `debug:<会话>` 进程，**只读档**）；〔v7〕§一：**「旁路为什么单独画：它是第二个执行体，而且它的输入是主 agent 的输出（可被网页污染）。所以它拿只读档，产出不许进'指令位'。」**

通信（〔v7〕§一 图两侧）：
- L1 ⇄ L2：**HTTPS + WebSocket（Bearer 令牌，WS 走子协议）**
- L2 ⇄ L3：**stdio JSON-RPC（`dsh --profile sdk --patch <role>`）**

三层对应到代码（〔三层草稿〕§〇 一页纸结论）：

| 问题 | 答案（原文） |
|---|---|
| 三层里哪层已经成型？ | **L2 调度层**（`dispatcher.js`）和 **L3 的主 agent** + **监控层** |
| 哪层完全空白？ | **L3 的知识层（KV）**；**L1 的小程序运行时**；**横跨 L1/L2 的制品管线** |

### 1.2 L1 终端 —— 是什么、跑在哪、用什么通信、边界在哪

**是什么**（〔L1〕开头 + §1.2 + §十四）：
- 范围：**`apps/mobile/`（Flutter：Web / iOS / Android）**。不含 L2 调度器与 L3 工作层。（〔L1〕开头）
- 职责：**渲染一条有序时间线；装小程序；上报事实**。（〔v7〕§二）
- 通信：**HTTPS + WebSocket（Bearer 令牌）**（〔三层草稿〕§二图）；契约见〔v7〕§3.2/§3.3。
- 契约来源（〔L1〕开头）：`ARCHITECTURE-v7.md` §3（命名与接口）为唯一契约，本文照抄不改；协议规则见 `packages/protocol/PROTOCOL.md`（R1–R14 继续有效）；UI 细节见 `docs/UI-terminal-floating-chat.md` + `docs/ui-terminal.html`；拍板见 `docs/pm-panel/DECISIONS.md`。

### 1.3 L2 调度器 —— 是什么、跑在哪、用什么通信、边界在哪

**是什么 / 跑在哪**（〔v7〕§一、§八）：
- `services/core`，**永续进程**，`systemd concierge-core:8091`。
- 定位：**节奏、任务账本、协议翻译、对账续做、准入与预算、制品分发**。（〔v7〕§二）
- 通信：对 L1 ＝ **HTTPS + WS**；对 L3 ＝ **stdio JSON-RPC**（〔v7〕§3.4）。

**L2 的「绝不」/「不许」（逐条）**：

| # | 原文 | 出处 |

| 2 | 调度器：不实现对话语义（那是 DSH 的）；不写台词（除产品固定话术） | 〔手机〕§一 |

### 1.4 L3 工作层 —— 是什么、跑在哪、用什么通信、边界在哪

**是什么**（〔L3〕§〇 一页纸，逐条原文答案）：

| 问题 | 答案 |
|---|---|
| L3 是什么 | **一个会话 = 一个真 `dsh` 子进程**；它就是接收层/处理层/反馈层三段输出的**同一个人** |
| 它怎么被起 | `dsh --profile sdk --patch <role-patch>`，**白名单 env** + `DSH_PERMISSION_MODE` |
| role 三类 | `owner`（全权但受 taint 约束）/ `untrusted`（只读档）/ `monitor`（只读档） |
| 能力几档 | **两档**：受信档 / 只读档 |
| 说话的是谁 | 主 agent；子 agent **永不直接对用户说话** |
| 记忆 | 事件流是真相源；L3 只加 `facts`（带出处与采信） |
| 最危险的一条 | agent 仍挂 `danger-full-access` + **免密 sudo**（实测 `sudo -n true` 通过） |

**跑在哪 / 进程模型**（〔L3〕§1.1）：
- 一个会话一个常驻 agent；实测空闲 **195MB RSS**（v7 §9 记 172MB，同一量级）。
- 冷启动 **2.7–5.1s**；空闲回收 **30 分钟**（`agentIdleEvictMs`），回收时 `dispose()` → `shutdown` + SIGTERM。
- 会话 id：我们这边 `sessionId` → DSH 那边 `${sessionId}.${bootId}`；**为什么要 bootId 后缀：SDK 只能 create 不能 resume**。
- 进程池：`Map<sessionId, AgentSession>`，`agent(sessionId)` 惰性创建。
- 并发上限：**无**（今天唯一的收敛手段是 30 分钟空闲回收）。

**L3 的「绝不」/「不许」（逐条）**：

| # | 原文 | 出处 |
|---|---|---|
| 1 | **永不直接对用户说话**（话由主 agent 出口） | 〔v7〕§一、§二 |
| 2 | 子 agent：不许直接对用户说话；不许越过自己的工具档 | 〔v7〕§二 |
| 3 | **「一个会话一个 agent；它说的话由它说，但**它能做什么由 host 说了算**。role 决定 patch，patch 决定能力，taint 决定角色，而 taint 只有主人能清。」** | 〔L3〕附 一句话纪律 |
| 4 | **L3 里不许出现"最多 N 个会话"这种常量** | 〔L3〕§1.3 |
| 5 | **role 只能在 spawn 层决定**（hook 的 `SubagentStart`/`SubagentStop` matcher 是常量 `general-purpose`）⇒ 必须在 `AgentRuntime` 里做 | 〔L3〕§1.2 |
| 6 | **只读档「不许限制只读与写工作区」**（拍板第 6 条）：所以**不能**把 `tool-fs` 整个 disabled —— 那会把"读文件"也一起杀掉，agent 变废人 | 〔L3〕§2.2 |
| 7 | hook 里**只写 `deny`，不写 `ask`**（SDK 会话没有人应答 `ask`） | 〔L3〕§2.4 |
| 8 | **`sandbox mode` 不是安全边界** ⇒ 降档做成**换进程**；**进程级隔离，模型碰不到** | 〔L3〕§2.4 |
| 9 | 人格硬规则 9 条：**先应一声**（第一句 ≤25 字、不给结论、**必须排在工具调用之前**、且**同一轮**）；**不许留客式追问**；**不许说要做然后不做**；**不许编造**（七类点名）；**不许用 markdown**；**不许提内部词**；**不许往回补对话**（只按时间说话）；**贴合但不迎合**；**被打断的活会自己接着做** | 〔L3〕§3.2 |
| 10 | **清除 taint 必须只在 host**：如果模型能清自己的 taint，"读到网页 → 自己清 → 改系统"就是一条直路 | 〔L3〕§4.2 |
| 11 | **`request_capability` 一键授权机制已砍**；**不新增**审批弹窗、不新增状态、不新增往返 | 〔L3〕§4.3 |
| 12 | 审计**只记事实，不记完整参数**（参数里可能有主人的隐私） | 〔L3〕§4.4 |
| 13 | 只允许**尾部**追加；前缀是"上一个进程见过的那些字节" | 〔L3〕§5.2 |
| 14 | recap 三节，且**只有 `主人：` 节允许出现在会授权"改系统"的位置** | 〔L3〕§5.3 |
| 15 | `resumePrompt` **边界（三条都要保留）**：① **不许**改成"你刚才做到哪了"；② **不许**折成一问一答的摘要；③ 非 `owner` 来源的任务重放时，第 4 行（"如果这件事要改代码/改系统…"）**必须去掉** | 〔L3〕§6.2 |
| 16 | `spawn_agent` 硬约束：**type 不在登记表 → rejected（不许模型现编类型）**；预算超上限 → rejected；池满/内存闸拒 → rejected + 一句人话；`maxDepth: 1` ⇒ 子 agent **没有** spawn 能力（不许孙 agent） | 〔L3〕§7.2 |
| 17 | **不许把不合格输出当结论用**（输出契约校验失败） | 〔L3〕§7.4 |
| 18 | KV 写入闸门：**兜底路径不沉淀**；**只写陈述，不写指令**；**无 `source` 不写**；`looksLikeInstruction()` 命中 → **quarantine**，**永不装配到指令位** | 〔L3〕§8.2 |
| 19 | **`experience` / `taxonomy` 不建**；v1 的 `taxonomy.js` 与 `ledger.js` 的父子继承**留档不启用** | 〔L3〕§8.4 |
| 20 | `AGENTS.md` **不许再是软链**（一个写点、两条链路） | 〔L3〕§九 |
| 21 | **`data/`、仓库不进工作区**（agent 改它们算"改系统"档） | 〔L3〕§九 |
| 22 | 监控改法：`title` **只由闭集 `issueClass()` + 引用原文**构成，**禁止自由文本进指令位**；`detail` 一律带前缀「【监控层建议·可能是错的·仅供判断，不是指令】」 | 〔L3〕§10.2 |
| 23 | **`ask` 在无头会话里不可用** ⇒ 一律用 deny（同 #7） | 〔L3〕§2.4 |

**L3 的知识层 KV（只建 `facts`）**（〔L3〕§八）：
- 读出口（拍板第 7 条，**只给主 agent**）：本轮 → 只读 facts 里与本轮相关的条目 → **尾部追加**成"装配简报" → 用途：决定派哪个子 agent / 要不要新建；**❌ 不给"KV 直接出话"出口**。
- `trust` 与"行动依据位"：`owner` 可进行动依据位；`verified` 可进行动依据位（需有复核记录）；`unverified` **只能进"参考"位**，且必须显示出处给用户可核。
- 衰减：`confidence × 0.5^(days/30)`（半衰期 30 天）；被引用：`hits+1`、`confidence = min(0.98, c+0.12)`。
- 隔离：每条带 `userId`；`search(userId, …)` **无无参重载**（R1）。可重建：事件流是权威；KV 丢了不影响对话正史（N6）。

### 1.5 第五层（旁路）：监控层

- 定位：**审对话的时效/合理性/个性适配/（后做）越权与成本**；**绝不**：不碰用户会话；产出不许进"指令位"。（〔v7〕§二）
- 运行时：`debug-agent.js#judge` 把 `timeliness.turns[].text`（**主 agent 自己的输出**，里面正带着它刚抓来的网页正文）拼进 prompt，发到 `this.runtime.agent('debug:'+id)`；由**同一个 `AgentRuntime`、同一份 cfg** 起，因此**同人格、同 `danger-full-access`、同免密 sudo、无 `toolFilter`**。（〔三层草稿〕R-SEC-11）
- 链路：**网页 → 主 agent 回答 → 监控 agent 上下文 → 任务簿 → 主 agent 执行**。（〔三层草稿〕R-SEC-11 第二跳；〔L3〕§10.2）
- 〔三层草稿〕§〇：**「监控层是第二个全权执行体」**（红队带来的四处实质修正之一）。
- 改造要求：role=`monitor`（只读）、`review` 完即杀、任务簿归属 root、删 `force`。（〔L3〕§十）

## 2. 多租户设计

> 主体出处：〔手机〕。这是它自称覆盖 v7 没有的三件事之一（〔手机〕开头：**「多租户：一个用户一台容器（v7 §15 悬空第 1 条"agent 仍挂免密 sudo"的答案之一）」**）。

### 2.1 一个用户一个容器

- 〔手机〕开头 §〇一句话：**「一台哑终端 + 一台云端专属主机 + 一个调度器。」**
- 〔手机〕§一与 v7 的关系表：

| | v7 的世界 | 本文的世界 |
|---|---|---|
| 用户 | 一个人（`userId` 恒为 `owner`） | **多个人，一人一台容器** |
| 会话 | 一条会话 = 一个话题 | **一条会话 = 一个工作区**；一个用户有多个工作区 |
| 客户端 | 一条时间线 | 一条时间线（**不变**），但底下是多条会话 |
| 隔离 | taint 棘轮 + 两档能力 | 加一层**容器**（物理）与**工作区**（逻辑） |
| 调度器 | 节奏 + 账本 | 加两件事：**对用户的路由** 与 **agent 之间的邮政** |

- 容器层在四层图里的位置（〔手机〕§一）：**「用户容器（= 这个用户的整个世界）」**，含三部分：
  1. 一份专属 DSH（会话运行时、上下文装配、流式、工具）
  2. 若干工作区（每工作区 = 一个目录 + 一条会话 + 桌面一个图标）
  3. hupo 地盘（记忆索引 KV / 制品 / 审计）
  - 注有 **【实测】DSH 的会话历史按 workspace root 分区落盘**。

### 2.2 容器里有什么（目录布局 —— 原文目录树逐字抄）

〔手机〕§3.1「容器内布局」，原文代码块：

```
/data/                          ← 容器内，这个用户的整个世界
  main/                         ← 主目录（顶层对话的 workspace root）⚠️ 不是 /data，不是 home
  workspaces/
    <scope-name>/               ← 子工作区（= 桌面上的一个 APP）
  hupo/                         ← hupo 的地盘，**不在任何 workspace root 里**
    memory/                     ← 记忆索引 KV
    apps/                       ← 生成的小程序制品
    audit/                      ← 审计
$DSH_HOME/                      ← 这份专属 DSH 的（会话历史按 root 分区）
```

〔手机〕§3.3「状态清单（**备份 / 迁移 / 删除的唯一依据**）」，原文代码块：

```
容器内属于"这个用户的状态"：
  /data/main/                    主目录的文件
  /data/workspaces/*/            各工作区的文件
  /data/hupo/memory/             记忆索引 KV
  /data/hupo/apps/               生成的小程序制品
  /data/hupo/audit/              审计
  $DSH_HOME/sessions/            会话历史（记忆本体）
  $DSH_HOME/storages/            投影 / 检查点
  $DSH_HOME/.credentials.yaml    ⚠️ 含模型密钥 → 备份必须加密

容器内**其他一切**可抛弃（基础镜像、系统包、临时文件）。
```

> 〔手机〕§3.3 末句：**「这份清单是一个零成本、但不许推迟的东西：清单就是几行路径；等到做备份时再回头猜，就是在已经跑起来的系统上考古。」**

### 2.3 三条硬规则（〔手机〕§3.1 原文）

| # | 规则 | 为什么 |
|---|---|---|
| 1 | **主目录 root 不许是 home** | `~/.dsh/.credentials.yaml`（模型密钥）、`~/.ssh/id_rsa` 会被**读**到；**`~/.bashrc` 会被写**到 ⇒ 持久化代码执行。**现有生产实现用的是 `~/hupo-workspace`，那是对的，别退回去** |
| 2 | **主目录 root 不许包含 `workspaces/`**（必须**平行**） | `workspace-write` 下主目录的 agent 会**写进子工作区**（算错一个相对路径就发生）。平行之后写被 root 挡住 |
| 3 | **每个用户一份 `DSH_HOME`** | 会话存储的键是**绝对路径**（`--home-deploy-proj-hupo--`）。两个用户的工作区若同名，**共享 DSH_HOME 就会撞进同一份记忆** |

> 第 2 条还有个未来理由：**万一以后要收紧"读"，平行布局不用搬家。**

### 2.4 沙箱模式（〔手机〕§3.2 原文表）

| 作用域 | 模式 | 说明 |
|---|---|---|
| 主目录 | `workspace-write` | 只能写 `/data/main` 内 |
| 各子工作区 | `workspace-write` | 各写各的 |
| 读 | —— | ⚠️ **默认不受限**（见 §2.3）。靠"**KV 指针 + 检索**"让它没有理由去翻目录，而不是靠堵 |

### 2.5 最重要的一句：`workspace root` 不是安全边界

〔手机〕§2.3 引用块原文：

> ⚠️ **本节最重要的一句话：`workspace root` 不是安全边界。**
> 它约束**写**，不约束**读**。把主目录和子工作区放成父子目录，
> **子工作区的文件对主目录的 agent 依然可读**。
> 记忆隔离靠的不是目录，而是"**会话历史按 root 分区**"（这一半是自动成立的）。

依据（〔手机〕§2.3 表）：`dsh-fs-sandbox` **只约束"写"** —— "confines model file **writes and edits** ... **while preserving the local filesystem's read behavior**"。

### 2.6 身份标识（〔手机〕§4.1 原文表）

| 标识 | 形态 | 谁看得见 | 变化 |
|---|---|---|---|
| `userId` | 字符串，**不再恒为 `owner`** | 调度器 / 容器 | ➕ 立起来（v7 标着"现在没有"） |
| `chatId` | = v7 的 `conversationId` | **客户端** | 语义**不变**（"我在跟哪一个聊天"） |
| **`scopeId`** | 一个工作区 = 一条 DSH 会话 | **只有调度器** | ➕ 新增 |
| `messageId` | `u_*` / `m_*` | 客户端 | 不变 |
| `taskId` | `task_*` | 客户端 | 不变 |

> **关键**：掩饰发生在调度器，所以**客户端协议几乎不用改**。`PROTOCOL.md` 不需要为多作用域做任何修改——客户端仍然只认一条 `chatId`。

### 2.7 本机现状与容器约束（〔手机〕§3.4，决定什么时候能动工）

| 项 | 状态 |
|---|---|
| 仓库 | 只有 `/home/deploy/proj/hupo`（`/home/deploy/projects/assistant` **不存在**） |
| 服务 | `concierge-core` inactive；无 timer / slice |
| Flutter / JDK / Android SDK | **已装**：`~/sdk`（Flutter 3.35.1 · Dart 3.9.0 · 修订号 `20f8274939`） |
| docker | 已装，但 `deploy` **不在 docker 组**（socket `root:docker 660`） |
| rootless 路线 | **被 AppArmor 挡住**：`apparmor_restrict_unprivileged_userns=1`（Ubuntu 24.04 默认），`bwrap` / `unshare -U` 全部 `Permission denied` |
| podman | 未装（但 `/etc/apparmor.d/podman` 已存在 ⇒ 装了就能走无根） |
| 机器 | 32 核 / 62G / 162G 空闲 —— **比生产机（4 vCPU / 7.2G）宽裕得多** |

> ⚠️ **A4 不是一个选择，是一个约束**（产品面板第二轮裁决）。因为 **`sudo` 要密码**，所以 `usermod -aG docker deploy`（加 docker 组）**和**装 rootless podman **两件当前都做不了**。所以"先做权限与清单、容器往后放"**不是保守路线，是当前权限下唯一能走的顺序**。产品面板一致永久否决"把 `deploy` 加进 docker 组"（那等于给一个跑着 agent 的账号免密 root）。容器的定位因此从"第一步"降为"**开第二个席位的开门条件**"。
> ⇒ **凡是不需要 docker 的块，今天就能动工。**

## 3. 作用域 / 工作区模型

### 3.1 作用域是什么（〔手机〕§四、§六）

- **`scopeId` ＝ 一个工作区 ＝ 一条 DSH 会话**（〔手机〕§4.1）。
- 工作区 ＝ **一个目录 + 标题 + 排序 + 该目录下的会话清单**（〔手机〕§4.2 "归置"层）。
- **v1 的简化**（〔手机〕§4.3 引用块原文）：
  > **一个工作区 = 一条会话 = 一个目录 = 桌面上一个图标（1:1:1:1）。**
  - 原文补充：**「这条简化让整个模型干净：切换对话框 = 切换工作区 = 切换会话 = 同一件事。」**
- 三层实体与"谁拥有记忆"（〔手机〕§4.2 原文表）：

| 层 | 实体 | 是什么 | 拥有记忆？ |
|---|---|---|---|
| 归置 | **workspace** | 一个目录 + 标题 + 排序 + 该目录下的会话清单 | ❌ **不拥有**（对模型完全不可见，零上下文成本） |
| 干活 | **session** | 一次连续对话；**自带 workspace root** | ✅ **记忆在这里** |
| 落盘 | `$DSH_HOME/sessions/<root 编码>/` | 历史文件 | —— |

> ⚠️ **"一个文件夹一套记忆"是结果，不是 workspace 这个实体在管。** 这条区别决定：改工作区名、归档、删图标时，动的是"归置"还是"记忆"。

### 3.2 作用域栈与焦点作用域

〔手机〕本身**没有出现"作用域栈"这个词**。与之直接对应的是〔手机〕§七「焦点与投递（块 11）」，以及旁证 `docs/design/R2-ENGINEERING.md` §3.2 给出的显式定义。

**〔手机〕§七 的原文要点**：
- §7.1 **决定：A 继续做完，结果搁置，不投递、不触发。**
  - 理由：**用户切走 ≠ 话题结束，而意图不可知**。
    - 猜"切走 = 结束" → 误判
    - 猜"切走 = 还相关" → 也误判
    - **不猜，两端各自做完、互不投递** → 零误判
  - 这是"**沉默优于编造**"从"答什么"搬到"投给谁"。
- §7.1 **精确表述**：
  > **A 照常做完，结果照常进 A 的会话历史、照常进统一时间线。不做任何跨作用域投递。**
  > **"搁置"不是一种新状态。它就是"A 的消息正常写完了"。**
  > **"隐藏"不是"不投递"，而是"不实时提醒"。**
- §7.2 三件要做的小事：
  1. **A 要知道"用户当前不在我这一层"** —— 落点：`dsh-system-prompt` 的 **dynamic runtime facts**（"当前焦点在 scope X"就是一个动态运行时事实）
  2. **未读标记**（桌面上 A 的图标带小点）—— "**动作可静默，事实不能静默**"最轻的落实
  3. **A 被回收前结果必须落盘**
- §7.4 要盯的账：A 继续跑 = 一个活跃 session = **195MB**；**非焦点工作区应 10 分钟无事件即卸载**（收口后再卸，绝不许被卸载杀掉）。

**〔旁证〕`docs/design/R2-ENGINEERING.md` §3.2「作用域」**，原文代码块：

```
一条可见时间线（客户端只认它）
  └── 作用域栈：[主目录] → [工作区] → …
        · 每个作用域 = 一个 workspace（目录）+ 一条 DSH 会话
        · 同时只有一个"焦点"作用域
```

- 该节「不变量」（原文）：N12（界面作用域 = session 的 workspace root，不一致就报错）、N15（切换前必须先收口）、N16（转交一轮最多一次、禁回环、目标必须已存在）、N19（挂起必有超时 + 合法收尾）。
- 该节「并行与上屏（别混）」：

| | 什么样 |
|---|---|
| **执行** | 随便并行——非焦点作用域该干活干活 |
| **上屏** | 排队——同一时刻最多一条未收口 |

### 3.3 作用域一致性（不变量）与切换的本质

〔手机〕§4.4 引用块原文：

> **界面显示的作用域，与 session 的 workspace root，必须始终一致；不一致就报错，不许继续。**

原文理由：**「为什么单列一条：只切界面没切 root，会出现"界面上我在小升初里，说话却写进了顶层"。这种 bug 最难查，而且它让隔离静默失效。」**

〔手机〕§4.5「切换的本质」：
- **【实测】** root 是**会话创建时**定下的（会话头里记着 `cwd`），**运行中改不了**。
- 所以"进入工作区" = **结束当前这条 + 开一条新的（带新 cwd）**。**是"换一条会话"，不是"改一个字段"。**

### 3.4 作用域与 DSH workspace / session 的对应关系

| 概念 | 对应 | 出处 |
|---|---|---|
| 作用域 `scopeId` | 一个工作区 ＝ 一条 DSH 会话 | 〔手机〕§4.1 |
| 工作区（workspace 实体） | 一个目录 + 标题 + 排序 + 该目录下的会话清单；**对模型完全不可见，零上下文成本** | 〔手机〕§4.2（引 `dsh-workspace`：**"invisible to models"**） |
| 会话（session） | 一次连续对话；**自带 workspace root**；**记忆在这里** | 〔手机〕§4.2 |
| 会话历史落盘 | **按 workspace root 分区**：`~/.dsh/sessions/--home-deploy-proj-hupo--/session-*/session.v3.jsonl.zstd`（`/` → `-`，两端补 `--`） | 〔手机〕§2.2 |
| 工作区登记表 | `~/.dsh/storages/workspace.json`：`global.workspaceIds[]` + `tables.workspaces[id] = {path, title, sessionIds[], createdAt, updatedAt}` | 〔手机〕§2.2 |
| 会话创建时可指定根 | `dsh-api-session-controller` 的 `CreateRequest { workspaceId?, **cwd?**, sessionId?, agentPreset? }`；存在动作 `openWorkspacePath` 与错误码 `session/workspace-attach-failed` | 〔手机〕§2.2 |
| 根是**会话级**的，不是进程级 | `dsh-api-workspace-files`："读取发生在 **Session** workspace root 内"；"每个方法都在线上带着 **Session identity**"；"**不借用父会话的根**" | 〔手机〕§2.2 |
| CLI 的 cwd 只是**默认值** | `@deepseek-ai/dsh` README：**"运行命令时所在的目录将作为默认 workspace 根目录"** | 〔手机〕§2.2 |

### 3.5 跨作用域转交协议（块 9）

**Case 1：A 判断该转给 B（用户在场）时序**（〔手机〕§5.1 原文）：

```
A 正在回答（同一条 messageId，同一个气泡）
  │
  ├─ ① A 调用 handoff_to(scope, reason)            ← ⚠️ 工具调用，不是自然语言
  ├─ ② A 那条 message **不 end**，状态置 handoff
  │      → 客户端显示「马上说完」（【实测】现有 StreamStatus.handoff 的文案）
  ├─ ③ 调度器组装交接包 → 交给 B
  ├─ ④ B 输出 → 写进**同一条 messageId**
  └─ ⑤ B 输出完 → message/end → 用户看到**一条完整的气泡**
```

- 原文：**「用户看不到接缝，因为接缝没被画出来。」** 且**「这不违反"消息不许交叉"（v6 附九）：这不是"写回更早的气泡"，而是同一条气泡的正常追加，只是作者换了。」**
- **交接包**（〔手机〕§5.1，沿用 `ARCHITECTURE-seamless.md` §2）：

```
【事实】用户原话 + 时间 + 出处（messageId）
【事实】A 已经说出口的全文                        ← 必需，否则 B 会重说一遍
【A 的判断，非事实】A 认为该你来处理，理由是 …     ← ⚠️ 必须标成判断
【系统提供】B 是哪个工作区、职责是什么             ← ⚠️ 不由 A 现编（见下）
【语气样本】A 最近 2–3 句原文                     ← 让 B 自己生成承接
```

- **四条硬要求**（〔手机〕§5.2）：

| # | 要求 | 不做会怎样 |
|---|---|---|
| 1 | **挂起必须有超时，且必有合法收尾** | 用户看到一个永远写着"马上说完"的气泡——**v6 附八"还有件事在处理"从 15:31 挂到 16:39 的同一形态** |
| 2 | **B 必须拿到 A 已输出全文** | B 把问题重答一遍，同一条气泡里说两遍 |
| 3 | **A 与 B 人格差异要小** | 用户觉得"换了个人"（`seamless` §4.3：**voice 共用、role 分开**） |
| 4 | **失败要回退给 A** | 转交失败而 A 已"完成"，用户的话僵在半路（违反 N11"拒绝要给人话"） |

- **三条约束**（〔手机〕§5.3）：

| # | 约束 | 理由 |
|---|---|---|
| 1 | **转交必须是一次工具调用，不许解析自然语言** | 可审计 + 可授权 + 不靠猜。A 被污染后随便说一句不该能触发转交 |
| 2 | **一轮内最多转交一次，禁止回环（A→B→A）** | 否则用户被踢来踢去——与"不留人、不拖时间"直接冲突。B 答不了就说答不了 |
| 3 | **转交的前提是"目标工作区已经存在"** | 否则每遇到一个话题就临时造 agent = 无限增殖，违反"单次不生成、多次才生成" |

- 第 3 条展开（〔手机〕§5.3）：B 已存在 ✅ 转交；B 不存在、这是第一次 ❌ **不转交**，A 自己答完（省一次 2.7–5.1s 冷启动 + 一次交接损耗）；反复出现（第 2~3 次）这时才**提议**建 B —— 频次当闸门。
  > **转交不是"换个更懂的人来答"，是"回到那个已经存在的专门地方去答"。**
- **"B 是什么"不由 A 现编**（〔手机〕§5.4）：A 不知道 B 的真实能力，**它只能编**。**正确做法**：A 只说"该交给谁"；**"谁是什么"由系统查**。**能力目录由系统维护。**
- **tainted 的 A 不许转交**（〔手机〕§5.5）：⇒ **A 处于 tainted 时，`handoff_to` 应被 deny**（或转交过去的内容仍带 taint，B 也走只读档）。

**Case 2：用户跟 A 聊到一半切走**：见 §3.2（决定：A 继续做完，结果搁置，不投递、不触发）。

### 3.6 主作用域的记忆索引 KV（块 10）

- §6.1 选型：**不写 `kv.js`**，用 **`dsh-storage-domain` + `dsh-storage-json`**（schema 校验；读同步；**写持久化成功才返回**；发 `domain/changed`；**对模型不可见**）与 **`dsh-session-projection` + `-cache`**（"**日志永远是权威，崩溃只可能落后，绝不超前**"）。
  - **N6 不变量不是设计出来的，是这个原语的固有性质。** 落地位置：`~/.dsh/storages/<域>.json`。
- §6.2 "KV 精简"与"前缀只追加"是一对天生矛盾 —— 解法是**分两层**：
  - 索引层（常驻上下文，永远精简）：实体/主题 + 一行 + 指针
  - 详情层（不进上下文，按需检索）：事实明细 + 原始会话；工具 `dsh-session-query-sqlite`
  - 每轮只在**尾部追加**"本轮相关的索引条目"（v7 §4.5 已这么写）；**完整 KV 留在 storage domain 里，当工具查，不当 prompt 注入**
- §6.3 键的定义：**键 = 实体 / 主题**（不是会话）。因为要的是"记忆关联"，关联的是**事**。
- §6.4 三个必须防的失败模式（原文表）：

| # | 失败模式 | 防法 |
|---|---|---|
| ① | **编造 → 固化 → 反复引用** | **无出处不写**（N4）。每条必须带 source 指针；无 source 只能进"待确认"，不能进"受信" |
| ② | **KV 与真相冲突**（用户后来改了日期） | 冲突以**事件流为准**（N6，`-projection` 已保证"永不超前"）；每条带指针可回查 |
| ③ | **KV 成为"注入持久化"的落点** | **KV 由 hupo 持有，agent 只能通过工具访问**；写入过 **provenance 校验**。**不能让 agent 直接写文件**——那会绕过全部审计 |

- §6.5 更新节奏：机械（谁何时聊过、标题、时间）**免费**；语义（"报名截止 3/20"）**花钱**（快模型 + **关思考**）；时机 **异步** —— **用户说话→看见第一句这条路上不许有 KV 抽取**。

### 3.7 来源标记（第一类公民）

〔手机〕§九原文要点：
- 调度器**知道每条消息来自谁**——DSH 不需要知道（`session/prompt` 在会话日志里始终是 user message），**在文本里带标记**即可（协议内约定，不依赖 DSH 元数据）。
- **你已经在这么做了**：`timelineContext` / `#withRecap` 就是"把一段带标记的背景块拼在用户原话前"的现成实现。
- **一处标记、四处生效**：

| 用途 | 用来源做什么 |
|---|---|
| 展示 | 客户端显示"这句话来自 B" |
| **权限** | 不同来源 → 不同能力档（taint 棘轮） |
| **记忆** | 进 KV 时带 `source` / `trust`（N4） |
| **审计** | 谁在什么时候说了什么 |

- 来源取值从 v7 的 `owner / product / derived / foreign` 扩展为：**`user` / `dispatcher` / `agent:<scopeId>`**。
- ⚠️ **B → A 的汇报，来源等级是 `derived`（不可信），不是 `owner`。** 理由：B 自己会联网，**B 可能已被它读到的网页内容污染**。⇒ 按现有规则 **A 读到 B 的汇报就该降只读档**。⇒ **A 可以"知道"，但不该因此"获得权限"**：不能因为 B 说了什么就去执行有副作用的动作——那必须等主人的原话（清 taint 只在 host）。

## 5. 调度器的职责

### 5.1 〔手机〕§八：**调度器的三个职责**（原文代码块，逐字）

```
调度器（永续，同时持有 A、B、C… 每条会话）
 ① 对用户的路由
      当前焦点在哪条 → 它的输出投给用户
      其它条的输出 → 照常进时间线，但**不实时提醒**（§7.1）
 ② agent 之间的邮政
      B 干完了 → **调度器收下并落盘** → 按"A 闲时"投给 A
 ③ 归一化
      把 N 条会话的输出合成用户看到的**那一条连续时间线**
      全局 seq 由调度器分配（**不是 DSH 的 session 内 seq**）
```

**② 的两个要点**（〔手机〕§八，原文）：
1. **汇报必须由调度器收下并落盘，不能依赖 DSH 的 in-session notice。** 因为【实测】`dsh-tool-jobs`："**待投递的通知不会在宿主销毁后存活**"，而 B 有 30 分钟 idle TTL。用户的场景恰恰是"用户跑了、B 还在干活" —— **调度器是永续的，它是唯一能保证"这句话不丢"的地方。**
2. **"闲时"有机械判据**：`dsh-tool-jobs` 明确区分 busy / idle（"忙的在下一步收到，空闲的可被一次有界 follow-up turn 唤醒"）。

**③ 的形状你已经有了**：`Conversation.emit()` + 全局 `seq`。要改的只是"来源"——从"唯一那条 session"变成"当前活跃的那条"。**客户端的 `sinceSeq` 续传逻辑一个字都不用改。**

**§8.1 唤醒风暴（要设闸门）**：`dsh-tool-jobs` 专门有 "consecutive wakeups" 配置 ⇒ DSH 作者已预见此风险：B 完成 → 唤醒 A → A 干活产生新 job → 又唤醒 → 成环。⇒ 设闸门：**同一对 agent 的唤醒频率上限** + **汇报可合并投递**（一次投多条摘要，而不是每条唤醒一次）。

### 6.3 为什么改（原文给的理由）

**关于成本模型（第一条）**，原文给的理由（〔手机〕§十三末行）：
> **无价格表、无 userId 维度**，且**总量被 cache read 主导（实测 98.57%–99.75%）** ⇒ 成本与配额一律用 `{userId, uncachedInputTokens + outputTokens}` 计数，**cache read 单列、不进阈值**。

同一条在〔L3〕§15 冲突 2 里被进一步说明为「**这是**我们客户端的限制，不是宿主的限制**」（原文加粗）：
> **v7 §11 写**：`DSH 的 session 事件没有 token 用量 ⇒ 算不出美元 ⇒ 不显示估算美元`。
> **实测**：① `session.event` 侧确实没有；② **但宿主有 `dsh-token-meter`**：`ctx.tokenMeter` 提供 `tokenUsage` / `contextPressure` / `contextBreakdown`，**replay 确定、无模型调用**，且"provider-reported usage is reused for an identical request envelope"。
> **结论**：这是**我们客户端的限制，不是宿主的限制**。
