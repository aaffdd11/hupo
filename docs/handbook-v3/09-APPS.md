**谁该读**：动小程序 / 容器 / 授权之前。

---

## 计划中的节

| 节 | 回答什么 |
|---|---|
| **一、它是什么** | 一格 ＝ 一间工作区 ＝ 一条对话 ＝ 一个制品；**两个原点**（持令牌的 vs 跑第三方代码的）为什么必须分开 |
| **二、沙箱三条铁律** ＋ 判据 | iframe 的 `sandbox` 取值（**绝不能加的那一个**）· 文档 CSP · 禁原生桥（**两端一致**的由来） |
| **三、能力与授权** | 五样能力（存储 / 上网 / 问助手 / 定时 / 拍照）各是什么形状；**声明 ≠ 已给**：打开时一次问完，允许/不给/还没问过三件事分开记 |
| **四、每一格自己的库** | 每 app 一个 SQLite · 执行在壳这一侧的子进程 · 上限与"清空" · 跨库那条路堵死 |
| **五、制品管线** | 从"他说要做"到"桌上有一格"：登记 · 发布 · 装（fork）· 上架 · 发现 · 活地址（**他正在改的那一份**）· 出去的那一份**就是清单声明的那一份** |
| **六、用户端 vs 包** | 用户端**没有"包"**、没有大小上限那一套；上限只在包那一侧 |
| **七、给"做小程序的 agent"的作业指导书** | 从需求到上桌的六步 · 制品标准 · 能力标准 · 交付话术模板 · 自查清单 · 反模式 |
| **八、判据** | 每条能力各自的闸在哪（测试名）＋ 负向对照 |
| **九、明确没做的** | 一条一行（不是"排后"） |

---

## 写这一份时的硬要求

- **"以他盒子里那份为准"**：凡涉及"跑的是哪一份 / 数据在哪"，必须写清是哪一台、哪一层。
- **给 agent 的作业指导书要能直接照抄**（它是发给"做小程序那个 agent"的规矩）。
- **判据带负向对照**（"两端一致"这类断言最容易被自己的闸骗过去）。
