## 二、真争议（六条，不折中，列清楚给主人拍板）

### 争议 1（最重要）：小程序——**这一轮到底做不做？**

| 立场 | 论据 |
|---|---|
| **陆明：做** | "今天从'主人说完'到'他在屏幕上点开'的时间是**无穷大**"。agent 已经能写出来、能说"放在工作区了"，**然后他拿不到**。交付形态只有编译进包的 Flutter 原生页，加一个要重编整个 Web 包。这是唯一把"助手"和"聊天机器人"分开的东西 |
| **沈简：不做** | 判据：数 `data/*.jsonl` 里"做个小工具/页面"类请求，**≤1 次/周不做，≥3 次/周才做**。省下的两期转给容量和首句 |
| **周慎：做最小形态，但三前提 + 门槛** | 三前提缺一不做（独立 origin / 制品搬出站点根 / 发布走特权管线）；门槛**每周 ≥3 次真会打开**才值得做运行时 |

**争议实质**：不是"要不要"，是**需求被压抑了数不出来**。陆明的反驳很硬：今天交付时间是无穷大 ⇒ 用户早就放弃提这类需求 ⇒ **你数不到，不等于没有**。

**我的裁决**：**设一个为期一周的"记录期"**，不动代码，只记一件事——
> 数的是「主人要一个**能操作的东西**」的次数，不是「要 H5」的次数（他不会说要 H5，他会说"整理成一个能筛选的表"）。

一周后 **≥3 条 ⇒ 做最小形态；<3 条 ⇒ 不做**。而且这一周**正好用来做 S0 止损**，所以：
- 陆明不亏：不用等三个前提全完工，一周后就能开工；
- 沈简/周慎不亏：拿到了他们要的门槛，而且这周本来就在修地基；
- 谁也不会"白干两周"。

**选错的代价**：周慎那句最难反驳——"**一个一天挂四次的助理，不会被用第二次**"。所以记录期必须与 S0 并行，不能串行。

### 争议 2：容量对外承诺写几？

| 立场 | 数字 |
|---|---|
| 沈简 | 写死 **3**（条件：砍掉每会话常驻的 `debug:<conv>`） |
| 陆明 | 接受 2–3，但**账算错了**：1 个对话 + 1 个后台重活 = 2 个进程；顺序是先搬重活再谈容量 |
| 周慎 | **"1 个满速 + 1 个可用"** + 准入三闸（会话 ≤2、agent 进程 ≤4、`memory.current/max ≥ 0.75` 即拒） |

**我先核了一件事实，它改变了裁决**：沈简的前提**部分是错的**——
`debug:<conv>` agent **本来就是按需起**：`debug-agent.js:592` 只在 `review()` 时创建，
而 `dispatcher.#watch` 里**规则不触发就不 review**；触发后驻留到 30 分钟空闲回收。
所以"每会话 2 个 agent"是**最坏情况**，不是基线。

修正后的模型：

| 情形 | 内存 | 能否装下（1G，留 25% 余量 → 768MB 可用） |
|---|---|---|
| 1 活跃会话（监控未触发） | 68 + 172 = **240MB** | ✅ 还能再来两个 |
| 1 活跃会话 + 监控刚触发 | 240 + 172~195 = **412–435MB** | ✅ 还能再来一个 |
| 2 活跃会话 + 都触发过监控 | ≈ **890MB** | ⚠ 越界 |
| **1 个会话 + 一次构建** | 68 + 172 + **846** = **1086MB** | ❌ **必然 OOM**（近 7 天实测 4 次） |

⇒ **绑定约束不是会话数，是（a）构建、（b）监控触发频率。**

**我的裁决**：
1. **对外承诺按周慎写**："**1 个满速 + 1 个可用**"——不许过度承诺（他的理由是"越界后的表现是说假话"）。
2. **内部目标按沈简写**：S0 把构建搬走后，稳态是 **3 个活跃会话**；监控频繁触发时降为 2。**三个数字写在同一行并附条件**，不许只写一个。
3. **采纳沈简的一条做法**：`debug:<conv>` 改成 **review 完即杀**（它每次自带 transcript，本来就不需要会话历史）——把"最坏情况驻留 30 分钟"压掉。
4. **准入三闸按周慎**（阈值 `0.75` 而非 `0.9`），且**拒绝不许新建 jsonl**；续做全局上限先按周慎的 **1**，观察一周再议是否升 2。

**选错的代价**：承诺 3 而实际 2 → 第三次有人用时，主人看到的是"正在恢复连接"；承诺 1 而实际 3 → 只是保守，没有代价。

### 争议 3：成本触顶——"降档仍答" 还是 "明说停"？

| 立场 | 结论 |
|---|---|
| 沈简 | **明说停**，且**必须在开口之前停**（`message/end.reason` 不许是 `max-tokens`/`failed`） |
| 陆明 | **降档但仍答 + 明说一行**（"明说停"在用户办事那一刻最糟；"偷偷降"更糟） |
| 周慎 | **三级 75 / 90 / 100**：90% 降档、100% 才停，且必须留一句人话 |

**裁决**：**这不是二选一，周慎的三级同时满足了三个人**——
90% 降档仍答（陆明），100% 停（沈简），全程明说不许静默（周慎）；并把沈简那条"**必须在开口之前停**"升级为不变量
（不许出现半句被截断）。另外三人一致同意：**删掉 `/api/debug/analyze` 的 `force` 参数**（它绕过 60 秒冷却，可无限刷）。

**一条技术前提（实测，必须写进文档）**：DSH 的 session 事件**根本没有 token 用量**（`grep usage|cost` 在 `services/core/src` 是 0 命中）
⇒ 第一版降档判据**只能基于计数**（steps / toolCalls / searches），**不能基于花销**。
所以**不显示估算美元**（沈简说"估算值就是假数，宁可显示—"，成立）。

### 争议 4：KV 建不建表？

| 立场 | 结论 |
|---|---|
| 沈简 | **连表都不建**：`experience` 的消费者是子 agent 体系（本轮不做）、`taxonomy` 是 v1 重资产 ⇒ **没有消费者的表就是负债** |
| 陆明 | 不给出口，但"第三次不用再问哪个客户，靠装配简报就够了"（隐含要表） |
| 周慎 | 第一版不给出口；附加"无采信等级就没有出口" |

**裁决**：**拆开看消费者**——
- `facts`（结论/事实）：消费者**现在就有**（主 agent 装配简报）⇒ 建，但排期在 S4（本来就在后面）；
- `experience` / `taxonomy`：消费者是**还不存在的子 agent 体系** ⇒ 等它落地时再建。

**所以沈简赢在排期，陆明/周慎赢在方向**——而且因为 KV 本来排在 S4，沈简的"不建"和这里的"晚建"**成本相同**。
他的反对在这一条上其实已经被排期满足了。

### 争议 5：工具权限——四档矩阵 还是 两档？

| 立场 | 结论 |
|---|---|
| 沈简 | 只实现**两档**（受信可用 / 受污染只读）；砍四档矩阵、砍 `request_capability`、砍 taint 自动衰减 |

理由（沈简）"再说一句话就是授权，不新增 UI / 状态 / 往返"。这是本轮**最干净的一次"机制被砍"**。

### 争议 6：宽屏收起态——横跨整宽 还是 限宽 760？

| 立场 | 结论 |
|---|---|
| 陆明 | **收起态必须横跨整宽**："否则'贴底的一条'在 1400 宽屏上变成'浮在中间的一条'，那就不是'最底下那个聊天窗口'了"——而主人原话是"在最底下" |
| 我（设计稿）与周慎 | 收起态也限宽 760 居中 |

**裁决**：**外壳横跨、内容限宽**——
收起态的**浮窗外框横跨整宽**（保住"贴底一条"的语义），但抓手 / 标题行 / 输入框的**内容区限宽 760 居中**（保住可读性与手感）。
展开态整体限宽 760 居中不变。

**这不是折中**：它分别满足两个**不同层面**的要求（外壳语义 vs 内容排版），而不是把一个要求砍一半。

另外周慎给的四条硬约束**全部采纳**：
① 正在输出的消息不许被"自动收起"藏起来（只对 `isFinished == false` 生效）；
② 收起不许吞掉未发送的输入（收起前后输入框 byte 级一致）；
③ 收起态必须仍留 `⏱N` 小标（R6 不能被浮窗吃掉）；
④ 拦截层**只在展开时存在**（收起时必须消失，否则小程序按钮点不动）——"这是最容易写错的一处"。

**并采纳沈简的一个减法（做法采纳，数字不采纳）**：他主张"两个相邻 44px 命中区间距只有 4px、会重叠 40px，
所以按'停下'可能发出消息"。**我核了一下，40px 这个数他不成立**：输入条按钮是
`IconButton(visualDensity: VisualDensity.compact, iconSize: 20)`（`chat_screen.dart` 的 `_Composer`），
compact 密度把默认 48 的布局盒压到约 **40px**，与相邻按钮间距 4px ⇒ 把命中区撑到 44 只多出每侧 2px，
**正好相接、没有重叠**。
但**他的方向是对的**：40px 盒 + 4px 间距在 44 目标下**没有任何余量**，稍微改一下图标或密度就会相碰。
所以**采纳"砍掉'停下'按钮、忙/闲共用同一个位置"**（闲=发送、忙=停下）——少一个按钮、零歧义、命中 44 更从容。
