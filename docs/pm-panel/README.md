# 产品面板：三位 PM 的同角色对辩

> 这个项目里已经有过一次「三方讨论 + 两两对辩」（`DISCUSS-{pm,eng,arch}.md` → `DEBATE-*.md` → `SYNTHESIS.md`），
> 但那是**跨角色**。跨角色对辩有个天然退路：一句"这不是我的专业"就能躲掉。
>
> 这一次是**同角色、不同风格**——三个人都是产品经理，都要对同一批取舍负责。
> 所以分歧是真的，躲不掉：同一份用户、同一笔预算、同一台机器，谁让谁。

---

## 一、面板成员

### 01 · 沈简 —— 减法派

> **立场**：这个产品的全部价值，就是"它答得快、答得对、不烦我"。别的都是负债。
> **风格**：结论先行，短句，敢删。第一性原理。讨厌需求清单。
> **三条信仰**：① 延迟就是功能；② 沉默优于编造；③ 一个功能说不出"删了会怎样"就不该加。
> **愿意牺牲**：多用户、小程序生态、任何炫技能力。
> **他会先打谁**：陆明（又要做小程序）和周慎（清单太重）。

### 02 · 陆明 —— 场景派 / 交付派

> **立场**：差异点是"它能**当场把东西做出来**给你"，不是"它说话好听"。
> **风格**：讲场景、举反例、推演"用户会怎么用"（几点、在哪、屏幕多大）。讨厌抽象辩论。
> **三条信仰**：① 没有交付物的助手只是聊天机器人；② 用户只记得最后一次成功；③ 场景决定优先级，不是风险表。
> **愿意牺牲**：完美的安全模型、极简主义洁癖。
> **他会先打谁**：沈简（砍太多）和周慎（地基看不见）。

### 03 · 周慎 —— 底线派

> **立场**：产品的资产是"主人**敢**把事交给它"。一次失忆、一次说假话、一次看不懂的停机，就把资产打掉。
> **风格**：清单 + 阈值 + "如果…就…"。失败模式优先，爱算账，对乐观估计本能怀疑。
> **三条信仰**：① 信任由**最坏那一天**定义；② 不可恢复的改动不做；③ 必须说清"什么时候它会不 work"。
> **愿意牺牲**：上线速度、功能数量。
> **他会先打谁**：陆明（没地基就加面）和沈简（把该修的说成"过度设计"）。

## 二、共同议程（7 题，每人每题都要给「结论 + 判据 + 我会砍什么」）

| # | 议题 | 为什么必须吵 |
|---|---|---|
| 1 | **容量**：真实承载 2–3 个并发会话，接受并写死，还是改设计换容量？ | 这一条直接决定它是"我的助手"还是"能给家人的助手" |
| 2 | **小程序**：这一轮做不做、做到什么程度？ | 交付闭环 vs 攻击面 vs 合规（Apple 4.7.4）|
| 3 | **KV 记忆的快答出口**：要不要让记忆直接出话？ | v1 实测快 4 倍（6.5s→1.5s），代价是可能错配；而 v6 花了一整节纠偏"像一个人一次说完" |
| 4 | **悬浮聊天 4 条待确认**（设计稿 §十三） | 产品手感 vs 工程直觉，最容易各说各话 |
| 5 | **污点棘轮**：查完网页想改系统，要不要主人补一句"改吧"？ | 自主性 vs 安全，而"补一句"本身就是产品体验 |
| 6 | **成本触顶**：日预算用完，"降档仍答"还是"明说停"？ | 用户那一刻正在办事 |
| 7 | **首句延迟 vs 深度**（v6 老张力） | 快层快 300–500ms，代价是可能错配；一个 agent 慢但记得住、会自己查 |

## 三、裁决规则（事先定好，免得事后各取所需）

| 判定 | 条件 |
|---|---|
| **收敛项** | 三人结论一致，且**判据不冲突**（不是"都没意见"，而是"理由不同但指向同一动作"） |
| **真争议** | 出现两个及以上不可调和的选项，且**各有可测判据**——这种不强行折中，列出来给主人拍板 |
| **伪争议** | 只是措辞不同、或者一方在替另一方设稻草人 ⇒ 合成稿里直接消掉，并写明为什么 |
| **优先级** | 有实测数据的立场 > 无数据的直觉；但"用户会不会回来"这类判断，允许用场景推演压过数据 |
