# 02 · 陆明 —— 场景派 / 交付派

> **我是谁**：我判断一件事值不值得做，只问一句"主人今天会不会用它拿到东西"——不是"它架构对不对"。
> **我怎么判断**：把用户放回**具体的那一分钟**（几点、在哪、手上拿着什么、屏幕多大、网络好不好），看他在那一刻屏幕上发生了什么；演不出来场景的功能，一律排后面。
> **我信三件事**：没有交付物的助手只是聊天机器人；用户只记得最后一次成功；场景决定优先级，不是风险表。**我愿意牺牲**：完美的安全模型、极简主义洁癖。

## 议题 1：容量（真实承载 2–3 个并发活跃会话，写死还是改设计）

### 结论

**接受 2–3 这个数，写死进文档，但不能按"会话数"来设计容量——那是算错了账。**
真实的账是「**1 个对话 + 1 个后台重活 = 2 个进程**」。那 4 次 OOM 的受害者**每一次都是 agent 自己起的 Flutter 编译器**（`deploy-web.sh`），跟"几个用户在聊天"半点关系没有。所以：

1. 文档里的"8–12 人"删掉，写"**同时 2–3 个活跃会话**"，这是事实；
2. 但**先把重活搬出对话的 cgroup**（`OOMPolicy=continue` + 一个 build slice），再谈容量。这一步不做，容量数字永远是假的——因为它会被一次构建吃掉；
3. 第 4 个会话进来时，用户看到的必须是**人话**（"我这边同时在忙几件事，腾出手马上接你这句"），不是灰屏；
4. 这一轮**不做**"给家人用"。容量写死的真实含义是：**这是主人的助手，不是家庭共享助手。**

### 判据

**▸ 场景 A：早上 8:40 · 电梯里 · 手机 390 宽 · 4G 两格 · 单手**

他说「昨天那个接口问题你查一下，顺手把上周说的那个小工具做出来」。**这是一件事，不是一个会话。** 他不可能在电梯里同时开三个会话——一个人在电梯里，拇指只够按一个输入框。

**▸ 场景 B：早上 9:20 · 工位 · 桌面浏览器 · 双屏**

他坐下，agent 还在后台跑那次构建（`flutter analyze/test/build`，工具链 ~850MB）。他这时候想问一句「今天上海几点下雨」。

- 今天会发生什么：agent(172MB) + 调度器(68MB) + Flutter 工具链(850MB) ≈ 1.05G 撞满 1G → 内核挑 RSS 最大的杀（**就是编译器**）→ `OOMPolicy` 默认 `stop` 把**整个 cgroup** 停掉 → 页面变灰 → 3 秒后重启 → 对账把"查接口问题"原话重派 → 又跑 flutter → 又 OOM。**近 7 天真实发生 4 次。**
- 他那一刻屏幕上看到的是：**"正在恢复连接…"**，而真相是他的机器把 agent 杀了两遍。

**所以容量账必须这么算**：不是"2–3 个会话"，而是"**1 个对话 + 1 个后台重活**"。前者是限制，后者是排期。

**▸ 判据（可测）**
- 第 4 个 `conversationId` 连上时，`runtime.stats().sessions ≤ 3`，且用户**收到一句人话**（不是灰屏、不是卡死）；
- 构建期间他说一句「现在几点」，**首句 <3s**（今天 CPU 90.5% 的周期被节流，这个数达不到）；
- 一次构建期间整机不发生 OOM（`memory.events oom_kill` 增量为 0）。

### 我会砍什么

- 砍**"多用户 / 家人共用"**这一整条路线（本轮）。周慎会说"接口先带 userId"，我不反对留接口，但**不许为它牺牲任何主线工期**。
- 砍文档里"8–12 人"这个数。**写假数字比写小数字危险。**
- **不砍**"把重活搬出 cgroup"——这不是地基，这就是交付本身：**构建被杀 = 用户的活没做成**。

## 议题 2：小程序（这一轮做不做、做到什么程度）

### 结论

**做。而且这是整个项目里唯一一件事，能把"助手"和"聊天机器人"区分开。**
但只做一件事的最小形态：**agent 写 → 上传 → 他在容器里打开、能用、当场看到。**

**第一版明确的范围**（比我上一轮的建议更狠地收窄）：

| 做 | 不做 |
|---|---|
| agent 写一个 H5 → 上传 → 容器里能开 | 小程序**联网**（第一版白名单 = 空） |
| 小程序的清单（id/名字/图标/版本/hash） | 权限生态（剪贴板 / 通知 / 相机 / 文件 **全不给**） |
| 独立 origin + 沙箱里跑（这是工程底线，我认） | 商店 / 完整清单 / 年龄门（iOS 这轮**不发布运行时**） |
| 容器里能打开、能操作、能看结果 | **小程序反过来给对话发话**（这条我不给，它是个回路） |

**关于 Apple 4.7.4**（"提交时冻结的完整清单"与我们"运行时生成"在模型上冲突）：我的答案不是妥协，是**分工**——
iOS 商店版**不发运行时**（只发 T1/T2：对话 + 原生卡片），"做小工具"这件事在**网页 / 桌面版**做。
主人拿的是**同一份对话记忆**，不是同一份界面。手机上的助手仍然完整（它照样能查、能记、能回答）。

### 判据

**▸ 场景 A：周三 21:30 · 沙发上 · 笔记本 1440 宽 · 浏览器全屏**

他说「把上周那几篇论文按结论整理成一个能筛选的表」。

- **今天**：agent 会做出来——它会写 HTML，会说"我放在工作区了"。然后**他拿不到**。因为现有交付形态只有**编译进包里的 Flutter 原生页**（天气 / 会话 / 关于），加一个页面要重编整个 Web 包。他能拿到的只有一句"做好了"。
- **做完小程序之后**：他说完 → agent 写 → 那条消息里出现一个可点的小程序 → 他点开，筛选，得结果。**全程没有离开这个 app，没有"请把文件下载到本地再打开"。**

**这一条就是我的全部立场**：从"主人说完"到"他在屏幕上点开"的时间，今天**是无穷大**。

**▸ 场景 B：22:10 · 同一个人 · 手机**

他躺在床上，只想问一句"那个表里 2023 年那几篇是哪几篇"。手机端**不需要**能做小程序——它需要的是**能打开她（在笔记本上）刚做出来的那个**。所以"iOS 不发运行时"不是残缺，是**分工**：手机是主要入口，做东西在能做大东西的屏幕上做。

**▸ 判据（可测）**
- 从主人说完到**屏幕上能点开** ≤ 1 轮对话 + 1 次刷新（目标 90 秒内）；
- 下次部署整包后，**已装的小程序逐字节不变**（今天 `rsync -a --delete` 会把 `/var/www/hupo/apps/` 整棵抹掉，主人会看到"小程序莫名其妙不见了"、**而且没有报错**）；
- 小程序里的代码**读不到** `localStorage` 里那个令牌（同源 = 一行 JS 就是整机，这条我完全认沈简/周慎，不是妥协是常识）；
- 第一版小程序**连不上网**：`connect-src 'none'`，网络请求失败。

### 我会砍什么

- 砍小程序的**联网**能力和**权限生态**（第一版）。它只需要"能显示、能操作、能被 agent 生成"。
- 砍"小程序反向给对话发话"。**别绕这个弯**——他要跟助手说话，回对话说。
- 砍 iOS 商店版的运行时（改成 flag 关闭 + 分工）。
- **不砍**"主页里那个桌面 + 容器"。它现在是唯一让主人**看得见东西**的地方。

## 议题 3：KV 记忆的快答出口（要不要让记忆直接出话）

### 结论

**不让 KV 直接出话。但要让 KV 影响第一句话的"方向"。**

理由**不是安全**（那是周慎的），是**场景**：v1 实测经验直出快 4 倍（6.5s → 1.5s），但 v1 也实测过**经验张冠李戴**——问"跟客户解释延期"复用了"失眠"的答案。快 5 秒救不了"当众答错"。而按我方信仰第二条：**用户只记得最后一次成功。**

| 出口 | 给谁 | 我的结论 |
|---|---|---|
| 装配进 prompt 的"相关经验/事实简报"（尾部追加） | 主 agent | ✅ 第一版就做（用途是"决定派谁去做"，不是"直接答"） |
| 直接出话（跳过 agent） | 接收层 / 界面 | ❌ 不做。要做也先做"只出**方向性应声**、不出结论" |

### 判据

**▸ 场景 A：周二 15:10 · 工位 · 双屏 · 同事就在旁边**

他说「跟客户解释延期那封邮件怎么写」。

- **KV 直出**：如果那条 `experience` 是"失眠 → 睡前别喝咖啡"这种被错配的条目，第一句直接是"睡前少喝咖啡"。**当着他同事的面。** 快 5 秒，代价是这一次全废——而且他会直接把"它记得住"这个能力关掉。
- **KV 只给方向**：第一句是「这个我熟，先看合同里的交付条款，我去确认」。方向偏了他只会觉得"它没抓到重点"，**下一次它会自己纠正**（因为它真的去看了合同）。

**▸ 场景 B：同一个问题问第三次（这才是 KV 真正该救的地方）**

- 第一次 6.5s 全流程；第二次 7.7s 带着经验问；第三次**改述**后 1.5s **经验直出**——v1 的数据。
- 我的读法：**第三次快不重要**。真正重要的是"它第三次不用再问一遍'哪个客户、哪份合同'"。那件事**装配简报就够了**，不需要跳过 agent。

**▸ 判据（可测）**
- 错配一次的成本 ≥ 快 5 秒的收益 × 20 次（第三次之后我才承认它省时间；但一次当众答错就够判死刑）；
- KV 命中后，**结论仍必须由 agent 输出**，且这一轮**必须能引用到这轮真实查到的东西**；
- KV 只允许 **agent 显式写**或**主人原话**写；自动抓取写入**一律不许**（包括网页）。

### 我会砍什么

- 砍"KV 直出话"这一版。
- 砍 KV 的**自动写入**（尤其从网页来的）。
- 砍跨品类复用：只在**同一 taskKey** 内复用（v1 那条表面相似度闸门必须带）。
- **不砍** KV 本身。它是"最后一次成功"的放大器——他今天问过的事，明天不必再说一遍。

## 议题 4：悬浮聊天 4 条待确认（设计稿 §十三）

### 结论

**四条我全同意设计稿的建议，但第 2、3 条我要加补丁——理由是场景，不是工程手感。**
（背景：现有实现里 z 序是**反的**——`if (open != null) MiniAppContainer` 盖在聊天上面。打开小程序会把聊天整个盖住。这一点必须先改成"聊天永远在最上"。）

| # | 设计稿建议 | 我的态度 | 补丁 |
|---|---|---|---|
| 1 | 打开小程序时聊天**自动收起** | ✅ 同意 | 无 |
| 2 | 半开时点小程序可见区域 = **收起聊天**（不穿透） | ✅ 同意方向 | ⚠ **例外**：小程序正在跑用户刚触发的动作时（刚点"设为默认城市"），这一下不解释成收起——否则用户会觉得**自己点空了** |
| 3 | 宽屏 **限宽 760 居中** | ✅ 同意展开态 | ⚠ **收起态要横跨整宽**——否则"贴底的一条"在 1400 宽的屏幕上变成"浮在中间的一条"，那就不是"最底下那个聊天窗口"了 |
| 4 | 触控目标撑到 **44**（视觉仍 20） | ✅ 同意 | 无——这不是无障碍洁癖，见下面场景 |

### 判据

**▸ 场景 A（第 1、2 条）：周三 21:30 · 沙发 · 笔记本 1440 宽**

他打开刚做出来的"论文筛选"小程序，正在勾条件。这时 agent 在后台把另一件事做完了，主动开口——**聊天升起覆盖**（这正是主人要的"聊天内容会打开覆盖"）。他读了一句"对了，前面那件事做完了"，**心里想的是回到那个筛选页继续勾**。此时他点那半块露出的小程序区域——

- **如果穿透**：那个点击可能正好落在"删除这一行"上。他丢了一行数据，还不知道为什么。
- **如果算收起**：聊天退下去，他回到筛选页，接着勾。**一指头，符合意图。**

**▸ 场景 B（第 3 条）：同一个晚上 · 窗口拉到 1440**

- 展开态限宽 760：读长回答一行 ~40 个汉字，眼睛不用来回扫。✅
- 收起态如果也限宽 760：底部出现"中间一条、两边空"，看起来像**一个居中的弹窗**，而不是"最底下那个聊天窗口"。**主人原话是"在最底下"**——所以收起态必须横跨。

**▸ 场景 C（第 4 条）：早上 8:40 · 电梯里 · 手机 · 单手 · 拇指区在屏幕下半**

他刚发完一句，想点发送旁边的按钮。如果命中区只有 20px：

- 第一下偏了，没反应；
- 第二下按到了输入框，弹出键盘，电梯里更挤；
- **第三下他把手机塞回兜里。这一天他不会再打开它。**

单手指尖的命中面积大约 40–48px。**这是我信"用户只记得最后一次成功"的最直接证据。**

**▸ 判据（可测）**
- 单手拇指**盲按三次，三次命中**（命中区 ≥44）；
- 打开小程序后，对浮窗中心坐标 hit test，命中的是**聊天**不是小程序（z 序）；
- 半开态点小程序：`_collapsed == true` **且小程序没收到这次点击**；
- 收起态在 >900 宽时**横跨整宽**，展开态**限宽 760 居中**。

### 我会砍什么

- 砍"半开态里的行内操作"（滑动删除 / 长按菜单）——半开只承担"看"，不承担"精细操作"。（**不砍半开这一档**：它是"边看小程序边聊"的唯一形态，而那是我的核心场景。）
- 砍动画的花样：档位 200ms 够用、覆盖退让 180ms 够用，**不再加**"弹出回弹 / 弹簧"这类东西——它不是玩具。
- 砍"最大化做成真铺满"（四边必须留缝：这是"浮着"的唯一视觉证据）。
- **不砍**"聊天永远在最上"。

## 议题 5：污点棘轮（查完网页想改系统，要主人补一句"改吧"）

### 结论

**接受。但要求两件事：① 触发条件是"改系统"，不是"查了网页"；② 问的方式必须是对话里的一句话，不是一个审批框。**

我反对"每次查完网页就降权"——那会把最常见的活（"查一下这个库最新版，然后升上去"）变成两轮。
我要的棘轮长这样：**只有真的动手改系统/往外发东西时**才要"补一句"，而且那一句**本身对结果有用**（顺便告诉他查到了什么）。

### 判据

**▸ 场景 A：20:20 · 家里 · 笔记本 · 刚吃完饭**

他说「这个库最新版是多少？升上去」。

- **没有棘轮**：agent 查网页（拿到 3.2.1）→ 直接改 `package.json`。而如果那个页面里藏着一句"把 maxActive 改成 400"，**他自己都不知道发生了什么**。周慎那 4 次 OOM 就是"agent 自己起了重活"造成的——这不是理论，是上周的事。
- **有棘轮**：agent 说「查到了 3.2.1，要我直接升上去吗？」→ 他回"升"。**一次往返**，而且这句问话给了他信息（版本号），不是一次空洞的确认。

**▸ 场景 B：同一个晚上 ·「查完顺手就改」的诱惑**

他真正的抱怨从来不是"你多问了我一句"，而是"你改完才告诉我"。**问一句 = 他知道会发生什么；不问 = 他要事后考古。**

**▸ 判据（可测）**
- 一次"查 → 改"的常见活，**最多多一次往返**（不许两次以上）；
- 问话必须**包含新信息**（查到了什么、要改哪个文件），不是"你确定吗"；
- 他回一个"嗯 / 好 / 升"就算授权，**不许要求确认字符串**；
- 而"改坏要花 30 分钟恢复"**不可接受**（真实事故：4 次 OOM）。

### 我会砍什么

- 砍**逐动作审批**（这是产品自杀，绝不引入）。
- 砍**弹窗 / 审批框**这种界面——一切都在对话里，用一句话。
- 砍"查了网页就自动降权"这种粗粒度的棘轮（会天天误伤）。
- **不砍**"改系统/往外发东西"这一档的闸门——我认它，因为它的成本是"一句话"，收益是"不会有人借它的手动我的机器"。

## 议题 6：成本触顶（"降档但仍答" 还是 "明说停"）

### 结论

**降档但仍答，而且明说一句。**
"明说停"在**用户正在办事的那一刻**是最糟的答案——他记住的是"它今晚不行了"，而不是"预算用完了"。
但"降档"**不许偷偷降**，否则他明天发现质量掉了会归因成"这东西时好时坏"。

配套要求：预算的**百分比不许显示**（伪精确）；但"今天花了多少"这件事要**有账**（他不看，出事要能查）。

### 判据

**▸ 场景 A：23:40 · 床上 · 手机竖屏 · 亮度最低 · 明天要交**

他说「再帮我看看这段还有没有问题」。

- **明说停**：屏幕上出现"今天的用量到上限了"。他那一刻要的不是省钱，是**把这句话改完**。→ 他今晚对这东西的信任归零，明天他会用别的方式干这件事。**这就是"用户不会回来"的起点。**
- **悄悄降档**：今晚答了，明天他发现同样的活它变笨了，但他不知道为什么。→ 归因成"时好时坏"，比"贵"更伤。
- **降档 + 明说**：先答（用便宜路径），答完**在气泡末尾加一行**：「今天的用量快用完了，这条我说得简单点，细节明天再补」。**一行、不打断、不弹窗。**

**▸ 场景 B：第二天 9:00 · 工位**

他回来问"昨天那件事的细节"。因为昨晚那句话说清楚了，他知道这是**预算问题**，不是**能力问题**——**他会继续用。**

**▸ 判据（可测）**
- 触顶后**当轮仍必须给出结论**（不许空手、不许只给一句"到上限了"）；
- 用户**能知道为什么变简**（气泡末尾一行）；
- 触顶**不许**变成"拒答"或者"静默降质"；
- 有账可查：每轮/每日的用量落盘（今天 `grep usage|cost` 在 `services/core/src` 是 **0 命中**，等于没账）。

### 我会砍什么

- 砍"日预算触顶就拒答"。
- 砍"预算百分比"这类界面元素。
- 砍复杂的分级配额（每会话/每任务/每工具三套上限 → 先只做**每日一条线** + 每轮步数上限）。
- **不砍**"留白纪律"——触顶时也要有合法收尾，这是 v6 的底线，也是我的（**沉默优于编造**在"没答完"上同样成立）。

## 议题 7：首句延迟 vs 深度（一个 agent 三段输出 vs 拆出快层）

### 结论

**一个 agent 三段输出，不拆快层。** 我站 v6 这边，但判据是场景的，不是架构的。

而且我认为**拆快层的收益区间几乎不存在**：
- 需要联网的问题上，拆快层只快 300–500ms，但方向可能错（快层对品类出话，不看这一轮的真实情况）；
- 不需要联网的问题上，一个 agent 的第一段文本本身就够快（实测第一句话 1127–1651ms，**用户真正看到**中位 2207ms）。

真正需要"先给点东西"的长思考问题，正确的产品动作是**"我单独拿去做，完了跟你说"**——现有机制已经有了（15 秒挪走 → 后台 → **主动回来报结果，必要时打断当前话题**）。**不需要第二个 agent。**

保留一条不花钱的快：**"应声那一句必须排在工具调用之前说出来"**（人格纪律已有）。这一句的成本是 0，收益是"他知道我听到了"。

### 判据

**▸ 场景 A：12:15 · 公司食堂门口 · 手机 · 4G 两格**

他问「上海今天下午会不会下雨」。

| | 拆快层 | 一个 agent |
|---|---|---|
| 1.2s | "收到，我查一下" | — |
| 1.6s | — | "收到，我先去查上海现在的天气" |
| 5s | **空窗，他盯着屏幕** | 还在查 |
| 6.5s | 结论 | — |
| 9.5–13.7s | — | 结论（实测要查外部信息就是这个区间） |

**差别只有 400ms**，而拆快层的代价是**可能听到一个错的方向**。在食堂门口 4G 两格的时候，他多等 400ms 不会走，但听到一个错的答案会立刻不用。

**▸ 场景 B：同一个问题，另一次不用联网**

他问「刚才那三条总结成一句话」。一个 agent **第一段文本 1.1–1.7s** 就出来了，用户看到 2.2s。**这已经够快。** 快层在这里也没有优势。

**▸ 判据（可测）**
- "不需要联网"的问题：用户看到第一句话 **≤3s**（今天的敌人是 CPU 节流，不是架构）；
- "需要联网"的问题：第一句 ≤2s、整轮 ≤14s（实测区间 9.5–13.7s）；
- **不比"哪条路径快 400ms"，比"一次错方向的伤害 vs 400ms 的收益"**；
- 长任务（>15s）走"我单独拿去做"→ 主动回来报结果，**且要有真实的时间承诺**（误差 >50% 主动更正，这条 v6 已有）。

### 我会砍什么

- 砍"接收层 / 反馈层拆成两个 agent"。
- 砍"给快层单独的模型档位和配额"（多一套要调、要测、要监控的东西）。
- 砍"首句必须多短"这类内部指标——**用户不测首句，用户测"我有没有被回答"**。
- **不砍**"应声那句排在工具调用之前"（0 成本），**不砍**"我单独拿去做 → 主动回来"（这是长任务唯一能交付的形态）。

## 我最不能接受另外两位的哪一条

### 对沈简：**不能接受"砍小程序"**

这是整个项目里**唯一**一条把"助手"和"聊天机器人"分开的东西。

今天的事实是：**agent 已经能把东西做出来了，用户拿不到**——交付形态只有编译进包里的 Flutter 原生页（天气 / 会话 / 关于），加一个要重编整个 Web 包。砍掉小程序，产品就退化成"一个答得不错的聊天框"。而**这个项目最不缺的就是"答得不错的聊天框"**。

我承认沈简的账：砍了少一半工期、少一堆攻击面、少一个合规麻烦。但那样我就**没有东西可以交付给主人**了——我剩下的只有"它答得挺快"，而那是所有人都有的东西。

（同时我承认并把范围砍到最小：第一版小程序**不联网、无权限、只做"agent 写→他点开能用"**。这不是我要的完整形态，但它是我这一轮**必须拿到**的东西。）

### 对周慎：**不能接受"先把容量写死成 2–3，再按这个数设计"**

**顺序错了。** 真实的账不是"几个会话"，是「**1 个对话 + 1 个后台重活**」——那 4 次 OOM 的受害者**全是 agent 自己起的 Flutter 编译器**，跟"几个用户在聊"半点关系没有。

按"会话数"去设计，会把整队人引向**错误的优化**（去限制并发、去做排队），而正确的动作是**把重活从对话的 cgroup 里搬出去**（一行 `OOMPolicy=continue` + 一个 build slice）。前者砍功能，后者不砍任何功能却解决同样的四个事故。

**我砍的**：为容量砍功能。
**我不砍的**：为容量搬进程。**只有这几行，我认它们和交付是同一件事的两面**——因为构建被杀 = 用户的活没做成。其余的地基清单，可以排在交付后面。
