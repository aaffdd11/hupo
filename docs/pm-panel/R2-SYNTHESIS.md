### 〇.1 事实更正一：`sudo` 到底要不要密码

| 谁 | 说法 | 判定 |
|---|---|---|
| 沈简（一轮） | "三道锁"：不在 docker 组 / **sudo 要密码** / AppArmor 挡无根 userns | ✅ **正确** |
| 周慎（一轮） | "`sudo -n true` 通过（免密）" | ❌ 错 |
| 沈简（二轮） | "周慎实测打掉我'sudo 要密码'这道锁，故 `usermod` 永不" | ⚠️ **前提错了**——他据以改判的事实不成立 |
| 周慎（二轮） | "`sudo -n true` **失败**（`sudo: a password is required`）；我第一轮写免密是错的" | ✅ **正确** |

**合成稿判定**：以周慎二轮的实测为准，**本机 sudo 需要密码**（与架构文档 §3.4 的记录一致）。

**但 A4 的结论不变，而且性质变了**：

> **A4 = c 不是一个选择，是一个约束。** 在拿到 sudo 密码之前，
> `usermod -aG docker`（a）和**装 rootless podman**（b）**两件都做不了**。
> 所以"先做 T0、容器往后放"不是三人妥协出来的顺序，**是当前权限下唯一能走的顺序**。

这条要写进文档，免得将来有人以为"我们选了个保守路线"。

### 〇.2 事实更正二：token 口径（**推翻架构文档里我自己写的一句话**）

我在 `ai-phone-architecture.md` §13 写了"`dsh-token-meter` 存在 ⇒ **v7 §11 的前提是错的，接上即可**"。
**这句是过度声称。** 周慎实测 + 我复核后的完整事实：

| 事实 | 出处 |
|---|---|
| 包存在且已挂 | `~/.dsh/profiles/node_modules/@deepseek-ai/dsh-token-meter`；`dsh-base/cordis.patch.yml:317` 注册 |
| 计数是活的 | **21/21** 会话的 `tokenUsage` 非零（周慎实测） |
| **但被 cache read 主导** | 实测 **98.57%–99.75%**（例：`cacheRead 322,944,768` vs `uncached 332,615`） |
| 没有价格表 | meter 全包无 currency/价格字段；README 自述文本用量是"**近似固定启发式**"（17 处 "heuristic"） |
| 没有 userId 维度 | — |

**入档口径（周慎给的，我采纳）**：

> **token 用量：计数可用、金额算不出。**
> `dsh-token-meter` 已随 bundle 挂着，实测 21/21 会话有非零计数
> （`uncachedInputTokens` / `outputTokens` / `cacheReadTokens`），
> 但**没有价格表**，**没有 userId 维度**，且**总量被 cache read 主导（98.6%–99.8%）**。
> ⇒ v7 §11"不显示估算美元"的**结论保留**，**理由改写**为"没有价格表且总量口径失真"。
> ⇒ 成本与配额一律用 `{userId, uncachedInputTokens + outputTokens}` **计数**，
> **cache read 单列、不进阈值**。

### 〇.3 合成稿新增的一处推论（三位都没说，但它很重要）

"cache read 占 98.6%–99.8%"这个数，除了修正成本口径，还**同时是两件事**：

1. **它是 R2（只追加、不改前缀）有效的硬证据**——比 v7 里那个"18 倍成本差"更直接：
   前缀被近乎 100% 复用。
2. **它是"代理"方案的一个新风险**：`dsh-token-meter` 自己的 README 说
   "provider-reported usage is reused **only for an identical request envelope**"。
   ⇒ 如果总机代理**改动了请求信封**（加一段计费用的 system 块、换 API key、改 header），
   **provider 侧缓存会全废** —— 而 98.6% 的量都在缓存里，代价是数量级的。

⇒ 这条成为 §二 真争议 1（E3）的一个新判据：**代理必须是"透明"的，且要带缓存命中率的回归测试。**

### 真争议 1 · E3：总机代理什么时候上

| 谁 | 立场 | 判据 |
|---|---|---|
| 沈简 | **a**：走代理，但**删掉"算钱"论据** | 密钥不进容器、不进备份包 |
| 周慎 | **a**：走代理是 v1 唯一形态 | 只留"密钥不扩散 + 集中限流/审计"；**"算钱"必须删** |
| 陆明 | **b**：**v1 不加代理**，代理是"开第二席位"的前置 | v1 单容器时，"密钥不扩散"与"限流"**收益为零**（同义反复） |

**新增判据（§〇.3）**：总量 98.6% 是 cache read，而 meter 自述
"provider usage 只在**请求信封一致**时复用"⇒ **代理若改动信封，缓存全废**。

**合成稿给的收敛路径**（如果主人想折中，这是唯一同时成立的）：
> v1 **直连**（省掉一个可能破缓存的中间层），
> 但把"代理"写成**开第二席位的硬前置**，并给代理定一条验收：
> **必须透明 + 带缓存命中率回归测试**。

### 真争议 2 · E4：拒绝阈值与内存数字

| 谁 | 数字 |
|---|---|
| 周慎 | 容器 **1.5G / 1.1G high**、磁盘 **10G**、活跃工作区 **≤2**、平台预留 **800MB**、**0.75 拒绝** |
| 陆明 | **先 LRU 卸载、0.85 才拒**；常驻基线 ≤420MB，**但本机 `dsh web` 单进程实测 719MB RSS ⇒ 此数必须实测校准、只许往上调**；非焦点工作区 **10 分钟**无事件即卸载（不是 30 分钟——现值 30 分钟、1G/172MB ⇒ 3 并发撞顶＝等于没做） |
| 周慎（实测修正） | agent RSS 是 **195MB**（非架构文档引用的 172MB）⇒ `⌊1024/195⌋ = 5`，**实际 3–4** |

**合成稿判定**：**这是数字争议，不是方向争议**——两人都同意"先卸载再拒绝"。
分歧只在阈值（0.75 vs 0.85）和基准数（172 vs 195 vs 719）。
⇒ **给主人的是一句话**：阈值取 **0.75（周慎，更保守）**，但**必须先把全局 LRU 做出来**——
否则 0.75 会在"三个 agent 都在跑"时直接拒绝，用户看到的是"满了"而不是"它在腾地方"。

**并附一条必须做的**：所有内存数字**落地后实测校准**，架构文档里的 172MB 要改成 195MB。

### 真争议 3 · 席位与"开门条件"的措辞

三人都同意"v1 一个席位"，但**"开第二席位"到底是日期还是条件**，措辞不同：

| 谁 | 措辞 |
|---|---|
| 沈简 | 第二个用户 = **搬家演练通过那天** |
| 陆明 | 第 2 步是**开门而非日期**，三条同时满足才开 |
| 周慎 | **九步序列**，最后一步是"干净机 V1–V5 全绿" |

**合成稿判定**：**这是伪争议**——三人说的是同一件事（"条件是硬闸，不是日期"），
只是陆明把它明确说出来了。**采陆明的措辞**：**开门，不是日期。**

## 四、三人各自独立撞到的同三条（**本轮最强信号**）

三条都是"现在不定就会返工"的承重墙。**没有商量，三人分别从不同方向撞上来**：

### ★ X1 · 时间线的排序与时间来源

| 来源 | 说的是什么 |
|---|---|
| 沈简 W2 | 归一化次序规则未定——**两个 agent 同时输出会错位** |
| 陆明 #3 | **一条消息有两个时间**（发生时刻 / 被看到时刻），seq 补发时**显示哪个没定** |
| 周慎 N2 | **全局 seq 在调度器重启后从哪里恢复没写**（现在是会话内内存 `++`，靠落盘事件最大值兜；`conversation.js:3` / `store.js:150`） |

**为什么是承重墙**：这是**唯一一处"底层改来源、客户端一个字都不用改"的改动**——
正因为客户端哑，`seq` 出错**没有任何一层能兜住**。
**必须写死**：`全局 seq = 已落盘事件的最大 seq + 1，只增不减`；
`同一时刻只有一条会话能写可见时间线`；`显示用发生时刻，补发段必须带"你不在时"`。

### ★ X2 · 协议必须带 `scopeId` 与来源

| 来源 | 说的是什么 |
|---|---|
| 陆明 #4 / B13 | **B 汇报的发言人标识与"可点开的指针"没定义** |
| 沈简 W1 | 桌面图标是**第三条入口**，没有触发条件却继承了 N12/N15/N19 |

**为什么是承重墙**：客户端虽然是哑的，但**协议字段一旦上线就改不动**
（旧客户端还在跑）。v1 的界面**可以只显示"它"**，但**字段必须现在就留**。

### ★ X3 · 生命周期：收起来 / 删掉 / 迁移 / 导出

| 来源 | 说的是什么 |
|---|---|
| 陆明 #2 | **"收起来" vs "删掉"没分档**——删除会碰会话记忆与 `/data/hupo/apps` 制品 |
| 沈简 W7 | 删除入口与二次确认缺失（**不可恢复的改动**） |
| 周慎 N9 | 用户自己的文件被 agent 删掉，**有没有回收站** |
| 周慎 N11 | **账号注销与数据导出没有出口** |
| 周慎 N1 / 陆明 | **未读清除规则**未定（"点开就没了" = 事实被静默） |

**为什么是承重墙**：五人从五头撞到同一个洞。**必须与 A1 状态清单同批**——
只写死两档：**默认"收起来"不删数据**；**"删掉"逐条对 A1 清单，且不提供"删会话原文"**；
工作区内删除 **7 天可找回**。
