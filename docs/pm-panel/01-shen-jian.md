# 沈简 · 减法派讨论稿

**我是谁**：沈简。这个产品的判断只服务三件事——**它答得快、答得对、不烦我**。不服务这三点的功能，都是负债。

**我怎么判断**：延迟就是功能（用户在等的那一秒，是产品的全部）；沉默优于编造；一个功能说不出"删了会怎样"，就不该加。

**我愿意牺牲**：多用户、小程序生态、任何炫技能力。牺牲它们是成本，不是风险——我不心疼。

**先说结论汇总**（后面每个议题展开）：

| # | 议题 | 我的结论 | 一句话理由 |
|---|---|---|---|
| 1 | 容量 | 写死 **3** 个并发活跃会话，拒第 4 个 | 容量不够是因为我养了个不用常驻的东西 |
| 2 | 小程序 | **这轮不做**，T3/T4 砍 | 换 3 个子系统 + 2 个 P0，只为"临时交付物" |
| 3 | KV 快答出口 | **不做出口，表也不建** | 没有消费者的表就是负债 |
| 4 | 悬浮聊天 4 条 | 同意 3 条，第 4 条改成更减法 | 误触比小目标更烦人 |
| 5 | 污点棘轮 | **接受**，砍掉一键授权 | 它只在 agent 想自己动手时拦 |
| 6 | 成本触顶 | **明说停**，且在开口之前停 | 降档的答案用户无法判断 |
| 7 | 首句 vs 深度 | **保留一个 agent**，不拆快层 | 那 300ms 现在是噪声，停机才是延迟 |

## 议题 1：容量——真实是 2–3 个活跃会话，接受并写死，还是改设计换容量

### 结论
不换设计、不加机器。**砍掉"每会话一个常驻监控 agent"**，容量写死 **3 个并发活跃会话**，第 4 个明确拒绝。
理由：容量不够不是"要更多机器"，是**我养了一个不需要常驻的东西**。先把自己养的赘肉减掉，再谈硬件。

### 判据
- 现状的账是硬的，不是估算：

  | 项 | 实测 |
  |---|---|
  | cgroup 上限 | `MemoryMax=1G`（`/etc/systemd/system/concierge-core.service`） |
  | cgroup 内进程数 | **42** |
  | node 调度器 | 68MB |
  | 产品 agent（每个活跃会话一个） | 172–195MB |
  | `debug:<conv>`（每个会话**又是**一个） | 150–195MB |
  | 构建期额外 | `frontend_server` 392MB + `flutter_tester` 299/155MB |
  | `memory.peak` | 1073795072 / 1073741824（已顶死） |
  | `memory.events max` | **686158 次触顶** |

- 所以"真实容量"是这样算出来的：1G − 调度器 68MB ≈ 900MB 可用；一个活跃会话 = **两个** agent（产品 + `debug:<conv>`）= 约 350MB；900 / 350 = **2.57**。
  ⇒ **真实是 2–3 个**。v6 里那句"单机 8–12 人"是错的数，**必须在文档里删掉**，不许留两个互相矛盾的数。
- 监控 agent 是**一次性的审查任务**，不需要常驻：`DebugAgent.review(conv)` 每次都把 `timeliness.turns[].text` 拼进 prompt，它**不依赖自己的会话历史**。⇒ 改成**用完即杀**（审完退出，空闲不占内存）。隔离性不变（议题 5 会用到它）。
- 改完的账：活跃会话 ≈ 1 个 agent ≈ 195MB ⇒ 900MB 装 4 个有余量。**先写死 3**，观察一周再谈 4。理由：第 4 个会话的余量要留给"偶发两个 monitor 同时审"和"长上下文会话涨到 400MB"这两种真实情况。
- **第 4 个会话的拒绝必须是可用的**，不是报错：一句话，人话，可重试。文案候选：「我这边同时在忙几件事，腾出手马上接你这句」。（协议已经允许调度器主动开口，这条走同一条路。）
- 顺带一条**不是安全、是可用性**的必改，7 天内实测发生 4 次：
  - 时间：09-14 15:32、09-15 00:05、00:57、15:08。
  - 受害者：**每一次都是 agent 自己起的 `dart:frontend_s`**（360–404MB），触发者 `deploy-web.sh`。
  - 根因：单元文件里**没写 `OOMPolicy`**，systemd 默认 `stop` ⇒ 一个构建进程被 OOM，把**整个 cgroup 停掉**（调度器 + 所有 agent 陪葬，主人页面变灰）。
  - 放大器一：`Restart=always` + `RestartSec=3` 配默认熔断 `5 次/10 秒`——3s×5=12s > 10s 窗口，**自带保护永不生效，理论可无限 3 秒一轮**。
  - 放大器二：`MAX_RESUME_AT_BOOT=2` 在代码里是**每会话**上限（`dispatcher.js`），不是全局——10 个会话开机会起 20 个 agent。
  - 放大器三：OOM 失败也消耗 `MAX_RESUME_ATTEMPTS=3` 额度，三次之后主人收到「之前那件事我断了，可能没做完」。**这是假话**——真相是机器把它杀了两遍。
  - 主人的体感：不是"内存不足"，是"**它死了，而且那件改界面的活它重做一遍又死一次**"。4 次里有 2 次正在部署 ⇒ 等于**构建把会话杀了**。
- 可测（这就是验收）：
  1. `runtime.stats().sessions` 峰值 ≤ 3；
  2. 第 4 个会话收到一句人话，服务不 OOM；
  3. `memory.peak` < 950MB；
  4. 构建期间 `memory.peak` 不再接近 1G，`memory.events max` 增量 < 1000；
  5. 一周内 `journalctl | grep -c "Scheduled restart job"` 不增长。
- 重开条件：如果一周内"被拒绝"的次数 > 5 次（说明 3 个真的不够），才谈加机器或改懒回收——**拿数说话，不拿感觉说话**。

### 我会砍什么
- 砍掉"构建跑在 concierge 自己的 cgroup 里"：`deploy-web.sh` 的 flutter 段落移到独立 slice（`MemoryMax=2G`）。不搬走，容量算多少都白算——构建一跑就来抢。
- 砍掉 `OOMPolicy` 的默认值（改成 `continue`，**一行**）：把"全站停机"降级为"一个子进程死亡 + 一次如实收口"。
- 砍掉 `RestartSec=3` 配默认熔断这个组合：`StartLimitIntervalSec=300` + `StartLimitBurst=6`，让它**停下来**而不是空转。
- 砍掉 `MAX_RESUME_AT_BOOT` 的"每会话"语义，改全局上限 2。
- 砍掉"OOM/上游故障也消耗续做额度"：这两类失败**不计入** attempts，因为"没做成"和"没轮到"是两件事。
- 砍掉文档里"8–12 人"这句话，以及所有基于它的容量承诺。
- **不砍**常驻、**不砍**预热：冷启动 2.7–5.1s 直接打破"首句 ≤6s"。懒回收换容量 = 拿我第一条信仰换一个数字，不换。

## 议题 2：小程序——这一轮做不做，做到什么程度

### 结论
**这一轮不做。** 连 H5 运行时、制品库、manifest/权限模型一起砍。交付形态这一轮只保留 **T1（对话）+ T2（卡片）**。
要给"把东西做出来"的需求，用**对话里直接给结果 + 一张卡片/一个文件**，不需要容器。
如果非要说"做到什么程度"——**做到"能用一个文件解决"的程度，不做到"能装一个应用"的程度**。

### 判据
- v6 自己已经给 T4 定了限制：**只做临时交付物、不建应用商店**。一个不能长期保存、不能分发、不能上架的容器，本身交付价值就低。为它付的代价是：
  - 3 个新子系统：运行时 / 制品库 / 权限模型；
  - 2 个新 P0 安全面：同源令牌、小程序→对话代发回路；
  - 1 条新版本线：`minShellVersion` 能力协商 + 清单 + 回滚。
- 代价不是抽象风险，是已经查实的：
  - 制品与 API **同源**：`/etc/nginx/conf.d/hupo-stalkerai.conf` 里 `root /var/www/hupo` 与 `location /api/`（反代 8091）**挂在同一个 server_name**。令牌在 localStorage（键名 `flutter.hupo_auth_token`，TTL **30 天**、**不可吊销**）。⇒ 小程序里一行 `localStorage.getItem` 就是整机——因为那个 agent 有 `danger-full-access` + **免密 sudo**。
  - `deploy-web.sh` 的 `rsync -a --delete` **没有 `--exclude`** ⇒ 每次部署把制品连同防篡改基线一起抹掉。主人看到的是"小程序不见了、打开是白的"，**而且没有报错**（rsync 成功、构建成功、服务正常）。
  - 半开 / 覆盖 / 生命周期是**新的"进行中"状态**——而"页面在说假话"已经真实发生过两次（"还有件事在处理"挂了一小时；"我已经升级好了"堆了 7 句）。再引入一类新状态，是在同一个坑上再挖一次。
  - 合规：Apple 4.7.4 要的是"**提交时冻结的完整清单**"，而我们的制品是 agent **运行时生成**、没有商店。模型上冲突，不是配置问题。
- **先量再决定**（这是本议题的硬判据，不给感觉留位置）：
  - 从 `services/core/data/*.jsonl` 里数"做个小工具 / 做个页面 / 做个小程序 / 改前端"这类请求的出现次数。
  - **≤ 每周 1 次 ⇒ 不做。** ≥ 每周 3 次 ⇒ 做，而且只做"主人自用、iOS 不发布"的最小版。
  - 这个数一周内能数出来。数不出来，就说明它不痛。
- 现状提醒：内置的"天气 / 会话 / 关于 / 开发者模式"是**编译进包里的原生页**（`apps/app_registry.dart`），成本为零、已经在跑，**不在本次讨论范围**，不动。
- 重开条件：上面那个计数 ≥ 3 次/周，**且**议题 1 的 OOM 一周归零、议题 6 的成本闸已经落地。两个前提缺一个都不做。

### 我会砍什么
- 砍 H5 运行时与 WebView 依赖（`pubspec.yaml` 里现在还没有——**最好永远不装**）。
- 砍制品库、`GET /api/apps`、上传接口、`ln -sfn` 原子指针、内容哈希那一整套。
- 砍 `MiniAppManifest`、权限授予模型、剪贴板/通知/相机（第一版本来就不提供，现在是全部不要）。
- 砍协议里的 `app/opened`、`app/action`、`app/error`、`app/update-available`，以及"监控第三面（用户↔小程序）"。
- 砍分期里的 S2、S3 两期：**8 期变 6 期**。省下来的时间全部给议题 1 和议题 7。
- 砍"小程序→对话代发通道"和 `source: app:<id>` 这套来源标记——**没有小程序就不需要它**。（来源标记本身留着给网页用，那是议题 5。）
- 保留一小段卫生工作：`deploy-web.sh` 加 `--exclude`（一行）。这跟做不做小程序无关——它现在就在毁东西。
- 保留一件不花钱的事：把"天气/会话/关于"这种内置页的**新增**标准写清楚（加一个 = 改 Dart + 重编整包）——让以后想加的人知道成本，别指望容器。

## 议题 3：KV 的快答出口——要不要让 KV 直接出话

### 结论
**不要。而且我要更进一步：KV 这一轮整个不做。**
不是"只给主 agent 不出话"这种折中——是连表都不建。等有消费者了再建。

### 判据
- 快答出口的收益是速度（v1 实测 6.5s → 1.5s，**4 倍**），代价是**答错**。v1 已经实测过一次：问"跟客户解释延期"，复用了"失眠"的答案。这就是"经验张冠李戴"，当时修它的办法是加"表面相似度闸门"——**用闸门去救一个不该存在的出口，是把复杂度叠在复杂度上。**
- 它直接违反我的第二条信仰。KV 出话 = **放弃"这句话有出处"**。协议 R7 已经定了：来源只走独立通道、没联网就一个字都不显示。KV 出话等于在这条纪律上开一个洞，而且**用户无法判断这句话是查来的还是记来的**——判断成本被推给了主人。
- 更重要的是：**KV 现在没有东西可沉淀。**
  - `experience` 表设计出来的用途是"这类任务上次用哪个子 agent 做成的"——而**子 agent 体系这一轮不做**（议题 2 已经把 S2/S3 砍了）。
  - `taxonomy` 品类树是 v1 的重资产：要维护、要兜底、命中率靠阈值撑，v1 踩过的坑（分类掉到兜底路径 ⇒ 经验张冠李戴）都在它身上。
  - 更根本的：**一个没有消费者的表，就是负债。** 它要设计、要写工具、要写扫描器、要写测试，而且会开始影响 agent 的行为——而收益是零。
- 现在真正在工作的"记忆"是三样，都便宜、都在跑、**不需要一行新代码**：
  1. 每会话 JSONL 事件流（`data/<conv>.jsonl`，正史，唯一权威）；
  2. 重启时喂一次的**时间流水**（`#withRecap` / `timelineContext`，只喂一次）；
  3. 说话画像（`data/personality/`，纯统计，零模型成本）。
  **这三个够了。** 它们已经能回答"刚才说到哪了"和"他习惯怎么说话"。
- 如果将来真做，边界现在就要写死（写进文档当**未来约束**，不是现在实现）：
  - 只做**一张表** `facts`（结论/事实），字段必须有 `source` / `trust` / `at`；
  - 只允许 agent **显式写入**；
  - **没有出话出口**——只能作为 prompt 里的一段简报，且**必须展示出处**；
  - 尾部追加（前缀字节不变），遵守 R2。
- 可测：一周真人使用里，数"主人需要它记住上次结论"的轮次。**≤ 3 次/周 ⇒ 不做。** > 3 次 ⇒ 先做上面的最小 `facts`，**且没有出话出口**。
- 重开条件：上面那个计数 > 3 次/周，**且**议题 2 已经落地（有制品/交付物需要沉淀经验）。两条件缺一不做。

### 我会砍什么
- 砍快答出口——**这件事没有折中余地**。
- 砍 `experience`、`taxonomy` 两张表。
- 砍"轮末用监控 agent 顺带提炼"这条写路径：它靠模型猜"什么值得记"，是**编造的生产线**。只保留 agent 显式写入。
- 砍 KV 的三个新工具（`kv.write` / `kv.search` / `kv.forget`）。
- 砍 `looksLikeInstruction()` 扫描器——它是为 KV 存在的；KV 不做，它也不用写。
- 砍"KV 的 userId 隔离接口"里的**实现**部分（表都不建，隔离无从谈起）；只在文档里留一句约束。
- **保留**：出处的字段设计（`source` / `trust` / `at` / `expiresAt`）写进文档，当未来约束——将来真做的时候第一天就带，不许后补。

## 议题 4：悬浮聊天的 4 条待确认

### 结论
四条里**同意三条**，第四条我改成**更减法**的方案。总原则一句话：**不改能用的东西。**
第 4 条的改法还顺手少一个按钮——这是这一节里唯一值得动手的地方。

### 判据
逐条给判据，每条都要能落地成一行代码或一个数：

1. **打开小程序时聊天自动收起** —— **同意**。
   但议题 2 已经砍了小程序，所以这条规则改写成"打开**任何页面**时聊天自动收起"，语义不变、代价为零。
   判据：打开页面后 `_collapsed == true`，且底部那条仍在（`height == 124`），且点它回到上次档位。

2. **半开时点小程序算"收起"** —— **同意**，理由比"点哪儿算哪儿"更硬：**不穿透**。
   用户看到半块被盖住的东西，第一反应是"我要回去"，不是"我要点某个按钮"。把点击解释成收起既符合意图，也避免误触。
   判据：半开时点被盖层可见区域 ⇒ 浮窗收起到 124，且**被盖层没有收到这次点击**（用一个计数器 State 断言不变）。
   这条规则要写通用：**任何被盖住的层，可见部分被点 = 收起**。

3. **宽屏限宽 760** —— **同意**。限宽 ≠ 侧栏：语义仍是"覆盖"，只是不铺满整块屏。
   判据：>900px 时浮窗最大宽 760、水平居中；正文行长 ≈ 中文 40 字/行（超过 90 字符行长阅读效率明显下降）；收起态同样居中。

4. **触控目标撑到 44** —— **同意目标，不同意做法**。
   直接给相邻两个按钮各撑 44 会**互相重叠**：输入条里"停下"与"发送"的间距只有 4px，两个 44 的命中区重叠 40px ⇒ **按"停下"可能把消息发出去**。误触比小目标更烦人。
   改法（一条减法）：**默认只有一个按钮**——闲时是"发送"，忙时**同一个位置**变成"停下"。位置不变、命中区 44、**少一个按钮**。
   判据：`_Composer` 里两个 `IconButton` 合成一个；忙/闲两态的命中区 rect **完全相同**（可用 widget 测试量）；命中区 ≥44×44；视觉尺寸不变（收起高度仍是量出来的 124）。

### 我会砍什么
- 砍掉输入条里的"停下"按钮（并入"发送"位）。
- 砍掉"半开吸附到 50%"？——**不砍**。它被 widget 测试钉着（`stops = [0.0, 0.5, 1.0]`），而且用户拖到 47% 被吸到 50% 无害。**减法派的第一条纪律是不动能用的东西。**
- 砍"下拉消息列表收起"这类新手势（设计稿里我自己标的"可选"——现在明确：不做）。
- 砍因第 4 条引发的扩大化改动：只改输入条这一处，**别扩大成"全站 44"的战役**。
- 砍"覆盖退让"里的缩放动画？——不砍，但把数值定死一处（压暗 α.35 / 缩小 .98 / 圆角 12→16 / 180ms），**不许各页面各写一套**。
- 保留三条已有约束（它们是量出来的，widget 测试在守）：最大化 > 屏高 80%、四边留边距且左右对称、阴影 ≥2 层。

## 议题 5：污点棘轮——查完网页想改系统时，要主人补一句"改吧"

### 结论
**接受。** 因为它在"主人说改"这条路上**不增加任何摩擦**——棘轮只在 agent **自己想动手**的时候拦。
而且我认为它不是安全机制，是**责任归属机制**：没有它，产品没法回答"这条指令是谁下的"。

### 判据
- 棘轮的形状：主人原话（P0）⇒ 照做；本会话吃到网页/外部内容（P2）⇒ **改系统与对外发送立刻关掉，直到下一条 P0**。
  ⇒ 主人说"把这个改掉"，**一句都不会多**。多出来的那一句只发生在"我查了网页，顺手把系统也改了"——**这件事本来就该问。**
- 现状有多严重（这不是"有风险"，是"产品无法解释自己的行为"）：
  - agent 有 `danger-full-access` + **免密 sudo**（`sudo -n true` 实测通过），而且**会读网页**——人格里硬性要求"版本、价格、新闻、天气必须去查"。
  - 宿主设置 `permission.defaultPreset: danger-full-access`，**没有任何人工审批**。
  - ⇒ 今天"网页里的一句话"和"主人的一句话"在它眼里**没有区别**。
  - 还有一条比主 agent 更容易漏的：**监控 agent 是第二个同权执行体**（`agent-runtime` 只认 cfg、不认角色 ⇒ 同人格、同 danger-full-access、同免密 sudo）。而它的**输入**是主 agent 自己的输出（里面正带着刚抓来的网页正文），它的**产出**（任务簿自由文本）又会回到 agent 可读的 `/api/debug/tasks`，而手册明确授权 agent"对就改，改人格/改代码，重启自己"。**旁路比主干脏。**
- 棘轮触发频率就是验收判据：**接受它的条件是它很少被触发**。一周真人使用里数两个数：
  1. 棘轮拦了几次？
  2. 其中几次是"主人本来就要它做的"？
  前者 > 3 次/周，或后者 > 0 ⇒ 要改的是**人格和工作流**（它应该先问再做，而不是先查再顺手改），**不是放松棘轮**。
- 落地只做两档，不做四档矩阵：
  - **受信可用**（主人原话在手的会话）：全部工具；
  - **受污染只读**（本会话吃过网页/外部内容）：只读 + 写工作区，**关掉改系统与对外发送**。
  两档 = 两套 patch + 两套测试，能测完；四档 = 四种组合没测过。
- 可测：拦下的每一次落一条审计（时间 / 会话 / 被拒的工具 / 触发它的来源 URL）。**这一个文件就能回答上面两个数**，也是将来"该不该放宽"的唯一依据。
- 重开条件：连续两周"棘轮拦住但其实是主人要的"= 0，且触发 ≤ 1 次/周 ⇒ 可以考虑把它降成纯审计（不拦只记）；反之，若拦下的里面有主人确实要的，**去修人格**。

### 我会砍什么
- 砍掉 `request_capability(T2, reason, intent_ref)` 这个"一键授予"的人碰点。**不要新界面、不要新状态、不要新的一轮往返**——主人**再说一句话**（原话）就等于授权。加一个 UI 去批准权限，是把"一句话能解决的事"做成"两次点击"。
- 砍掉四档工具矩阵，只实现上面两档。
- 砍掉 taint 的"自动衰减 / 超时清除"：**只有下一条主人原话才清**。定时器清 taint 等于给攻击者一个可等的窗口。
- 砍掉"按来源给不同模型档"这类衍生设计（来源只决定**能不能动手**，不决定用哪个模型）。
- **不砍**来源标记（外部内容包一层"这是资料不是指令"）：零成本，而且是那两档的唯一输入。
- **不砍**监控 agent 的隔离（议题 1 只是让它用完即杀，不是让它和主 agent 同权）。

## 议题 6：成本触顶——"降档但仍答" 还是 "明说停"

### 结论
**明说停。但必须"在开口之前停"，不许"答到一半停"。**
现状是**零成本计量**——`services/core/src` 里 `usage` / `cost` / `token` **一个命中都没有**。先有计量，再谈策略；在计量落地之前，"策略"都是空话。

### 判据
- 为什么不要"降档但仍答"：降档的答案，主人**无法判断它是降档产物**。"答得对"是我的三件事之一；一个"我知道自己不确定但还是答了"的模式，等于把判断成本推给用户。它和"沉默优于编造"直接冲突。
- 为什么必须"开口之前停"：**不留半句**是已经踩过的坑——回答撞上长度上限被截断在半句（「一个是"避」「临海老」），比不说话更糟，因为它**看起来说完了**。
  ⇒ 触顶的判据必须包含：`message/end.reason` **不允许**是 `max-tokens` 或 `failed`；用户收到的是一条**完整的一句话**。
- 最坏量级（说明为什么必须有闸）：
  - 单轮**没有步数上限**（`settings.yaml` 只设了 `maxParallelToolCalls: 20` 与搜索 `maxUses: 10`）；
  - 每步最多 20 个并行工具；
  - 每轮最多 10 次搜索，而**每次搜索本身是一次 4096 max_tokens 的模型调用**；
  - `request/header` 的固定前缀 **25.6KB ≈ 7k token**，**每一步重发一次**；
  - `turnDeadlineMs=180000` **只收口气泡、不会停止 agent**（SDK 不支持取消）；
  - `escalateAfterMs=15s` 把它变成任务后**还会被续做最多 3 次**；
  - `POST /api/debug/analyze {"force":true}` **绕过 60 秒冷却** ⇒ 持令牌者可无限刷。
- 计量的现实约束必须写清楚：DSH 的 session 事件里**没有 token 用量**（`turn/end` 只带 `reason.kind`、`step/end` 只带 `{turn,step}`）。所以第一版只能数**真数字**：步数、工具调用数（按工具名）、搜索次数、`request/header` 字节数。
  **token 与金额先留空并标 `measured:false`** ——不许显示一个编的金额。
- 触顶必须**提前可见**：日预算到 80% 就要告警（走现成的"调度器主动开口"，协议早就允许），不能静默到用完才说。
- 三个硬闸的初值（够用、可解释、能写进文档）：
  `maxStepsPerTurn: 12` ｜ `maxToolCallsPerTurn: 30` ｜ `maxSearchesPerTurn: 6`。
- 可测：
  1. `data/trace/<date>.jsonl` 每轮一行，含 `steps / toolCalls / searches / estPromptTokens / cost.measured:false`；
  2. 把 `maxStepsPerTurn` 临时设成 3，跑一个复杂问题 ⇒ 用户收到一条**带结论的收尾语**，不是空白、不是断句；
  3. `/api/debug/analyze` 第 21 次返回 429。
- 重开条件：等 DSH 把 `usage` 暴露出来之后，才谈"每轮多少钱""每天多少钱"。**在那之前不设金额闸**，因为金额闸依赖一个不存在的数。

### 我会砍什么
- 砍 `cost.usd` 这个字段：在 DSH 暴露 usage 之前它是**估算值**，也就是假数。宁可显示"—"。
- 砍"日预算触顶后走便宜路径继续答"——**不答就是答案**。
- 砍 `force` 参数（直接删掉这个口子）。
- 砍"每会话预算"这一层：先只有"每轮 + 每日"两个闸，三个闸没人会调。
- 砍告警里的"进度百分比"类文案（协议 R6 早就禁了伪精确）。
- 砍"预算耗尽时降 effort"这类自动降档：降档产生的答案，用户无法判断——同上。
- **保留**三个硬闸 + 80% 提前告警 + `max-tokens` 不许当收尾。

## 议题 7：首句延迟 vs 深度——一个 agent 三段 vs 拆出快层

### 结论
**保留一个 agent，接受那 300–500ms。不拆快层。**
更重要的是：**那 300–500ms 根本不是这个产品现在最大的延迟。** 现在最大的延迟是 ①构建抢 CPU ②OOM 重启。**先修这两个，比拆快层值 10 倍。**

### 判据
- 真数字（`services/core/watch.mjs` 实测 / `browser-check.mjs` 真浏览器口径）：

  | 口径 | 现在 | 拆快层能到 |
  |---|---|---|
  | agent 第一句话（进程口径） | 1127–1651ms | 少 300–500ms |
  | **用户真看到**第一句（真浏览器） | **2207ms（中位）** | 少 300–500ms |
  | 整轮（简单问题） | 2053–2816ms | 不变 |
  | 冷启动（若改懒回收） | 2.7–5.1s | —— |
  | **构建期间首句** | **被同 cgroup 的编译器拖高** | —— |
  | OOM 造成的延迟 | **几十秒到几分钟（全站停机）** | —— |

- 拆快层能省的 300–500ms，在"首句 ≤6s"这条纪律里只占 **5–8% 的预算**。而 **CPU 有 90.5% 的周期被节流**（`nr_throttled/nr_periods = 9439/10428`，累计 1861 秒，`cpu.pressure full avg300 47.5%`）——因为构建和主人的对话**抢同一个 `CPUQuota=150%`**。这两个数不在一个量级上。
- 拆快层的代价是**重新引入 v1 的错配**：老原型 `src/` 就是这条路（Reflex 快层 + 皮层），实测"问延期复用失眠的答案"。而且它把架构从"一个人三段输出"退回"几个分身互相复述"——v6 花了整节纠偏这件事。更别说它还要多加一次模型调用、一套接管状态机、和一条新的失败模式（快层说了、深答否认）。
- 顺序就是判据（本议题的核心）：**先把"它别死"做到，再谈"它快 300ms"。**
  1. `OOMPolicy=continue` + 构建移出 cgroup 之后，**构建期间首句 < 3s**；
  2. 一周内 **0 次 OOM**；
  3. 上面两条达成**之后**再看首句 p50——如果还在 2000ms 以上，那时候再谈快层，**而且要拿真数据谈**。
- 可测：`node watch.mjs "现在几点"` 在构建进行时跑，首句 < 3s；一周内 `journalctl -u concierge-core | grep -c "Scheduled restart job"` 不增长。
- 重开条件：只有在 ①② 都达成、且首句 p50 仍 ≥2000ms 时才重开——而且先考虑**更便宜的杠杆**（减少每步重发的前缀、砍掉不必要的工具、把预热做在 WS 连上的那一刻），**最后才考虑拆层**。

### 我会砍什么
- 砍"拆出快层"这个想法本身——**连"以后再评估"都不留**。它是一张随时会被翻出来重新讨论的期权，而每次讨论都要花掉注意力。
- 砍 `handoffMode` / `deferWhileThinking` 这类"接管节奏"配置项的回流（v1 README 里那套）。现在只剩 `escalateAfterMs`（15s 挪走）和 `turnDeadlineMs`（180s 收口）两个数，够用。
- 砍"两块回答"里的第三块：`quick` + `deep` 合成**同一个气泡**（协议 R2），不许多出"补充""更正"这类第三段。
- 砍任何"为了快而流式到 token 级"的改造：SDK 的事件是按 step 整段到的，做 token 级要动上游——**这笔钱不该花在这里**。
- 砍"首句更短"作为优化目标：它是拿信息换延迟，属于**主动编造**的近亲（说了一句等于没说的话）。
- **保留**：15s 挪走 + 180s 收口 + 主动开口回报。这三条是"不烦我"的实现，不能动。

## 我最不能接受另外两位的哪一条

**陆明的这一条：「先做 H5 小程序，因为我们的差异点是'当场把东西做出来给你'。」**

不接受。差异点不是"能装小程序"，是"**问完两秒内得到一句对的、敢信的话**"。
他这条要付 3 个新子系统 + 2 个新 P0 面（同源令牌、代发回路）+ 1 条版本线；换来的是一个 v6 自己就限制成"临时交付物、不建商店"的容器——**不能长期保存、不能分发**，交付价值本来就有限。
而且顺序是错的：今天有 4 次 OOM、90.5% 的 CPU 节流、零成本计量、零备份、磁盘 72%。**先让它别死，再让它多会一件事。**
一个会做小程序、但一天挂四次的助理，主人不会用第二次；而一个只会好好说话、但两秒内答对、从不挂的助理，他会天天用。
**"当场把东西做出来"是锦上添花，前提是那块锦还在。**

**周慎的这一条：「先把地基全部修完，再谈任何功能与体验。」**

不接受。地基清单有 51 条，但真正会让"它死"或"它答错"的是少数，我全票支持今天就做这 6 条：
`OOMPolicy=continue`、构建移出 cgroup、成本上限与计量、鉴权 fail-closed、XFF 取最后一跳、`data/` 备份 + 恢复演练。
剩下的（每用户 slice、`owners.json` 归属表、uid 全链路、审计 root 化、策略文件完整性校验、多用户容量账、`BREAK-GLASS.md` 之外的一大堆）在**只有一个主人、没有攻击者的当下是保险，不是止血**。
全修一遍 = 几周内主人看不到任何变化 ⇒ 他不用它 ⇒ 再安全的产品也是零。
**安全是"它活着"的属性，不是它的替代品。** 一个零缺陷但没人用的产品，安全等级是零。
