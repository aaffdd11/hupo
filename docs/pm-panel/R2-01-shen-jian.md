# 沈简 · 第二轮讨论稿（AI 手机）

> **立场连续性声明**：我的三条信仰一字未改——延迟就是功能；沉默优于编造；一个功能说不出"删了会怎样"就不该加。
> **变了一条**：第一轮我接受"容器是唯一的物理隔离"（虽然没写进稿子，但我默许了 S7 多用户的条件触发）。
> 这一轮我**明确撤回**：容器只解决"用户和用户之间"，解决不了"agent 和宿主之间"。
> 而后者才是我们真正的伤口。所以我要求**先摘 agent 的 sudo，再谈容器**。
> 撤回的理由不是"容器难做"，是**顺序**——一个握着 root 的执行体，放进容器里还是握着 root。

## 二、D1 / D2 单独说

### D1 · 能力契约层：**只做契约，不做服务，今天做**

**结论**：做，但只做**最小的一半**——一张登记表 + 一个 `capability.json` 格式 + 一条规矩：**没写数据形状的，不许登记**。
云端数据服务、第三方接入、带 schema 的完整契约体系：这一轮**不做**。第一个真实条目就是本机已经在用的搜索。

**为什么现在做（而不是"以后再想"）**：
没有 schema，所有"生成物"都是不可验证的自由文本。而"多次需求固化成 APP"这条主线的**承重墙**只有一句话：
**AI 只做组合与渲染，绝不发明接口。** 这句话有一个非常便宜的机械落点：登记表里每一条，都必须有 `input` / `output` 的形状。写不出形状 ⇒ 不许登记 ⇒ 也就不许生成。

**为什么现在不做服务**：一个自己都说不清返回什么的数据服务，是所有负债里最贵的一种——它会长进每一轮 prompt,还会在它变化时静默毁掉所有历史生成物。

**判据（可测，不靠感觉）**：
1. 登记表里**每一条**带 `input` / `output` 形状，**校验不过的进不去**（这是 CI 用例，不是约定）；
2. 第一天只登记**本机已经在用的两三个**（搜索、时间、本机状态）——**不新增任何外部依赖**；
3. 生成物里出现"调用一个没登记的接口" ⇒ **按失败处理**，不是降级；
4. 一周后数登记表条目数。**条目数 = 0 说明这条线是空想，当场停掉**——不心疼。

**我会砍什么**：砍云端数据服务、砍"先接三个数据源"、砍"AI 现场发明接口"、砍一切"以后再补 schema"。代价：生成能力这一轮很弱——**我接受，因为生成的前提是那张表，而不是那个容器。**

### D2 · 没有 API 的世界：**不做，只做一张"它做不了什么"的清单**

**结论**：不做代操作。**闭集声明**，不承诺能力边界以外的事。并且**把"AI 手机"这个名字从文档里去掉**。

**理由（这是这一轮我最想说服两位的一条）**：
选项只有两个，而且已经穷尽——模拟点击（已否：UI 一改就碎、无法审计、延迟高）和声明式代操作（**没有 API 就没有可声明的动作**）。所以真值表是：

| | 做一半 | 不做 |
|---|---|---|
| 用户预期 | "它能替我操作" | "它不会替我操作" |
| 第一次失败 | 不知道走到哪一步、钱扣没扣、要不要重试 | 没有失败 |
| 代价 | **信任** | 少一个能力 |

**做一半比不做差。** 因为主人不会因为"不能替我挂号"减少使用，但会因为"说帮我弄然后卡在验证码那一步"**不再信任任何一句结论**。信任是这个产品唯一的资产，而"答得快、答得对"是它的全部内容——**不是"能做多少事"。**

**它要替代的是什么（这才是我愿意做的部分）**：
主人不需要 AI 操作银行，他需要的是**两秒内知道"这笔理财还有几天到期、要不要动"**。后者能答对，前者不做，产品是完整的；反过来，前者做一半，后者也答不好。

**判据（可测）**：
1. 文档里有一张**"它做不了什么"的清单**（银行/政务/挂号/快递…），且这张清单在**用户第一次问这类事之前**就已经存在于产品里；
2. 撞上清单里的事时，**一句话 + 一个可点的替代动作**（"这件事我替你做不了，点这里打开 App"），**不许出现"我来试试"**；
3. 时间口径：从用户说完到这句拒绝 ≤1.5s——拒绝也要快。

**我会砍什么**：砍挂号/银行/政务/快递全部场景，砍"声明式代操作"的整套设计，砍"AI 手机"这个名字。代价：产品覆盖面**明确变小**。我把这个代价写在桌面上——**用覆盖面换"每一句话都是真的"。**

> **一次说清 D1 与 D2 的关系**：D1 决定**它能生成什么**，D2 决定**它敢承诺什么**。
> 我的顺序与直觉相反但很硬：**先说清不敢做什么（D2），再谈能生成什么（D1）。**
> 边界不清的产品，能力越多越危险。

## 三、议程上没有的问题（我认为这一节最值钱）

### W1 · 桌面图标是**第三条入口**，它没有触发条件，但会继承前两条的全部不变量
**问题**：B6 从未定过。系统转交有 `handoff_to` 当触发，用户切走有焦点当触发；点图标**什么都没有**——它随时可能发生，包括 A 正在输出、B 正在跑、有未读、有挂起气泡时。
**为什么现在不处理会更贵**：第三条入口一旦落地，N15（切换前必须收口）、N19（挂起必有收尾）、N12（界面作用域=root）都要在这里各测一遍。等它和容器、KV 一起出现时再想，就是三个未定义状态互相触发。
**建议塞进**：**B 组**，与 N15/N19 同批验收。判据：A 正在输出时点图标，用户看到的是"上一条被合法收口"而不是两个半句。

### W2 · 归一化的**次序规则**没定：两个 agent 同时输出，谁进时间线
**问题**：调度器分配全局 `seq`（§八），但"先到先得"意味着 B 的一句可能插在 A 的回答中间——用户看到的是"**B 在答 A 的问题**"。这正是我们抓过的"页面在说假话"。
**为什么现在不处理会更贵**：多工作区并行**必然**产生同时输出；而这条 bug 的形态是"看起来对、其实错位"，最难查。
**建议塞进**：**B 组**。规则我建议一条就够：**同一时刻只有一条会话可以写入用户可见时间线**（焦点会话优先；其余排队，等它收口）。判据：并发两个工作区，时间线上**永远看不到两条会话交错**。

### W3 · "第二个用户"是谁——这个答案决定 S7 能不能开工
**问题**：家人自用、和外部付费用户，在合规、隐私政策、发票、责任边界上完全不同。全篇没写。

### 五、我认为"现在不定就会返工"的前 3 条

**1. 时间线的权威源**（周慎 N2 + 我的 W2 + 陆明 B12）——**三个人的三条问题，其实是同一条。**
