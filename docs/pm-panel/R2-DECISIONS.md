具体五条（2026-09-18 主人逐条同意）：

| # | 内容 |

| **P1.2** | **"够"的标准**：只要还有任何一条路径能让助手的写入变成"**下次开机自动读**"的东西，就没摘够。判据可执行：`grep = 0`（含 KV / `AGENTS.md` / persona / settings preset） |
| **P1.3** | **说明书同批改**：`AGENTS.md` 与 `hupo-persona.yml` 里"直接动手、不要问"那两处**必须与能力收回同批改**，否则助手会一直试、一直被拒，体验比现在更差 |
| **P1.4** | **清单本身要护住**（递归坑）：判断"哪些文件不能写"靠一份清单 ⇒ **清单必须系统级只读、助手碰不到**；每次开机核对，对不上就拒绝启动 + 报警 |
| **P1.5** | **回退点**：每次执行前先存"改之前的样子"；**回退由主人一句话完成，不需要助手参与**（出问题时助手本身可能就是出问题的那个） |
| **P1.6** | **提申请的形式**：写成**一个文件**（改了哪几处 / 改成什么 / 为什么）放在**助手自己的工作区**；主人点头后由 host 侧按该文件执行；**每次改动记一笔账**（时间、主人原话、改了什么、回退点在哪） |

### 理由

- **威胁的真实形态不是"它干一次坏事"**（那能收拾），而是"**坏事能不能留下来**"：
  它读到一段看不见的网页内容 → 被诱导写进自己的配置 → **从今往后每轮开机都读那一段** → 而表面上一切正常。
- 这条不只是"顺手修的权限"。**它是其他所有隔离的地基**：只要它还握着改自己的手，
  一人一容器、工作区不串记忆、外部内容一律不可信——**全都白装**，因为它能从那一边把墙拆了。
- **形式与既有决定一致**：`ARCHITECTURE-v7.md` §10.1 已经定了"无审批 UI，就在对话里说一句带新信息的话"。
  B 就是那句话的延伸——把"要不要升级"换成"要不要改我自己"。

## P2 · 执行改动的特权从哪来 —— ✅ 已拍板

### 拍板

**选甲：手动执行。** 主人说"改吧"，助手把改动与命令准备好，**主人自己上机器跑**。

三条一起确认（2026-09-18）：

| # | 内容 |
|---|---|
| **P2.1** | **执行方式 = 甲（手动）**：不需要任何预装的 root 组件、不需要定时任务、不需要 uid 隔离。**今天就能用** |
| **P2.2** | **docker 组永久不碰**：永远不把 `deploy` 加进 docker 组（那等于给一个跑着 AI 的账号**免密 root**，比现在的 sudo 更松）。三位 PM 一致 |
| **P2.3** | **本轮不装 podman**：容器是"开第二个用户"的开门条件，不是第一步 |

### 关键澄清：两种 root 不是一回事（主人提出，采纳）

| | 是什么 | 给不给 |
|---|---|---|
| **宿主上的 docker 访问权** | = **宿主的 root**（能挂载任何目录、起特权容器） | ❌ **永远不给** |
| **容器内部的 root** | = **那个盒子里的 root** | ✅ **应该给**（等容器做出来那天）——不给它就是个残废，装不了包、改不了配置 |

> **这正是容器方案的卖点**：现在不敢给它 root，因为给了就是给整台机器；
> 有了容器，可以**在盒子里给它完整 root**，而外面一点碰不到。

**但有三个前提，缺一条就全白做**（写进将来的容器验收）：

1. **绝不能把宿主 docker 的接口挂进容器** —— 挂了等于把整串钥匙放进一个你打算锁起来的房间
2. **不许 `--privileged`、不许挂宿主 `/` `/etc` `/home/deploy` `~/.ssh` `~/.dsh`**；capabilities 默认全收、按需开
3. **封住通往宿主与云元数据的每一条路**：宿主内网端口（如 8091）+ **`169.254.169.254`**（云凭据，容器逃逸的标准第一步）
4. 补：**系统盘只读、只有数据盘可写** ⇒ 改坏了扔掉重建即可

### 甲 的安全取决于一件事（必须写清）

> **甲 的安全性 = "主人真的看一眼"。**
> 如果养成闭眼跑的习惯，甲就退化成"助手有 root，只是慢一点"。

所以甲的**形态**要设计成"**短到主人愿意看**"：

```
助手产出：一个补丁（diff）—— 改了哪几个文件、从什么改成什么
主人看到：一条命令 + 一个补丁
主人跑：  cd <repo> && git apply <patch> && git commit && sudo systemctl restart concierge-core
回退：    git checkout HEAD~1 && sudo systemctl restart concierge-core
记账：    git log（白拿）
```

- **助手能控制的只有补丁内容** —— 而那正是主人要看的那一眼
- **回退点、审计、谁什么时候改的**：git 天生都有，不用另造
- **零预装**：不需要放脚本、不需要 root 服务、不需要定时任务

### 与 P1 的关系

- P1 要"apply 由主人触发"；**甲是这条最字面的实现**——触发就是主人自己动手
- **不是终点**：将来做完 uid 隔离（助手与调度器不再是同一个用户），可以升级到
  "推分支 → 手机上点合并 → 自动拉取"（乙），或"root 侧助手 + 签名"（丙）
- 甲与乙丙**不冲突**：甲是当前权限下（`sudo` 要密码、无 uid 隔离）唯一能走的形态

### 代价（已认下）

> **每次改助手本身，主人都要上机器跑一条命令。**
> 与"频繁迭代"的节奏有摩擦——所以它**必须**做到"十秒能看完"，否则会被绕过。

### X1 · 时间线的权威源 —— ✅ 已拍板

**背景**：客户端是**哑的**——它只按一个编号排序，不做任何判断。
所以**编号错了，它不会报错，只会静默丢消息**，而且**没有任何一层能兜住**。

**七条定案**（2026-09-18 主人确认）：

| # | 定什么 |
|---|---|
| **X1.1** | 编号由**调度器统一发**（不是各会话自己数自己的） |
| **X1.2** | 全局编号 = **已落盘事件的最大编号 + 1，只增不减** |
| **X1.3** | **先落盘、再推给客户端**；⚠️ **写盘失败必须报出来，不能吞**——现有 `store.append`（`store.js:22-28`）正是静默吞异常，与 v7 §3.5"写失败必须上抛"相反，**必须先修** |
| **X1.4** | 可见时间线上，**同一时刻最多一条"还没说完"的消息**；别的先排队。**但执行照常并行**（排队的是"上屏"，不是"干活"） |
| **X1.5** | 显示用**发生时刻**（不是收到时刻） |
| **X1.6** | 补发段**必须带"你不在的时候"**，且需要一个标记字段（**现在就留**） |
| **X1.7** | 计数器**按可见时间线各数各的**，不是全机器一个（张三的号不影响李四的） |

**为什么这条最容易埋雷**：它的错法是"**服务端日志一切正常，用户屏幕一片空白**"——
正是你们已经踩过的那个形态，也是最难查的一种。

**连带**：X1.4 是 v6 附九"消息不许交叉"的升格版（从"一条消息内"升到"整个可见时间线"）；
**转交场景符合它**——A 转给 B 时 A 那条消息不收口，B 接着往**同一条消息**里写，所以"同时只有一条没收口"依然成立。

### X3 · 收起 / 删掉 / 真删 —— ✅ 已拍板（主人提出"删掉 = 进回收站"，采纳）

```
① 收起来        藏到"已收起"，无期限，一键恢复（我不想看见它，但还要用）
② 删掉          进回收站，默认留 30 天
                · 删前先列清单：会删掉多少轮对话、多少文件、多少制品
                · 回收站里一键恢复；也可以"立刻彻底删"（急着删隐私时用）
③ 到期          真的没了（提前一周告一声）
④ 注销账号      回收站连同一切，立刻彻底删干净（合规要求）
```

**"收起来"和"删掉"的区别只有一条：有没有期限。** 收起 = 长年收纳、不自动清；删掉 = 有后悔期、到期真删。

**三个细节**：回收站 **30 天**（与 v7 的墓碑 + `.trash/` 30 天一致）｜**到期自动真删、提前一周告**｜**删前必须列清单**（用户不知道一个图标背后有多少东西；不列，"回收站"只是心理安慰）。

> **主人的这一改比 PM 的结论好**：三位 PM 原本主张"不提供删会话原文"，主人改成"删掉就是进回收站"——
> 一个动作同时满足四件事：可见即可恢复（周慎"不可恢复的改动不做"）、隐私能删（回收站里立刻彻底删）、

| 项 | 内容 |

## P5 · 不做代执行 —— ✅ 已拍板

**只做"准备到最后一键"，不做模拟点击。**

```
用户：帮我把这个月的报销提交了
❌ 助手：好的，我打开报销系统、填表、提交     ← 做不到，也不该假装能做
✅ 助手：报销单我填好了，3 笔、合计 842 元。
        登录和提交这两下得你来——链接在这，点开就是填好的表。（30 秒）
```

**代价（已认下）**：**"AI 手机"在真实生活里只覆盖"愿意开放接口的那一小块"。**
银行、政务、挂号、快递这些永远不会给接口 ⇒ **这个边界必须明确告诉用户，不能装作能做**（"沉默优于编造"）。

**用词警告（沈简提的）**：**别叫"声明式代操作"——名字会自己长回自动化。** 正名用"**准备到最后一键**"这类说法。

## D7 · 展示"在做什么"（过程可见性）—— ✅ 已拍板

**选 B：分层。**（主人 2026-09-18 拍板）

### 为什么这条一次能带走 22 条 UX 问题

| 根因 | 为什么它解决 |
|---|---|
| **R1**（13 条：等待期是空的） | 等待期有东西看了。**而且更好的是：它让 R1 的应声从"固定话术"变成"真实动作"**——不是"收到"，是"**我去查一下上海现在的天气**" |
| **R3**（9 条：系统什么都不说） | "看得见它在干什么"本身就是"系统在说话" |

### 关键区分：**"在做什么" 和 "在想什么" 是两件事**

| | **a. 动作**（在做什么） | **b. 推理原文**（在想什么） |
|---|---|---|
| 例子 | "在查上海天气" → "在算这个月的账" → "在整理成表" | 模型的完整思维链 |
| 长度 | 一句话 | 几百到几千字，而且乱 |
| 给用户 | ✅ **有用** | ⚠️ 大部分是噪音 |
| 风险 | 几乎没有 | ⚠️ **有**：可能含用户隐私、**系统提示词片段**、以及对用户的判断 |

### 四档设计

| 档 | 用户看到 | 谁能开 |
|---|---|---|
| **安静** | 只有结论 + 一个"在处理"标记 | 任何人（04 通勤要的：40 秒只要结果） |
| **在做什么** ✅ **默认** | 一句话动作摘要，**逐个替换**："在查天气" → "在算账" → "整理成表" | 任何人 |
| **步骤流水** | 工具名 / 目标 / 耗时 / 成败（**一键展开**） | 任何人（02 技术要的"我能验证"） |
| **推理原文** | 模型在想什么 | ⚠️ **只有主人**（默认关）——见下面的安全边界 |

**"步骤流水"不是默认，但必须一键可达**：02 的核心诉求是"**我要能验证你不是在编**"，而展示过程正好是验证手段。

### 五条规则

| # | 规则 |
|---|---|
| **D7.1** | **默认档的文案必须是人话**：`web_search` → "在查资料"；phase 内部名一律不露。**并进 R4 那张禁用词扫描表** |
| **D7.2** | **不承诺时间**（v3 已定"只说在做什么、不承诺时间"）。展示动作有副作用：**有了预期却没兑现，用户会更焦虑**（"你说在查天气，怎么 8 秒了还没好"） |
| **D7.3** | **展示过程不能替代速度**。04 的容忍线还在：打开到能打字 **3s** / 首字 **6s** / 首字到可用 **8s**。它只是**让等待可忍受** |
| **D7.4** | **推理原文只给主人**（默认关）。理由：它可能含**系统提示词的片段**（那是产品的核心资产）、其他数据、以及模型对用户的判断 |

## UX · 10 个不同用户的体验走查 —— ⏳ 进行中

### 为什么它要在工程师**之前**

> 如果走查发现"用户根本不会去点桌面上那个图标"，工程做得再好也白做。

读设计 → 写下"我第一天怎么用、第一周怎么用、我卡在哪、我会不会回来"。

每人要交：

| # | 交给什么 |
|---|---|
| 1 | **他是谁**（一段话，含技术熟练度、用手机的习惯、需求类型） |
| 2 | **第一天**：打开 App 后前 5 分钟发生什么（逐步剧本） |
| 3 | **第一次卡住**在哪（具体到哪一屏、哪一句话） |
| 4 | **第一周**：还在用吗？为什么？有没有主动去点桌面上生成的东西 |
| 5 | **他有没有发现"工作区"这个概念** |
| 6 | **他发现的 UX 问题**（一行一条） |

### 预判会被撞到的（让他们去验，不是给答案）

- **空状态**：新用户第一分钟面对的是空聊天框 + 空桌面
- **"我该说什么"**：没有示例、没有提示，用户会盯着输入框
- **工作区是怎么出现的**：用户不会知道"它给我建了个工作区"
- **第一次失败就走了**：第一件想问的事答不出来（没有接口）时的留存

- **浮窗的手势**：可拖可收，新用户会不会不知道怎么用

- "**密码**"：微信/支付宝时代**已经学过** ✅
- "**开门的话**"：**新造的说法，要学** ❌

### 真 bug（四人一致挖到底，这条比措辞值钱）

代言人的红线是"**不许把进门只做成打字**"，但三个人都回答"06 第一次要靠别人帮"——
代言人明确不接受："**一条要靠别人站旁边才能过的门，不是门，是门票。**"

周慎把它挖到底了：

> **令牌 30 天硬到期、断网即登出** ⇒ 06 **每 30 天要打一次电话**。

| 真 bug | 出处 |
|---|---|
| **B1 断网即登出** | `websocket_transport.dart:112-115` 的 catch 把任何网络失败当未登录，清令牌并落盘 |
| **令牌 30 天硬到期、无续期** | `auth.js:110/139` ⇒ **第 31 天全员回登录页** |
| **忘密码零恢复路径** | 只有机器上 `auth-cli.mjs` 一条命令，而这一屏没写 |
| **`needsSetup` 客户端零引用** | 服务端说"还没设密码"，客户端不知道，怎么输都不对 |

⇒ **"第一次要人帮"可以接受**（68 岁老人的手机本来就是子女装的，跟 03 让儿子帮装是同一件事）。
**不可接受的是"每 30 天要人帮一次"。把"只出现一次"做成真的只出现一次——这才是那条红线的解法。**

### 定稿（选项丙）

```
        助手
   你说的事它真会去做，不只是陪聊。
   所以这道门只有你能开。
   [ 密码 ]
     装机器时给你的那一串
   [ 打开 ]
```

**同批必须带三件机制**（否则这屏还会出现第二次）：

1. **修 B1**：连不上服务器**不清令牌**；这屏上明说"连不上，你还登着，网回来自己进"
2. **令牌到期续期**（或延长成"设备记住就不再问"）
3. **忘密码的恢复写在这一屏**（机器上一条命令重设）

**另三件顺带要做的**：

- **错误文案**：现在连不上时给用户看的是 `ClientException with SocketException: …`（洋文报错）
- **锁 15 分钟的文案要给剩余时间**（现在只说"试得太频繁了"）
- **`needsSetup` 用上**（服务端说"还没设密码"时，别让用户在那儿瞎试）

- **关于页**（周慎）
- **第一次真要动手的那一刻**（沈简）——也就是 **P1 的"申请"那一刻**：它第一次要动真东西时，明说自己在动什么

## D4 · 平板是不是主目标设备 —— ✅ 已拍板（选丙 + 主人补的一句）

### ⭐ 主人补的一句（这条定义了本题的答案）

| **主开发设备** | **每天用它、验收看它、第一印象来自它** ⇒ **平板** |

⇒ **实际含义：平板的宽屏不是"第 1 批顺带做"，而是第 1 批的首要验收场景。**
理由（陆明的原话）："**他每天亲眼看的坏东西，会绑住他后面两周的排期**。"

### 五条共识（四人一致）

| # | 定什么 |
|---|---|
| **D4.1** | **手机是主目标设备，平板是主开发设备**（见上） |
| **D4.2** | **宽屏不能只是"排后"**——现在的形状在平板上**是坏的，不是"学过的"** |
| **D4.3** | **浮窗高度改绝对档位 + 转屏重置到最近档** |
| **D4.4** | **自动拉满必须收敛**（判据见下） |
| **D4.5** | **内容列限宽 + 居中** |

### 周慎把两件事判成 **bug**（不管选哪个都成立，进第 1 批）

**① 转屏是 bug，不是"没做"**

> 判据：**没有设计意图支持"换个姿势重新决定占我多少桌面"**，而两个已有契约
> （`_showOlder()` 注释"读历史不该变追历史"、P3 那条"状态不可丢"）都要求保住阅读位。
> **验收**：满档时记录视口顶那条，转屏后仍在同一屏，**20 次全过，位移 ≤50px**。

**② 自动拉满是 bug**

> 判据：**一次"我什么也没做"的消息到达，能否在我不操作时把浮窗从收起/半开变满**——能，就是 bug。

## P-e ★ transport 生命周期（批 0-a 的核心）

**今天的事实**（评审挖出来的）：

```
main.dart:114        只造一个 transport
  ├── :116  给主 controller
  └── :195  给 ChatScreen → chat_screen.dart:223 MiniAppEnv
              → app_registry.dart:34 → conversation_list_screen.dart:81
                            ↑ 同一个实例（_events 是 broadcast，:207）

用户退出那个会话：
  conversation_list_screen.dart:88  controller.dispose()
    → chat_controller.dart:442      _transport.dispose()
      → websocket_transport.dart:306-308   关掉 _events / _devSteps / _agentSnaps
        → _disposed = true ⇒ _open():155 永不重连
```

⇒ **进「会话」应用、退出来，主屏从此一条消息都收不到，而且不自恢复。**

| 选项 | 做法 | 代价 |
|---|---|---|
| **甲** ✅ | **拆两层**：`Connection`（重连 / 令牌 / 版本 / 唯一的 WS）由**顶层持有**；`Session`（`conversationId` / `sinceSeq` / `lastSeq`）**每会话一个**。`Session.dispose()` **只解除自己那一路订阅**，**碰不到 `Connection`** | 要动 `transport.dart`（89 行接口）+ `mock_transport.dart`（423 行）+ 全部调用点；但**这是唯一能同时解决 §1.4 欠账 2 与 3 的方案** |
| **乙** | 保持单例，**`dispose` 不再关 `_events`**，改为暴露"按会话取消订阅" | 改动小，但**单例里仍存着会话级字段**（`_conversationId` / `_sinceSeq`）⇒ **多作用域一上来必炸**（那是欠账 2） |
| **丙** | **每会话一个完整 transport**（不复用连接） | 连接数 = 会话数，**和"一条统一时间线"直接冲突**；手机网络下必被系统掐 |

**推荐：甲。** 理由：**一个 WS 连接是物理约束**（不能每会话一条），**而会话级状态必须分离**——
甲正好是这两句话的直译。而且**它同时是批 0-a"多作用域客户端怎么接"的答案**。

## P-f ★ 一轮的稳定 id（`dispatcher` 的 `turns` 键）

| **甲** ✅ | **"不占号" = "不上时间线"**：`client/reload` 是**控制帧**、本地应声是 **UI 状态**，二者**在进入 `timeline` 之前就被消费掉**；**`marker` 是持久事件（取号、落盘、有位置）** | **零**：`ServerEvent.seq` 保持 `required int`；**不碰基类**；`test/unit/timeline_test.dart:128`（"缺 seq 被拒"）**继续绿** |
| **乙** | `seq` 改可空 + 客户端排序加兜底键 | ⚠️ 要动基类 + **破一条硬闸测试**；而且**兜底键不能顺手用 `at`**（本地发言是客户端钟、服务端事件是服务端钟，**混钟当排序键会乱**，现网是刻意避免混钟的） |
| **丙** | 保留 `emitTransient` 发号，把 N22 的措辞改成"持久事件无空洞" | 承认磁盘有空洞，**但"只增不减"就失去了可校验性**（无法用"最大号 + 1"判重） |

**推荐：甲。** 理由：它**让"不占号"和"占位置"不再打架**，而且**不动已经稳定的基类与硬闸**。

## P-h `catchUp`：线上字段，还是客户端自己算

**背景**：客户端**已经有** `at >= _serverNowAtConnect` 划线（`chat_controller.dart:298-300`）。
⚠️ 而且 **`main.dart:79` 的 `connect()` 默认 `resumeFrom = 0`** ⇒ **首次打开也走 replay**，
服务端若无条件标 `catchUp`，会**把全量历史标成"断线补发"**。

| 选项 | 做法 | 代价 |
|---|---|---|
| **甲** ✅ | **线上字段**；`server.js:110-119` 在**补发唯一出口 `:119`** 包一层；⚠️ **不许 `Object.assign(事件, {catchUp})`**（事件对象来自 `conv.log`，**会被写坏**），必须浅拷贝；**服务端只在 `sinceSeq > 0` 时标 `true`** | 小；且**首次打开不再被误标** |
| **乙** | **客户端推导**（用已有的划线），零协议字段 | 免费，但**混钟**（客户端钟 vs 服务端钟） |
| **丙** | 不加字段、不推导：进入时**插一条 `timeline/marker`** 表达 | 依赖 P-3 定稿（marker 是持久事件）；**多一条历史** |

**推荐：甲。** 理由：**"是不是补发"只有服务端知道**（它知道客户端报的 `sinceSeq`）；
客户端推导要在混钟上做判断，那是已知会乱的。

## P-k 上抛之后的进程级策略

**背景**：`store.append` 上抛之后，**`emit` 有 18 个调用点、无一处 `try`**
（dispatcher 12 / conversation 5 / server 1）；最狠的路径是 `agent-runtime.js:300` ← `stdout.on('data'):117`
与 `dispatcher:603/610` 的 `setTimeout`——**在 Node 里都是未捕获异常**（全库无 `uncaughtException`）
⇒ **盘满 → 退出 → 重启 → 再盘满**。

| 选项 | 做法 | 代价 |
|---|---|---|
| **甲** ✅ | **`emit` 统一包一层**（不再逐处 try）+ 进程级 `uncaughtException` / `unhandledRejection`：**用 `emitTransient` 发一条人话 notice**（它不落盘 ⇒ **盘满也能发出去**），然后**有界退出 + 退避重启** | 小；**判据要加一条"调用点不需要自己 try"** |
| **乙** | 只 `emit` 抛，靠调用方自己处理 | ❌ **18 处里漏一处就回到原点** |
| **丙** | `emit` 抛 + **不退出**：捕获后进内存队列，盘恢复再补写 | ⚠️ **它把"丢了"伪装成"稍后写"**——进程一崩，队列里的**永久没了**；而且掩盖了盘满这个事实 |

**推荐：甲。** 理由：**盘满是运维事实，必须让人知道**；丙把故障藏起来，**正是 09 最恨的那种"看着像成功了"**。
