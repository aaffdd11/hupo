# 03 · 周慎 —— 底线派

> **我是谁**：我判断一切取舍只用一把尺子 —— 主人**敢不敢**把事交给它。
> **我怎么判断**：先列失败模式，再给阈值，最后算恢复时间；算不出来的，我就说不做。
> **我认的账**：信任不是由"最好那天"攒的，是由"最坏那天"能不能恢复决定的。

## 议题 1：容量 —— 真实承诺是「1 个满速 + 1 个可用」，不是 2–3，更不是 8–12

### 结论

**接受物理事实并写死，不改设计换容量。** 对外承诺写成 **「同时 1 个满速、最多 2 个可用」，超过就明确拒绝**。
`ARCHITECTURE-v6.md` 里"单机 8–12 人"这句话**当场删掉**，并在同一处写清它错在哪。
改设计换容量（懒回收 / 每会话一个 slice / 多机）不在这一轮 —— 它是"第 3 个人真要同时用"的条件触发项。

### 判据

先把账摊开（MB，标了来源）：

| 组成 | 来源 | 占用 |
|---|---|---|
| node 调度器 | 实测 | 68 |
| 产品 agent（1 个活跃会话） | 实测 | 172 |
| `debug:<会话>` 监控 agent（同会话，规则触发时起） | 推定（同 cfg、同进程形态） | 172–195 |
| **1 个活跃会话小计** | | **344–367** |
| Flutter 工具链（`frontend_server` 392 + `flutter_tester` 299 + 155） | **实测** | **846** |
| cgroup 上限 | **实测** `memory.max = 1073741824` | 1024 |

- **1 个活跃会话 + 一次客户端构建 = 68 + 172 + 846 = 1086MB > 1024MB ⇒ 必然 OOM。**
  这不是推演：**近 7 天 OOM 4 次**（09-14 15:32、09-15 00:05 / 00:57 / 15:08，实测），
  受害者**每一次都是 agent 自己起的 `dart:frontend_s`**。
- **2 个活跃会话（各带监控 agent）= 68 + 2×344 ≈ 756–802MB ⇒ 可用，余量 220–270MB。**
- **3 个活跃会话 = 1100–1169MB ⇒ 已经越界**，不用等构建。所以"2–3"这个区间的上界是假的，
  真正能给的是 **2**。
- 但余量只有 ~25%，而**瞬时峰值**（起 agent 的握手、`memory.peak` 实测已经打到 `1073795072`、
  触顶 `memory.events max` 累计 **686158 次**）会把它吃掉 ⇒ 所以对外的话应该再收一格：
  **"1 个满速 + 1 个可用"**。
- **准入三道闸（都写进 `config.js`）**：
  1. 活跃会话数 **≤ 2**；
  2. agent 进程数 **≤ 4**（2 会话 × 产品 + 监控）；
  3. `memory.current / memory.max ≥ 0.75` ⇒ **立即拒绝新会话**。
     阈值为什么是 0.75 而不是 0.9：OOM 发生在 1.0，而余下的 25% 要留给监控 agent 起进程与握手峰值。
- **拒绝必须是"人话"**：客户端在 3s 内显示一句固定话术（"我这边同时在忙几件事，腾出手马上接你这句"），
  并且**不许创建新的 jsonl 文件**（被拒了还留下一个空会话，等于把"拒绝"写成"开始"）。
- **什么时候它会不 work（我必须能说清）**：主人一边让 agent 改客户端（跑构建）、一边开着两个会话说话时，
  **第 3 个请求会被拒**。这是设计，不是故障 —— 但必须让用户看得见这句话，而不是变慢。
- 顺带一条硬闸：**预热要关**。现在 WS 一连上就 `warm()` 预起 agent（`server.js` → `dispatcher.warm`），
  等于"打开页面就吃 172–195MB"。在 1G 里这是负资产 —— 用**冷启动 2.7–5.1s（实测）**换内存，账是划算的。

### 我会砍什么

1. **砍掉"给家人的助手"这个容量承诺**（陆明那条）。加一个人不是加一份配额，是加一次 OOM 概率。
2. **砍掉预热**（上面那条）。
3. **砍掉 `MAX_RESUME_AT_BOOT` 的"每会话 2 件"**（实测 `dispatcher.js:281` 是**每会话**上限，不是全局）——
   它现在等于"10 个会话有未完成任务就起 20 个 agent"，在 1G 里是自杀。改成**全局 ≤1**。
4. **砍掉 `ARCHITECTURE-v6.md` 的 8–12 人**这句话本身。文档里互相矛盾的数字比没有数字更危险。

## 议题 2：小程序 —— 这一轮做「能看」，不做「能管理」；三个前提缺一不做

### 结论

**做，但只做最小形态**：一次性的 H5 页面（v6 的 T3 档），**能打开、能看、能关**。
**不做** T4 小应用平台：不做制品库、不做上传接口、不做版本管理、不做权限授予模型、不做离线、不做 iOS 发布。

**三个前提，缺任何一个就整条不做**（不是"先做后补"）：
1. 制品有**独立 origin**（与 API **绝不**同源）；
2. 制品目录**搬出 `/var/www/hupo`**（或至少 `--exclude`）；
3. 发布走**特权管线**，不是 agent 直接写站点根。

### 判据

- **前提 2 的证据（实测）**：`scripts/deploy-web.sh` 里是
  `sudo rsync -a --delete "$APP/build/web/" /var/www/hupo/`，**没有 `--exclude`**。
  制品如果落在 `apps/` 下，**下一次常规部署就把它整棵删掉 —— 而且不报错**
  （rsync 成功、构建成功、服务正常）。主人看到的只是"小程序不见了"。
  验收判据：跑一次 `deploy-web.sh`，制品目录 `sha256sum` **逐字节不变**。
- **前提 1 的证据（实测）**：`hupo-stalkerai.conf` 里 `root /var/www/hupo` 与 `location /api/`
  挂在**同一个 server_name** 下 ⇒ 小程序的一行 JS
  `localStorage.getItem('flutter.hupo_auth_token')` 就能拿到令牌；
  而令牌 TTL **30 天**、**无吊销机制**（实测），链路尽头是 `danger-full-access` + **免密 sudo** 的 agent。
  验收判据：在小程序里读 `localStorage`、`fetch('/api/...')`、`fetch('http://127.0.0.1:8091/...')`
  **三个都拿不到东西**，且这条用例进 CI。
- **前提 3 的证据（实测）**：nginx 把所有外部请求的源地址都变成 `127.0.0.1`
  （`ARCHITECTURE-v6.md` 附十明确写过"这个捷径永远不能加"）⇒ **用"是不是本机 IP"判写权当场失效**。
  所以上传只能走 Unix socket 或只监听 127.0.0.1 带独立密钥的端口，**绝不挂公网 `/api/` 下**。
- **合规（推定，二手来源待复核）**：Apple 4.7.4 要的是"**提交时冻结的完整内容清单**"，
  而我们的小程序是 **agent 运行时生成、没有商店** ⇒ 模型上冲突。所以：
  **iOS 发行版不发布小程序运行时**，只发固定内置应用；小程序在主人自用范围里长。
- **值得做的门槛（自用实测）**：只有"主人**每周 ≥3 次**要打开一个 agent 生成的页面"才值得做这一轮。
  在拿到这个数之前，先做前提 1/2，不做运行时。**如果一周下来一次都没打开，那就是不用做。**
- **时间承诺**：前提 1+2 是**小时级**（一张证书、一个 server 块、搬一次目录、加一个 `--exclude`）；
  运行时是**天级**。所以顺序不冲突：先把便宜的做掉。

### 我会砍什么

1. **砍制品库 / 上传接口 / 版本与回滚 / 权限模型**（第二版再说）。
2. **砍"小程序能把话送进对话"（`say` 能力）** —— 那是一条提权回路（agent 写的文字冒充主人的话），
   收益（小程序里喊助手）远小于风险。
3. **砍 iOS 上的运行时**（合规 + 攻击面，两笔账一起省）。
4. **砍离线、砍崩溃隔离矩阵、砍动效包装** —— 这些是"平台化"的配套，不是 T3 的配套。
5. **砍"制品放站点根"这个过渡方案**本身。要么搬出去，要么不做 —— 我不接受"先放站点根、以后再搬"，
   因为搬的时候正是那个 `--delete` 在等它。

## 议题 3：KV 快答出口 —— 第一版不给。快 4 倍买不到"它说错话"的权力

### 结论

**不给。** KV 第一版只有一条读出口：**装配进主 agent 的简报**（用途是"决定派哪个子 agent / 要不要新建"）。
**KV 绝不直接对用户说话。**

### 判据

- **收益（实测，v1 原型）**：经验直出 **1.5s** vs 全流水线 **6.5s**，约 **4 倍**。
  这个数我认，它是真的。
- **代价（实测，v1 原型）**：它错配过 —— 问"跟客户解释延期"复用回了"失眠"的答案。
  v1 的修法是**表面相似度闸门**（覆盖率 0.6 + Jaccard 0.4 的混合，阈值 **0.18**）+ 兜底路径不沉淀。
- **为什么我不能接受**：错配在"参考位"是**建议**，在"出话位"是**对主人说了错的话**。
  而 v6 的产品纪律里最硬的一条是 **沉默优于编造**，还有一条是**"进行中"状态不许说假话**（已经两次真实事故）。
  快 4 倍换来的是一类新的假话，账不划算。
- **放行门槛（可测）**：要用 30 条历史问题做**离线回放**，
  KV 直出的**错配率必须 < 1/30（≤3.3%）**，且错配的都不涉及数字、时间、来源这三类。
  在这个数据出来之前，我不签字。
- **还有一条比错配更硬**：KV 的写入来源分等级（`owner` / `verified` / `unverified`）。
  **从网页、制品、别的会话写进来的条目，一律不得进"行动依据"位** —— 否则就是"慢速投毒"：
  一次注入写进记忆，此后**每个新会话都当成主人自己的知识**。这条与快答出口绑定：**没有采信等级，就没有出口。**
- **替代方案（够用且不破纪律）**：首句的"快"由**主 agent 的第一段文本**承担 ——
  人格里已经写了"先应一声、不超过 25 字、不给结论"。所以"快"这件事**不需要第二条出口**，
  也就不需要一个新的错配面。判据：首句实测 1127–1651ms，用户看到第一句 2207ms（真浏览器）。
- **KV 的真相源纪律（写进设计）**：KV 是**派生数据、可重建**；与事件流冲突时，**以事件流为准**。
  否则我们就有了第二个真相源，而"哪个是对的"这件事本身会变成故障。

### 我会砍什么

1. **砍"KV 直出话"这条通道**（不是延迟到以后，是**第一版没有**）。
2. **砍 KV 的自动写入**：先只允许 agent 显式调工具写 + 复核过的才升 `verified`。
3. **砍"用 KV 替代会查证的回答"**：凡是涉及版本、价格、天气、时间这类会过时的，**必须去查**。
4. **砍 v1 那条错配的复盘**——不是砍，是**保留**：把它作为快答出口的回归测试第一条。

## 议题 4：悬浮聊天 4 条 —— 全部同意，但每条我都要加一个"出事怎么办"

设计稿：`docs/UI-terminal-floating-chat.md` §十三。

### 结论

4 条全同意（自动收起 / 半开点小程序算收起 / 宽屏限宽 760 / 触控撑到 44），
但每条各加一条**附加约束**，否则"手感优化"会顺手把两条纪律破掉。

### 判据

**4.1 打开小程序时聊天自动收起 —— 同意，但加两条硬约束。**

- 附加 A：**正在输出的消息不许被"自动收起"藏起来**。
  判据：只对 `isFinished == false` 的当前消息生效 —— 如果助手正在说，
  要么不收起，要么收起但标题行必须显示"正在说…"。**不能让"我说了一半的话"从屏幕上消失。**
- 附加 B：**收起不许吞掉未发送的输入**。判据：收起前后输入框内容 byte 级一致（测试断言）。
- 因为 **R6 不能被浮窗吃掉**：收起态必须仍留着"还有件事在处理"的小标（`⏱N`）。
  判据：收起态下该小标可见（widget 测试断言存在）。

**4.2 半开时点小程序可见区域 = 收起 —— 同意，不穿透。**

- 判据：点可见区域后 `_collapsed == true`，且小程序**收到的点击次数为 0**
  （在小程序里放一个自增计数器 State，断言计数不变）。
- 附加：这个拦截层**只在聊天展开时存在**；聊天收起时它必须消失，否则小程序的按钮点不动 ——
  这是最容易写错的一处，判据同上（计数器在收起态必须能自增）。

**4.3 宽屏限宽 760 居中 —— 同意。**

- 判据：宽度 >900px 时，浮窗实际宽 ≤760 且水平居中；**语义不变**（仍是覆盖，不做侧栏）。
- 附加：宽屏下三档高度**按容器高算，不按屏高** —— 否则最大化会超出容器上沿。
  判据：最大化时 `top ≥ 12`、`bottom ≥ 10`（复用现有测试的"四边留缝"断言，改成用容器尺寸算）。

**4.4 触控目标撑到 44 —— 必须做，而且要给回归判据。**

- 现状（实测）：为了把收起高度压到 **124**，输入条按钮被压成 `VisualDensity.compact + iconSize 20`；
  v6 附五记过：收起高度第一版写 104 时，widget 测试直接报 `RenderFlex overflowed by 6.5 pixels`。
- 所以这条是**两个约束打架**：可点性（≥44）与高度（124）。我的裁定：**视觉保持 20，命中区用透明 padding 撑到 44。**
- 判据：① 按钮命中区实测 ≥44×44（`tester.getRect`）；② 收起高度**仍为 124**；
  ③ `RenderFlex overflow` 的回归测试必须仍然通过（不许用"把高度改成 130"来绕）。

### 我会砍什么

1. **砍"下拉消息列表到顶再收起"**这类花活 —— 它和多一个手势冲突，收益小、误触大。
2. **砍侧栏/停靠形态** —— 主人明确要"打开覆盖"，宽屏也只是限宽。
3. **砍动效装饰**：只留 200ms 档位切换 + 180ms 覆盖退让；其余（新消息位移、渐变噱头）全砍。
4. **砍"最大化 = 铺满"**这个念头 —— 四边留缝是"它浮着"的唯一证据。

## 议题 5：污点棘轮 —— 接受。这是唯一能同时保住"直接动手"和"网页永远借不到手"的解

### 结论

**接受。** 规则钉死为：
**读到不可信内容（网页 / 制品 / 别的会话输出）⇒ 本会话当场关掉"改系统"和"对外发送"两档；
只有主人下一条原话能清。** 主人说"改"，直接改；"查完网页顺手改系统"，补一句"改吧"。

### 判据

- **威胁是真的，不是假想（实测）**：agent 有 `danger-full-access`（`~/.dsh/settings.yaml`）、
  `sudo -n true` 通过、人格要求"版本/价格/新闻必须去查"⇒ 它**必然会读网页**；
  而它读到的内容在它眼里**和主人的话没有区别**。
- **第二个执行体（实测）**：监控 agent 走**同一个 `AgentRuntime`、同一份 cfg** ⇒ 同权、无 `toolFilter`；
  而它的输入是**主 agent 自己的输出**（含刚抓来的网页正文），产出又会回到 agent 可读的任务簿
  （`/api/debug/tasks`），而手册授权它"对就改、重启自己"。
  **所以只防主 agent 是不够的 —— 今天有两个全权执行体。**
- **代价要算清楚（我认这个代价）**：
  - 不碰网页的轮次：**零影响**；
  - 只读工具（看文件、搜、查）：**零影响**；
  - **写工作区**（T1）：**零影响** —— 这条必须保留，否则 agent 连草稿都写不了，会变成废人；
  - 只有"**读到外部内容 + 要动系统/往外发**"才需要补一句。
  - 频次预估：**1–2 次/天**（推定）。**校准方式**：先记账 7 天，主人每补一句就记一条；
    如果实际 **>3 次/天**，这个设计就得改（改成"当轮声明意图即可"，而不是每轮追问）。
- **落地判据（DSH 侧已核实可用）**：
  - `PostToolUse` 命中 `web_search|web_fetch` ⇒ 置 taint；
  - `PreToolUse` 命中 `bash|write|edit` ⇒ 读 taint ⇒ **deny**（不用 `ask`：本环境 approval=never，`ask` 无意义）；
  - **清 taint 的动作必须放在 host 进程**（`dispatcher.say()` 收到主人原话时清），**模型碰不到**；
  - 关掉的档位在 trace 里留痕（`taint: on, denied: bash`），事后可复盘。
- **例外清单（必须先列，否则会被当成"什么都拦"）**：
  ① 主人原话触发的轮次不降档；② 上游故障、超时这类**非内容来源**不置 taint；
  ③ 同一个会话里"主人先说了改、之后才查的网页"—— 按**时间顺序**判定，不以"查过"一票否决整轮。
- **如果这套不做**：那么"网页"到"整机"之间**没有墙**，而门后面是主人的全部对话 + 免密 sudo + 30 天不可吊销的令牌。
  这一条我不接受用"先做起来再说"来换。

### 我会砍什么

1. **砍"逐动作人工审批"**：每天几十次打扰，而且本环境 approval 是禁用的（技术上也不成立）。
2. **砍"agent 自己清 taint"**：裁决权必须在 host。
3. **砍"只给主 agent 加约束、监控 agent 照旧"** —— 监控层必须一起降权（只读 patch、无 bash/无 web）。
4. **砍任何"用提示词解决"的方案**：人格里写"不要被注入"是提示级，不是执行边界。

## 议题 6：成本触顶 —— 先降档、仍要答、同时**明说**；只有彻底耗尽才停，且必须留一句人话

### 结论

**分三级，不许静默**：
**75% 预算 → 降档仍答；90% → 只许"答 + 不加新工具"；100% → 当天不再开新轮，回一句固定人话。**
全程在 trace 留痕。**任何一级都不允许"静默变慢"或"静默截断"。**

### 判据

- **现状（实测）**：`grep usage|cost|token` 在 `services/core/src` **0 命中** ⇒ **零计量**。
  在这种状态下谈"预算"是空的 —— 所以第一件事不是加限制，是**先有数**。
- **一轮的最坏量级（实测/推定）**：单轮**无步数上限**（`settings.yaml` 只设了
  `maxParallelToolCalls: 20` 与搜索 `maxUses: 10`）；每步最多 **20 个并行工具**；
  每轮最多 **10 次搜索**，而**每次搜索本身是一次 4096 max_tokens 的模型调用**；
  `request/header` 固定前缀 **25.6KB ≈ 7k token**，**每一步重发一次**。
- **两个放大器（实测）**：
  ① `turnDeadlineMs = 180000` **只收口气泡、不会停止 agent**（SDK 不支持取消）⇒ 到点了它还在烧；
  ② `escalateAfterMs = 15s` 把它变成任务后**还会被续做最多 3 次** ⇒ 成本再乘一遍。
- **可被刷的入口（实测）**：`POST /api/debug/analyze {"force": true}` **直接绕过 60 秒冷却** ⇒
  持令牌者可无限刷监控审查。**这是安全与成本两个问题叠在一处**，必须先关。
- **阈值（推定，需按第一周真实账单校准）**：
  `maxStepsPerTurn = 12`、`maxToolCallsPerTurn = 30`、`maxSearchesPerTurn = 6`、
  `budgetUsdPerTurn = 0.20`、`budgetUsdPerDay = 3.00`。
- **分级行为**：75% ⇒ 关思考 / 降 effort / 少搜（trace 记 `degraded:true`）；
  90% ⇒ 允许"把结论说完"，禁止新开工具；100% ⇒ 当天不再开新轮，回一句固定话术。
  **判据**：把 `maxStepsPerTurn` 临时设为 3，跑一个复杂问题 ⇒ trace 里 `steps ≤ 3`，
  且用户收到的是一条**带结论的**收尾语（不是空白、不是半句）。
- **必须先修的前提（实测缺口）**：**DSH 的 session 事件里没有 token 用量**
  （`turn/end` 只有 `reason.kind`，`step/end` 只有 `{turn,step}`）。
  所以第一版的降档判据**只能基于计数**（步数 / 工具数 / 搜索次数 / 前缀字节估算），
  **不能基于花销**。这一点必须写明 —— 否则我们会以为自己在按钱降档，其实不是。
- **明说的文案纪律**：预算触顶时说的话要**短、不解释内情、不留客式追问**
  （人格里明令禁止"要不要我…"）。判据：文案里不出现百分比、不出现"配额""额度"这类内部词。

### 我会砍什么

1. **砍 `/api/debug/analyze` 的无限制 `force`**（每日 ≤20、最小间隔 10s、记审计）。
2. **砍任何"预算内不限"的承诺** —— 我宁可现在写死一个小数字，也不要一个没有闸门的"通常够用"。
3. **砍第一版的后台扇出**（workflow / ralph 那类多 agent 并发）；单轮预算没落地之前不开。
4. **砍"静默降档"**：降档必须被记下来，否则出了怪事没人知道它已经降过档。

## 议题 7：首句延迟 vs 深度 —— 不拆快层。先止损，再谈延迟

### 结论

**不拆。保留"一个 agent 三段输出"。** 延迟问题的**第一个变量不是模型，是 CPU 抢用**；
在构建还没移出 cgroup 之前，任何延迟优化都是**在错误的变量上优化**。

### 判据

- **现状（实测）**：首句 **1127–1651ms**；用户看到第一句（真浏览器口径）**2207ms**；
  整轮 **2053–2816ms**；需要查外部信息 **9500–13768ms**。
  v6 之前的手搓版本首句是 626–824ms —— 但它会编、不会自己查、不记上一轮。**这笔换来的东西是真的。**
- **真正的元凶（实测）**：`cpu.stat` 里 **10428 个周期有 9439 个被节流（90.5%）**，累计节流 **1861 秒**。
  也就是说：只要 agent 在跑构建，**主人那一轮的首句延迟被同 cgroup 的构建拖着**，
  而且更容易撞上 `escalateAfterMs = 15s`（被挪走）与 `turnDeadlineMs = 180s`（被收口）。
- **所以先做这两件，再谈拆层**：
  ① 构建移出主 cgroup（`build.slice`，`CPUQuota=300%`、`CPUWeight=10`）；
  ② agent 进程 `CPUWeight=100`（让它总先跑）。
  判据：构建期间 `nr_throttled / nr_periods` **不再接近 100%**，且构建期间
  `node watch.mjs "现在几点"` 的首句 **< 3s**（实测目标）。
- **拆快层的门槛（写死，免得以后凭感觉翻案）**：只有当
  ① 冷启动已解决、② 构建不再抢 CPU，**之后**实测**首句 p50 仍 > 2s**，才重新讨论拆层。
  现在两条都不成立。
- **拆层的代价（我的账）**：多一个"能对用户说话"的执行体 ⇒
  直接和 v6 花了整节纠偏的"**像一个人一次说完**"冲突，并且**新增一个错配面**（见议题 3）。
  收益上限约 **300–500ms**（推定）。在冷启动还占 2.7–5.1s 的时候，这 500ms 我不换。
- **顺带一条必须一起做的**：`turnDeadlineMs = 180s` 只收口气泡、**不停止 agent**（实测）⇒
  超时之后它还在烧钱、还在占内存。判据：超时事件里必须有 `agentStillRunning: true` 的标记，
  并在下一次机会**强制回收该 agent 进程**（不能只收气泡就完事）。

### 我会砍什么

1. **砍"为延迟引入第二个会说话的执行体"**。
2. **砍"止损之前做任何性能 PR"** —— 顺序错了，优化出来的数不可信。
3. **砍"预热换首句"**（与议题 1 同一条）：1G 里预热是负资产。
4. **砍"把超时当收口"**：收口 ≠ 停止。这条我要求写进不变量：**超时必须伴随资源回收动作。**

## 我最不能接受另外两位的哪一条

### 对沈简：不能接受「因为风险清单太重，所以先砍清单」

他要砍功能，我支持；砍到清单上，我反对。**这两者的不可恢复程度差一个量级。**

- 砍一个功能：用户当场就知道"没有这个"，随时能加回来。**可恢复。**
- 砍一条边界：它不报错、不提示，直到最坏那天 —— 而那天它就是**不可恢复**的。
  证据有两条，都不是推演：
  ① `OOMPolicy` 没写 ⇒ 默认 `stop` ⇒ 一次构建进程被 OOM **升级成整个 cgroup 停机 + 3 秒重启 + 把同一件重活重派一遍**
     （近 7 天 4 次，受害者每次都是 agent 自己起的 Flutter 编译器）；
  ② 制品与 API 同源 + `rsync -a --delete` 没有 `--exclude` ⇒
     **下一次常规部署就把小程序和防篡改基线一起抹掉，而且不报错**。
- 所以我的反提案：**清单可以砍，但砍的是"没有可测判据的条目"，不是"看起来不紧急的条目"。**
  砍 P2 里那些写不出验收判据的，我同意；砍 P0/P1 的，请给出
  "**这条失效时，恢复时间 < X 分钟**"的论证，我们逐条过。
- 我承认他有一半是对的：**清单本身也是成本**。51 条里有相当一部分应该被合并、被降级成"守则"，
  而不是每条都当成一个项目去做。这个账（人日）我认。

### 对陆明：不能接受「要更多容量给家人用」

这不是意愿问题，是 1G cgroup 的**物理事实**。而且它坏的姿势特别难看。

- 算给他看：每多一个活跃会话 ≈ **+344–367MB**（产品 agent 172 实测 + 监控 agent 172–195 推定），
  对 1024MB 上限。**2 个就占 756–802MB**；第 3 个越界。
- 上限不是我们定的，是内核定的。越界之后的表现**不是"慢一点"**，是：
  内核挑 RSS 最大的杀 → `OOMPolicy=stop` 停掉**整个 cgroup** → 3 秒后重启 →
  对账把同一件活**原话重派**（`resumePrompt` 还要求"先把改动做完并验证生效"）→ 再 OOM。
  三个放大器：`RestartSec=3` 配 systemd 默认熔断 `5 次/10 秒` **永远凑不满**（自带保护失效）；
  `MAX_RESUME_AT_BOOT=2` 其实是**每会话**；OOM 失败**也消耗**续做额度。
- 于是主人最后收到的是「可能没做完」。**他以为是 agent 没做完，真相是机器把它杀了两遍** ——
  而页面上那句"正在恢复连接"也是假的。这正是本项目**已经两次真实事故**的那一类：
  **页面在说假话**。而"最后一次成功"是陆明自己定的信仰 —— 我提醒他：
  **OOM 连环的结果，是用户连一次成功都拿不到。**
- 我也不同意他把地基说成"用户看不到的变化"。备份、`OOMPolicy`、独立 origin，
  **它们的价值恰好只在最坏那一天显现**；而那天要是没有它们，代价是**不可恢复**（`data/` 零备份，
  四处副本全无保留期）。看不见 ≠ 不产生价值；只是它的价值在别的时间线上兑现。
- 我的让步（诚实的）：**加人这件事不必永远不做** —— 但它有前提顺序：
  ① 先把构建移出 cgroup（否则一次构建就吃掉两个会话的份额）；
  ② 再给每个会话独立 slice（各自限额，一个死不带崩别人）；
  ③ 然后才是第三个会话。这三步都不是"这一轮"。
- 一句话给他：**先把"第 2 个人也能稳定用"做到，再谈第 3 个人。**

## 一句话

**我支持砍功能、砍清单里的空话、砍一切花活；但我要求在这一轮先把三件"不报错的坏事"堵上 ——
`OOMPolicy` 默认值、制品同源与 `rsync --delete`、`data/` 零备份；
因为功能砍了随时能加回来，而这三件一旦在最坏那天应验，是加不回来的。**
