## 七、✅ **agent 本体进镜像了**（多租户 ②-1，2026-09-21）

> 上半（§一–§六）证明的是"**整套服务的形状**装得进容器"。
> 这一节补的是那件一直缺的事：**镜像里没有 `dsh`** ⇒ 容器起来了也**没有 agent 可跑**
> （服务会 spawn 一个不存在的程序，现象只是"它不理我"）。

### 7.1 结果（实测）

| 判据 | 读数 |
|---|---|
| 镜像大小 | **130 MB → 385 MB** ⚠️ 但**所有租户共用同一份镜像层**（`podman images` 里只有一份）⇒ 每人真正占的是**他自己的卷**，不是 385MB |
| 容器里 `dsh --version` | **`0.1.5-rc.1`** |
| 空 `DSH_HOME` 起 `sdk` profile | ✅ `--help` 正常出（**镜像里不需要带 profile 模板**，见 7.2①） |
| 带人格那一层 | ✅ `--patch /app/hupo-persona.yml --dump-config` = 14643 字节 |
| 服务照常起 | ✅ `/api/version` **200** · 根 **`EROFS`** · 容器里 `dsh` 在 |

### 7.2 三条**先测了才写**的事实（省掉一整类返工）

① **`dsh` 自带 `sdk` profile** ⇒ 镜像里**不用带 profile 模板**。
   空 `DSH_HOME` 直接 `dsh --profile sdk --dump-config` 就出 11178 字节的树。
   ⚠️ 我差点自己塞一份模板进去（那会多一份**会漂**的东西）。
   ⚠️ 顺带：`--from-default-profile sdk` 会被它**自己拒掉**
   —— *"profile sdk is shipped and cannot be a custom profile target"*。
② **起的过程中不碰任何包管理器 / registry**（grep `pnpm|npm install|registry` = **0**）
   ⇒ 这台机器够不着 Docker Hub **不影响**。
③ **`bin.js` 只看 `process.argv.slice(2)`**（不看 `argv[1]`），而且**不直接调 shell**
   （没有 `exec(` / `shell:true` / `/bin/sh` 字面量）。

### 7.3 🔴 两个坑（都真踩了，都记下来）

**坑 ①：给 `bin.js` **包一层启动器**，进程会静默退出 0、一个字都不输出。**

镜像里**没有 `/usr/bin/env`**（scratch + 只拷了 node），而 `bin.js` 的 shebang 正是
`#!/usr/bin/env node` ⇒ 直接执行它一定失败。我第一版写了个三行的启动器：

```js
#!/bin/node
import '/app/node_modules/@deepseek-ai/dsh/lib/bin.js';   // ❌ 静默退出 0
```

**根因**在 `bin.js` 最后一行：`if (import.meta.main) await runCli();`
—— 被 `import` 时 `import.meta.main` 是 **false**（入口变成了启动器），
于是 **`runCli()` 一次都没调**，进程正常退出（退出码 0）。

⇒ ✅ **正解**：把**拷进来那一份**的第一行 shebang 换成 `#!/bin/node`，
`/bin/dsh` 直接指向它。此时它**仍然是被执行的入口** ⇒ `import.meta.main` 为真，
它自己那些**相对路径**的 `import("./plugin-….js")` 也照旧解析（没有搬家）。
⚠️ 并且判据卡在**"真换了没有"**上：`sed` 没匹配上会**静默不改**，而那种镜像照样 commit。

> 这条的教训不止于 dsh：**"包装一下就哑了"是退出码 0 的那种失败** ——
> 它不会红，只会"什么都没发生"。所以判据必须是**看输出**，不是看退出码。

**坑 ②：注释写在**续行命令**中间 ⇒ 整条命令失败，而脚本**照样打印成功**。**

```bash
"$BUILDAH" config \
  --env HUPO_AGENT_CWD=/data/main \
  # ⚠️ 这行不是注释 —— 上一行的 \ 已经把它拼进同一条命令了
  --env HUPO_DSH_BIN=/bin/dsh \
```

⇒ `buildah config` 整条失败（镜像**没有 Cmd/Env**），而 `commit` 仍然成功，
脚本**照样打印"✅ 镜像好了"**。是日志里那句 `--env: command not found` 露的馅。
⇒ 修法两条：注释放到**整条命令之前**；并且 `config ... || exit 3`（**失败了不许往下走**）。

## 八、✅ **换手**：agent 的手真的是 uid 1000 了（多租户 ②-2，2026-09-21）

> 决策 ① 说"**agent 读不到自己的 key**"。而 userns 的容器 root 带着 `CAP_DAC_OVERRIDE`
> ⇒ **agent 只要是 root，任何权限位都拦不住它**。所以"盒内服务 = root、**agent 的手 = uid 1000**"
> 不是讲究，**是那条决策的唯一实现**。§七 只是把 `agent` 这个身份**写进了 `/etc/passwd`**
> —— 那时它**只是声明**；这一节才让它真的跑起来。

### 8.1 落成了什么

| 件 | 在哪 |
|---|---|
| `HUPO_AGENT_UID` / `HUPO_AGENT_GID` | `config.js`（**默认 `null` = 不换手**）+ 镜像里设 `1000` |
| spawn 时真的降权 | `agent-runtime.js` 把 `uid`/`gid` 放进 `spawn` 的 opts（**不设时一个键都不加**） |
| `DSH_HOME=/data/dsh` 归 agent | 镜像 env + 入口建那一格（`/data` 是 root `0711`，uid 1000 自己建不出来） |
| **横幅如实报"手是谁"** | `describeAgentIdentity(cfg)` —— 没换手 / `uid 1000 / gid 1000` / **⚠️ root** 三种说法 |

⚠️ **宿主上必须不换手**：本机服务跑在 `deploy` 下，他的 agent 就该是 `deploy`
（换手要特权，而宿主上的服务**没有**特权，也不该有）⇒ 所以默认是 `null`。

### 8.2 判据（容器里实测，2026-09-21）

| # | 判据 | 读数 |
|---|---|---|
| 1 | 入口铺完那几格的属主/权限（**自己 `exec` 进去看**） | `/data` **`0:0 0711`** · `main`/`workspaces`/`hupo`/**`dsh`** 全是 **`1000:1000 0700`** |
| 2 | 横幅那一行 | **`agent 身份 uid 1000 / gid 1000（盒子里的"手"；服务自己是 root）`** |
| 3 | 🔴 **换手本身**：容器 root 以 `uid:1000` 起 `dsh` | ✅ `status=0`、输出 `0.1.5-rc.1` |
| 4 | **负向对照**：不换手时子进程是谁 | 🔴 **`uid=0`** —— 这就是决策 ① 要避开的那个 |
| 5 | 换手之后**还干得了活** | ✅ 写 `/data/dsh/sessions/x` ✓ · 写 `/data/main/note` ✓ |
| 6 | 换手之后**够不着不该够的** | ✅ 写 `/etc/hosts` ⇒ **`EACCES`** |
| 7 | **负向对照**：服务（root）读得到 agent 的东西吗 | ✅ 读得到（它**该**读得到：那是用户自己的话） |

**判据 3/4 是一对**：少了 4，"以 uid 1000 起得来"可能只是因为**这台机器上换不换都一样**
（比如服务本来就不是 root）。⇒ 两个读数摆在一起才说明"这条闸真的在起作用"。

### 8.3 ⚠️ 换不过去**必须大声失败**（不许静默退回 root）

`spawn` 的 `uid` 不存在 ⇒ **EPERM**（异步 error）⇒ 走 `child.on('error')` 那条路
⇒ agent 起不来、**报错**。**这正是要的**：静默退回原身份 = 边界不在而一切看起来正常。

判据（`test/agent-identity.test.js`，**5 条**）：
横幅三种说法 · 配置解析（没设/写错 ⇒ 不换手，而 **`0` 原样读出来**——
把它悄悄变成 `null` 会让"我明明设了 0"变成"我什么都没设"，更难查）·
**不设时 spawn 的 opts 里一个 `uid`/`gid` 键都没有**（负向对照，宿主行为逐字不变）·
设了 `1000/1000` ⇒ 真传下去 · **换不过去（不存在的 uid）⇒ 报错**。

### 8.4 ⚠️ 一件**还没定、但已经绕不开**的：容器里"我是谁"

`worlds.js` 里 `owner` 的数据在 `data/` 根、别人在 `data/users/<uid>/`。
而**容器里只有一个用户**、卷就是 `/data` ⇒ 入口铺的是 `/data/main`、`/data/dsh`（**根下**）。

⇒ 也就是说，**容器里那个租户必须表现为 `owner`**，那几格才对得上。
机制现成（服务开机用 `HUPO_OWNER_PHONE` 把某个号绑到 `owner`），
⇒ **起容器时把那个租户的号传进去**就行。
⚠️ 这一条**我还没接线**（③ 那半才用到），**先写在这里免得下一个人以为容器里会走 `users/<uid>/`**。

## 九、✅ **盒子里的 root 小代理**：它持有 key，agent 读不到明文（多租户 ②-3，2026-09-21）

> 决策 ① 要"**agent 读不到自己的 key**"，可 dsh 调模型**必须**有 key。
> 这一节把"**持有**"与"**使用**"分开 —— 这是 `37-MULTITENANT.md` §12.2 右边那一列的落地。

### 9.1 形状（一条线看懂）

```
明文  →  /run/hupo/creds.yaml      （tmpfs · root 0600 · 不在 /data 也不在 /home）
持有  →  src/model-proxy.mjs       （root 身份跑，只听 127.0.0.1:8787）
使用  →  agent 把请求发给那个口     （它的 env 里只有一个**占位符**）
```

**怎么让 agent 走代理**：一份**静态 patch**（`/app/hupo-model-proxy.yml`）改 `llm-deepseek`
那一条的 `baseURL` + `apiKeyEnv`：

```yaml
- id: llm-deepseek
  config:
    baseURL: http://127.0.0.1:8787
    apiKeyEnv: HUPO_MODEL_TICKET
```

⚠️ **为什么走 patch 而不是环境变量**：`baseURL` 本来能被 `DEEPSEEK_BASE_URL` 覆盖，
但**那个名字自带 `DEEPSEEK`** ⇒ 会踩 V4b 那条 `env` 扫描。⇒ 两条都走 patch，
**agent 的 env 保持干净**。

⚠️ **占位符为什么叫 `HUPO_MODEL_TICKET`**：`apiKeyEnv` 必须是合法引用名
（`^[A-Za-z_][A-Za-z0-9_]*$`），而这个名字**刻意避开** `_API_KEY` / `_TOKEN` / `_SECRET` / `DEEPSEEK`
⇒ V4b 扫描命中 **0**（实测）。它**不是秘密**（真 key 在代理那边）。

### 9.2 判据（容器里实测）

| # | 判据 | 读数 |
|---|---|---|
| 1 | 代理起来了吗（它的日志） | `模型代理 127.0.0.1:8787 → …（key 从 /run/hupo/creds.yaml 现读）` —— ⚠️ **日志里没有 key** |
| 2 | 🔴 **V4b**：agent 那一侧 env 里秘密形状的变量 | **命中 `0`**；占位符 `HUPO_MODEL_TICKET=hupo-local-model-proxy` 在 |
| 3 | root 放 key（`0600` `属主 0`）之后，**agent 经代理请求** | ✅ **`200`** |
| 4 | 🔴 **agent 自己读那份 key 文件** | ✅ **`EACCES`**（**不是 `ENOENT`** —— 文件真的在，只是它够不着） |
| 5 | 🔴 **上游收到的是谁** | ✅ **`Bearer REAL-KEY-MUST-REACH-UPSTREAM`**（**真 key**） |
| 6 | **负向对照**：上游收到的是不是那个占位符 | ✅ **不是**（是的话 = 头根本没换 = 这条路没接上） |

⚠️ 判据 5/6 那一对是这一节的**全部意义**：光看"请求返回 200"证明不了"换头了没有"
（上游可能压根没校验）。⇒ 探针里用一个**假上游**把收到的 `Authorization` **记下来**看。

### 9.3 单测（`test/model-proxy.test.js`，**9 条**）+ **四处变异验证**

判据：解析（单行 / YAML 那种 / 引号 / 注释 / **名字有值空 ⇒ 没有 key**）·
**换头**（上游必须收到真 key，且**不许**是占位符）· 没 key ⇒ **503 `no-key` 且一次都不去打扰上游** ·
**流式**（第一段必须在第二段发出**之前**到客户端 —— 缓冲了就不算流式）·
**日志里一个字节的 key 都没有**（拿真日志扫）· 默认只绑回环。

| 变异 | 结果 |
|---|---|
| 不换 `Authorization`（原样转出去） | 🔴 抓住（2 条红） |
| 不判空 key（没 key 也去试上游） | 🔴 抓住 |
| 把 key 打进日志 | 🔴 抓住 |
| 解析把空值当值（`NAME:` 那种） | 🔴 抓住 |

⚠️ **最后那条是测试自己抓出来的真 bug**：`NAME:`（名字有、值空）原来会走
"整份就是一把 key"那条路 ⇒ **字面量 `NAME:` 被当成 key 发给上游**。
现象是"上游说鉴权失败"，而真正原因在解析。⇒ 改成**先判像不像 YAML**，有冒号就只按 YAML 解。

⚠️ **另外一个坑**（写这一份测试时踩的）：断言在 `await close()` 之前失败 ⇒
监听挂着 ⇒ **测试进程永不退出**（"红"变成"挂到超时"）。而且我一开始让所有用例都用默认端口 8787
⇒ 一条失败会让后面**全部 `EADDRINUSE`**，一条真问题被放大成七条。
⇒ 两条一起修：文件级 `after()` 兜底关、端口用 `0`（临时端口）。**变异验证正好会大量制造"断言提前失败"**，
所以这两条不修，变异根本跑不动。

### 9.4 ⚠️ 还没做的（明说）

* **key 从外面进来**那一步（②-4）：现在 `/run/hupo/creds.yaml` 是**手动放的**。
  真正的注入（中心服务当**不透明管道**）还没写。
* **`SO_PEERCRED` 不在这一层**：容器有**自己的网络命名空间**，回环口外面进不来
  ⇒ 这一层的边界就是"容器"本身。`SO_PEERCRED` 是留给**宿主↔容器**那条通道的（②-4）。

## 十、✅ **宿主↔容器那条通道**：容器开机连出来领自己那份配置（多租户 ②-4，2026-09-21）

> 这是 `37-MULTITENANT.md` §12.1 那五步里 **②③④** 的落地：
> **容器起来是个空壳 → 等着 → key 到了 → 才启动真正那套服务**。
> 也是 §九 那个代理**真正的 key 从哪来**的答案（§九 里那份文件还是手动放的）。

### 10.1 🔴 先记一条**推翻原计划**的实测：纯 Node 拿不到 `SO_PEERCRED`

权限席给的方向是"**反向 UDS + `SO_PEERCRED`，交给内核**"。**实测做不到**：

| 查什么 | 结果 |
|---|---|
| `net.Socket.prototype.getPeerCredentials` | **不存在** |
| `sock._handle.getPeerCredentials` | **不存在** |
| `process.binding('pipe_wrap').Pipe.prototype` | 只有 `bind / listen / connect / open / fchmod` |

⇒ 要么写原生插件，要么退回"谁连上就算谁"（**不可接受**）。**所以换了一条同样由内核保证的路。**

### 10.2 ✅ 换成"**挂载表就是边界**"（权限席的另一句原话）

* 宿主**每个租户各听一个套接字**：`<dir>/<userId>.sock`；
* **每个租户的容器只挂它自己那一个**（`-v <dir>/u1.sock:/run/hupo-host.sock`）；
* ⇒ 乙的容器**在文件系统里根本看不见**甲的套接字（两个 mount namespace）
  ⇒ 身份 = "**你连的是哪一个**"，由**内核的挂载命名空间**保证。

⚠️ **代价要说清**：这样**挂载表写错 = 边界没了**（乙挂到了甲的套接字）。
这和 `39-PERMISSIONS.md` §5.7 那条"**mount 表必须 `strict`**"是**同一件事**，不是新引入的风险。
⚠️ 套接字是 `0666` 的：**安全性不来自这个权限位**（它只让容器里那个"壳"能连上），
**来自"只有那一个容器挂得到这个路径"**。

### 10.3 判据（**两台真容器**，各挂自己那一个套接字）

| # | 判据 | 读数 |
|---|---|---|
| 1 | 甲领到的是谁的 key | `HUPO_MODEL_KEY: KEY-FOR-U1-ONLY`（`600` `属主0`） |
| 2 | 乙领到的是谁的 key | `HUPO_MODEL_KEY: KEY-FOR-U2-ONLY` |
| 3 | 🔴 **交叉**：甲的 key 有没有跑到乙那儿 | ✅ **没有**（两边各查一次，双向） |
| 4 | 🔴 **它看得见几个套接字** | 每台只看得见 `hupo-host.sock`（**它自己那一个**）—— 另一个**不在它的文件系统里** |
| 5 | 容器日志里有没有 key | **0 次**（两台都是） |
| 6 | 宿主日志里有没有 key | **0 次** |
| 7 | 宿主的通道状态 | `u1:ready → u1:hello → u1:up`，`u2` 同样（握手走完） |

### 10.4 单测（`test/tenant-channel.test.js`，**12 条**）+ 变异验证

判据：一个租户一个套接字（`userId` 不许当路径用）· 没 key ⇒ `waiting` 且**不许造出空文件** ·
**key 晚到**（用户过一会儿才填）不用重连也能送到 · **两边日志都没有 key** ·
协议版本不对照实回 · 写 key **原子**（先 `.tmp` 再 `rename` —— 代理每次请求现读，不许读到半个）·
套接字不在 ⇒ `false` 不抛。

**变异验证**（都被抓住）：

| 变异 | 结果 |
|---|---|
| 凭据文件不是 `0600` | 🔴 抓住（2 条红） |
| `waiting` 分支没了 | 🔴 抓住（2 条红） |
| 每个套接字都用同一个人的 key | 🔴 抓住 |
| 把 key 打进日志 | 🔴 抓住 |

### 10.5 🔴 这一轮变异暴露的**两个真缺陷**（比变异本身值钱）

**缺陷 ①：一句不认识的话 ⇒ 容器**永远**停在"等配置"那一步。**

原来只有 `ready` / `waiting` / `error` 三个分支，别的状态就 `continue`（"没听见"）⇒
**promise 永远不 resolve** ⇒ 容器永远起不来。⇒ 修法是**两条一起加**：
认不出的状态**照实收场**，**外加一个总时限**（`hardMs`，默认 `waitMs + 30s`）兜底。
判据也补了两条：认不出的状态要**立刻**收场 · 对面一句话都不说时**总时限到点也要收场**。

**缺陷 ②：变异"表现为挂住"= 等于没抓住。**

`waiting` 变异第一版**抓不住**：总时限最终**也会**返回 `false`，只是要等 30 秒，
而我的判据只断言了返回值、**没断言"多快"** ⇒ 变异"通过"了。⇒ 两条修法：
判据加**时间断言**；并且给测试的总时限一个**短到能被断言看见**的值
（否则变异表现为"挂 30 秒"，在我的命令时限里**看不出是红**）。

> ⚠️ 这条的教训是通用的：**"卡住"和"红"在自动化里必须能分开**。
> 一个只会"挂住"的缺陷，在只看退出码的地方等于不存在。

## 十一、✅ **容器真的跑起来了，而且真的领到了 key**（多租户 ②-6 + ②-4b 前半，2026-09-21）

> 这一节是**串起来的那一步**：主人问的"新用户登录 → 建容器 → 配 key"里，
> **容器**与**配 key** 两件到这里是真的了（还差"聊天从中心转发进容器"，见 §11.5）。

### 11.1 池子：一次建好，之后**服务一行特权都不用**

* **谁建的**：`scripts/create-tenant-pool.sh`（`--yes` 才动手，先打印）
* **建了什么**：租户卷（`/home/<租户>/tenant` `0700`）· `linger` · 镜像进**他自己那份** rootless 存储
  · 通道目录（`/etc/tmpfiles.d/hupo-channel.conf`，开机自动重建）
  · **systemd 用户单元**（`~<租户>/.config/systemd/user/hupo-tenant.service`）
* 🔴 **为什么是"池子"而不是"来一个人现起一个"**：服务（`deploy`）**没有特权**，开不了别人的容器。
  两条路：给 `deploy` 一把**常驻的钥匙**（polkit / sudoers），或者**事先起好让它等着**。
  ⇒ 走后者：**服务一行特权都不需要**，容器由租户**自己的** systemd 用户管理器看着
  （`Restart=on-failure`）。
* ⚠️ **`linger` 是这一步真正的代价**：它让租户的进程**留在机器上**（权限席点名要单独看的那个面）。
  开它是因为"容器必须一直跑着等配置"这个形状**非要它不可** —— **如实写在这里，不藏**。

### 11.2 端到端（**真机、真租户、真 API**）

```
网页那条 API（POST /api/model-key，身份只从令牌的 sub 来）
   → 宿主服务把 key 记在**内存**里（不落盘、不进日志）
   → 经**他自己那个套接字**推给容器
   → 容器的"空壳"写进 /run/hupo/creds.yaml（tmpfs · root 0600）
   → 模型代理拿着它去请求上游
```

| # | 判据 | 读数 |
|---|---|---|
| 1 | 两台容器真的在跑（各自的 systemd 管着） | `hupo-tenant-hupo-a` **Up** · `hupo-tenant-hupo-b` **Up**（单元都 `active`） |
| 2 | 宿主服务报通道 | `租户通道 2 个租户在听（/run/hupo-channel）` |
| 3 | 提交 `u1` 的 key | `{"ok":true}`；服务日志 `🔑 u1 的模型凭据已收下（送给他那台容器；**不落盘**）` |
| 4 | 🔴 **甲那台容器里** | `/run/hupo/creds.yaml` = 那把 key，**`600 属主0`** |
| 5 | 🔴 **乙那台容器里** | **`ENOENT`** —— 没串过去 |
| 6 | 日志里有没有 key | 服务日志**没有**；容器日志**没有** |
| 7 | 容器里的调度器 | `/api/version` → **200** |
| 8 | 容器里的模型代理 | `/v1/models` → **401**（**不再是 503**：它有 key 了，只是那把是假的，上游说不行） |

**判据 8 是这条链真的通了的最好证据**：503 会说明"代理还没 key"，
而 401 说明"代理**拿着 key 真去问了上游**"。

### 11.3 🔴 三个坑（都真踩了）

**坑 ①：`podman` **不能以 root 跑**。**
镜像住在**造它的那个用户**（`deploy`）的 rootless 存储里，不在 root 的存储里
⇒ 以 root 跑 `podman image exists` 会得到"没有这个镜像"，然后你会以为镜像丢了。
⇒ 池子脚本里**每一处 podman 都以它自己的属主身份跑**。

**坑 ②：`sudo -u` **保留 cwd** ⇒ 换身份之后 chdir 就 `Permission denied`。**
报错长这样：`cannot chdir to /home/deploy/proj/hupo: Permission denied` +
`invalid internal status, try resetting the pause process` ——
**看起来像"权限不对"，其实只是"站在一个他进不去的地方"**。
⇒ 换身份之前先 `cd /tmp`。同一个坑这个项目**已经记过一次**，这是第二次。

**坑 ③：`podman save -o` 不许覆盖已存在的文件**
（`docker-archive doesn't support modifying existing images`）⇒ 先删再导。

⚠️ **还有一个"看起来没有、其实是权限"的**：我早先以 `deploy` 查 `/home/hupo-a/tenant`
得到"卷还没有"，而它**早就在了** —— `deploy` 进不去 `/home/hupo-a`（`0700`）。
⇒ **"看不见"和"不存在"要分清**（这和判据里那条"失败必须是 `EACCES` 而不是 `ENOENT`"是同一个道理）。

### 11.4 ⚠️ 这一步**动了机器状态**（如实记账）

| 动了什么 | 为什么 | 怎么撤 |
|---|---|---|
| `/etc/tmpfiles.d/hupo-channel.conf` | 开机重建 `/run/hupo-channel`（deploy 建不了 `/run` 下的东西） | 删掉它 |
| `/run/hupo-channel/` | 每个租户一个套接字 | 重启即消失 |
| `linger`：`hupo-a` / `hupo-b` | 容器要在他们没登录时也活着 | `loginctl disable-linger <u>` |
| `~<租户>/.config/systemd/user/hupo-tenant.service` | 容器由**他自己的** systemd 看着 | `systemctl --user disable --now` |
| `/var/tmp/hupo-tenant-image.tar`（367M） | 给租户 `podman load` 用 | 删掉；要用再导 |
| 各自 rootless 存储里的镜像（各 ~385M） | 每人一份、互不可见 | `podman rmi`（以租户身份） |

### 11.5 ⚠️ 还差的那一件（**说清楚，别让它看起来像做完了**）

**聊天还没有从中心转发进容器。** 现在：
* 容器在跑、有 key、里面的调度器**活着**（`/api/version` 200）；
* 但**中心服务没有把用户的话转给它** —— 用户在网页上聊天，走的还是宿主上那套。

⇒ 差的是一件 **②-4b 后半**：**数据面**。可选两条：

| 选项 | 代价 |
|---|---|
| **(甲) 每个租户一个回环端口**（`-p 127.0.0.1:<port>:8080`） | ⚠️ **回环是拓扑不是准入**：宿主上**任何** uid 都能连到那个口 ⇒ 甲的口乙够得着（本项目已经否过一次这条路） |
| **(乙) 经同一条通道做反向代理** ✅ | 要把通道协议从"送配置"扩成"转发 HTTP"；但**没有端口、没有回环暴露**，身份还是"你连的是哪个套接字" |

**建议 (乙)** —— 它和这一整套的形状一致。**这一件没做，所以我不会说"新用户已经能用了"。**

## 十二、🚧 **数据面**：隧道通了，但**还不能用**（②-4b 后半，2026-09-21 收在中途）

> 这一节**如实记在中途**。§11.5 说的"选项乙"（经同一条通道做反向代理）**已经写了一半**，
> 但**没有跑通**，所以**不能说"新用户已经能用了"**。

### 12.1 写好了什么

| 件 | 在哪 | 状态 |
|---|---|---|
| 宿主侧"虚拟 socket" | `tenant-channel.mjs` 的 `openSocket(tenant)` | ✅ 写好了（`Duplex`；`http.request` 与 `ws` 都能直接用它） |
| 容器侧隧道代理 | `src/tenant-tunnel-agent.mjs` | ✅ 写好了（**只连本机 8080**，`open` 帧里的地址一概不认；断了会自己重连） |
| 路由转发 | `server.js` 的 `proxyToTenant` | ✅ 写好了（只转发 `/api/say` `/api/health` `/api/export` `/api/trash`；**别的留在中心**） |
| 容器里那两行日志 | 实测 | ✅ **`隧道通了（→ 127.0.0.1:8080）`** |
| 隧道没通时的回执 | `proxyToTenant` | ✅ **`503 tenant-not-ready`** + 一句人话（**不许假装通了**）· 有 20 秒上限 ⇒ 超时回 **`504 tenant-timeout`** |

### 12.2 🔴 为什么还不能用（两个真原因）

**原因 ①：容器里那台服务是 `fail-closed` 的 —— 它不认宿主转进来的请求。**

实测：容器里自己的 `/api/health` 回的是
`{"error":"not-setup","text":"这台机器还没设密码，先设好再用。"}`
—— 因为容器里的 `Auth` **没有口令**，而它和宿主**不是同一份密钥**，
所以宿主签的令牌**在容器里验不过**。

⇒ 这是个**要定的设计点**，三条路：

| 选项 | 评价 |
|---|---|
| (甲) 容器信一条**只有 root 能开的 UDS**（内核按文件权限保证） | ✅ 与"交给内核"这条线一致；要服务支持 UDS 监听 |
| (乙) 通道发一份**每租户的密钥**给容器（宿主用它签令牌） | 要管一份每租户秘密；⚠️ **绝不能用宿主那一份密钥**（一个容器被攻破 = 能伪造别人的令牌） |
| (丙) 池子建的时候在容器里设口令、宿主持一份令牌 | 多一份要存的秘密 |

**我倾向 (甲)** —— 它不需要新增秘密，而且"root 才开得开那个套接字"是内核说了算的。

**原因 ②：宿主重启之后，容器的隧道要重新连上（这一条我修了一半）。**

🔴 **修掉的那个真问题**：套接字每次 `listen` 都要**先删再建**（新 inode），
而容器原来挂的是**那一个文件** ⇒ 宿主一重启，挂载点就指着**已经被删的旧 inode**
⇒ 容器**永远重连不上**（现象：`tenant-not-ready` 一直不变）。
⇒ 改成**每个租户挂自己的一个目录**（`/run/hupo-channel/<租户>/` 里面放 `channel.sock`），
目录 inode 是稳的。**边界没变**：每个租户只挂自己那一个目录。

⚠️ 改完之后**还要让容器重连一次**（重启容器，或者等它自己的重连周期）。
**这一步我没验完就收在中途了** —— 所以这一节是 🚧 不是 ✅。

### 12.3 🔴 另一个只有"真重启"才暴露的缺陷（已修）

**容器第二次起不来**：入口每次都 `chmod` 那几格，而**第二次开机时它们已经属于 agent(1000)** 了
⇒ root 再 `chmod` 就需要 `FOWNER`，而当时的 4 条能力里没有
⇒ 报 `EPERM: chmod '/data/main'`，**第一次好好的、重启就死**。
⇒ 修法两条一起：入口**改成幂等**（已经是他的就只确认权限）+ **把 `FOWNER` 加回来**
（root 本来就有 `DAC_OVERRIDE`，比它更强 ⇒ **多这一条不改变边界**）。

⚠️ 还有一个连带的：`--rm` **不保证**把 systemd 停下来的旧容器清掉
⇒ 下一次 `podman run --name` 报 "name is already in use"（**退出码 125**）。
⇒ 单元里加 **`--replace`**（podman 自己在报错里给的正解）。
