## 三、小程序那一屏的"白边"（报了三次的那一条）

### 3.1 主人给的那张截图，**逐像素量过**（不是靠看）

装置：PIL 直接读主人 2026-10-05 02:21 那张截图（1619×2590，安卓 Chrome，井字棋那一屏）。

| 位置 | 读数 |
|---|---|
| **右侧** | 最右**一列**是 `(244,234,255)`（**半盖**的浅色）→ 再往左一列是偏暗的紫 → 然后才是正常底色 ⇒ **一条 1 物理像素的缝** |
| 左侧 | 同样的位置**没有**这条线（0 像素） |
| 上方 | 小程序内容**贴着最上面**（y=0 就是它的深紫）—— 这张截图里**没有**上边那条 |
| 下方 | 306 物理像素的纸色 = **那一格让给聊天条**（`D3.14`"网页不铺满"，**是设计**） |

### 3.2 成因（拿真浏览器量出来的）

给探针加了两个开关（`scripts/check-web-browser.mjs`）：`--device 540x863@2.998`
（造"分数像素比那台机器"）与 `--safe-top 24`（造"有刘海那台"）。
用页内合成指针事件点开一个小程序之后，把 DOM 逐层量出来：

```
IFRAME            absolute  clip    [0,0,1281,512]
  DIV（我们那个 wrapper）  absolute  hidden  [0,0,1281,512]   ← 与"这一格"逐像素相同
    FLT-PLATFORM-VIEW static  [0,0,0,0]
      FLUTTER-VIEW   absolute          [0,0,1281,614]
```

两条结论（都是量出来的，不是猜的）：

1. 🔴 **那一帧最右一列物理像素只被盖住一部分**（他的机器上 CSS 视口宽是分数：
   物理宽 ÷ 像素比）⇒ 露出来的是它后面的**纸**（白）⇒ 那条白线。
2. 🔴 **我们原来那个"多铺 2 像素"（wrapper 上写 `right/bottom:-2px`）一个字都没生效**：
   Flutter 把**那个 wrapper 的尺寸写死成"这一格的矩形"**（量出来 1281×512，与槽一样）
   ⇒ 那两个 `-2px` 是**白写的**（2026-10-06 已删）。

### 3.3 改法

"多铺 2 像素"**改挂在 iframe 身上**（它的尺寸是我们说了算）：
`width: calc(100% + 2px)`，外层 `overflow:hidden` 把超出去的部分裁掉
（底下那条聊天条**不会被压到**）。代价如实说：小程序页面看到的宽度宽 2 像素（0.4%），
右边那 2 像素本来就在屏幕外。

⚠️ **上方那条不动**：`Padding(top: safe.top)` 是给**安卓 App**（edge-to-edge，第一行压在时钟底下）
用的；而网页那一侧量出来 **Flutter 报的安全区是 0**（`--safe-top 24` 塞进去，
`env(safe-area-inset-top)` 真读到 24，而那一帧的 top **还是 0**）⇒ 它在网页上**本来就是 0**，
不可能是那条白边的来源。

### 3.4 如实说（这一条最要紧）

* 在**他那台的形状**上（540 CSS px @ 2.998 = 1619 物理像素）我没能**复现**那条缝：
  当前线上版本量出来最右一列**没有**浅色（`right_white=0`）。
  ⇒ 结论只能说到这一步：**成因量清楚了、白写的修法换成真能生效的**，
  但"他那台手机上现在还有没有那条线"**要他一眼**。
* 他那只截图是 **2026-10-05 02:21** 拍的，而"那一帧精确等于槽"那次改动**之后**才上线
  ⇒ 也有可能已经好了。
