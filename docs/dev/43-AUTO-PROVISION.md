# 43 · 新号自动拿到一台容器（申请队列 · 安全模型先定）

> 主人 2026-09-21 选的：**真的自动开一台**（不是"只把话说明白"）。
> 同时他点名：**要定安全模型**。⇒ 这一篇**先定模型，再写代码**。

---

## 一、现在是什么样（问题的准确形状）

| 件 | 现在 |
|---|---|
| 谁有容器 | **写死的两台**：`u1→hupo-a`、`u2→hupo-b`（`data/tenants.env` 的 `HUPO_TENANT_MAP`） |
| 第 3 个新号登录 | 建号成功、拿到令牌，但 `tenantOf()` 返回 `null` ⇒ `/api/space` 回 `queued` |
| 客户端 | 等待屏**每 2 秒自己重问**、三步一直不勾 —— **诚实，但永远不会好** |
| 服务有没有特权 | **没有**。`deploy` 不在 docker 组、没 sudoers、没 polkit |

⇒ 所以"自动开一台"这句话的**全部难点**只有一件：
**一个公开的网页登录口，要怎么才能触发一个特权动作，而不等于把 root 交出去。**

## 二、三条路（以及为什么选第三条）

| | 做法 | 为什么不行 / 行 |
|---|---|---|
| ① | 给 `deploy` 一条 **sudoers / polkit** 规则，允许它跑建租户的脚本 | ⚠️ 这等于"**服务能执行特权命令**"。边界从"一个整数"变成"那个 bash 脚本必须毫无破绽"—— 而脚本要吃 `PATH`/`IFS`/环境、要处理参数，**每加一个功能就多一个面**。`create-tenant-pool.sh` 自己在文件头就否掉过这一条 |
| ② | 一个**常驻的 root 守护**，服务连它的套接字 | 边界比 ① 好（协议窄），但**常驻 root 进程**本身就是一块要长期盯着的面：它要一直活着、要防协议解析漏洞、要被监控 |
| ③ | ✅ **申请队列**：服务只能"**放一个文件**"，root 侧**按需**（systemd 触发）读它 | **服务永远不能执行任何东西**。申请的**全部内容就是一个整数**（连文件内容都不读）。特权侧只在有申请时被 systemd 拉起、跑完就退。边界小到**能用眼睛看完全部输入** |

**选 ③。** 下面就是它的不变量。

## 三、安全模型（不变量 A1–A8）

> 这一节是**判据**，不是描述。每条都写"怎么验"。

### A1 🔴 **特权侧只读一个整数，别的什么都不读**

申请 = `/run/hupo-provision/<n>.req` 这个**文件名**。
**文件内容一律不读**（可以是空的）、**不读环境变量里的任何路径**、**不接受参数**。

* 怎么验：往申请目录里放一个内容是一串 shell 命令的 `<n>.req` ⇒ 那个 `n` 正常建，
  **那一串命令一个字都没被执行**（负向对照：拿掉 `n` 的合法性，必须被拒）。

### A2 🔴 **一切路径/用户名/uid 都由特权侧从 `n` 用固定模板推出来**

```
n            ∈ [1, HUPO_MAX_TENANTS]        （整数，其余一律拒）
OS 用户       hupo-t<n>
uid / gid    3000 + n
home         /home/hupo-t<n>
卷           <home>/tenant
subuid 起点   (3000+n) * 100000
单元         <home>/.config/systemd/user/hupo-tenant.service
通道         /run/hupo-channel/hupo-t<n>/channel.sock
```

* 怎么验：拿 `n=../etc`、`n=1;id`、`n=-1`、`n=1$(id)`、`n=9999`（超上限）、
  `n=`（空）逐个塞进去 ⇒ **全部拒**，而且**目录里一个东西都没多出来**。

> ⚠️ **服务侧必须推出同一个名字**（它要提前去听那条通道）。
> 所以这条模板**只有一处权威实现是被两边共用的纯函数**（`tenants.js`），
> shell 那侧照它写、并有一条闸盯着两边一致（见 §五 判据 5）。

### A3 🔴 **申请目录是 sticky、root 属主、只允许服务"放文件"**

`/run/hupo-provision`：`1733 root:deploy`（服务能进能写、**列不出**别人的、**替换不掉** root 的文件）。
特权侧读到的每一项都必须：`lstat` 是**普通文件**（不是符号链接）、**属主是服务的那个 uid**。

* 怎么验：服务身份放一个**符号链接** `3.req -> /etc/shadow` ⇒ **拒**（负向对照：
  放一个普通文件 ⇒ 正常）。

### A4 🔴 **幂等 + 有上限 + 有最短间隔**

* 同一个 `n` 重复申请：第二次什么都不做（不能变成"重建、清空人家数据"）。
* `n` 超过上限：**不做**，并且**如实**把它记成"满了"（不是假装在开）。
* 两次真建之间有一个最短间隔（防一条申请风暴把机器打满）。

* 怎么验：同一个 `n` 连申请 5 次 ⇒ 只建一次、容器**只重启 0 次**；
  狂塞 200 个申请 ⇒ 建的数量 ≤ 上限，且**每一次拒绝都留了一行日志**。

### A5 🔴 **特权侧删掉申请，且只删它自己处理过的那一个**

处理完（无论成功失败）把这个文件删掉。失败也删 —— 否则一个坏申请会**每次开机**
被 `.path` 单元反复触发（那就是一个死循环）。

* 怎么验：放一个超上限的申请 ⇒ 文件**不见了**、日志里有那一行、系统**没有**反复触发。

### A6 **服务的身份不变**：它**不是** root、不进 docker 组、不新增任何 sudo 权限

* 怎么验：装完之后 `id deploy`、`sudo -l -U deploy`、`getent group docker` 三条
  **与装之前逐字相同**。

### A7 **每一次申请与每一次真建都留痕**

一行：时间 · `n` · 结果（建了 / 跳过了 / 拒了，以及为什么）。
申请本身**不含手机号、不含 key**（只有 `n`）⇒ 这一行日志**不泄露个人信息**。

### A8 ⚠️ **装它本身是"部署期"的动作 —— 要主人签字**

助手**只写代码、只准备方案**；把那一串单元装进系统的命令**由主人跑**
（`AGENTS.md` §八：部署期 P1/P2 原样有效）。

### A9 🔴 **root 要跑的每一份文件，都必须 root 拥有**（写这一篇时差点栽在这）

**这一条是写安装脚本时才想明白的，而它一破，A1–A7 全部作废。**

第一版我是这么想的：systemd 单元的 `ExecStart` 直接指仓库里那个
`scripts/provision-tenant-request.sh`，它再去调 `create-tenant-users.sh` /
`create-tenant-pool.sh`，三个脚本都读仓库里的 `tenant-template.conf`。

🔴 **那等于什么都没防住**：这四个文件都在 `/home/deploy/proj/hupo/` 里，
**属主是 `deploy`（也就是服务自己）** ⇒ 一个被攻陷的服务只要
**改一行那几个脚本**（或者把 `name_prefix` 改成 `../../etc`、把 `max_tenants` 改成 `999999`），
下一次申请被 `.path` 单元触发时，**那段代码就是以 root 跑的**。

> 这就是"**边界画在了一个可写的地方**"——和 `39-PERMISSIONS.md` 里
> "挂载表写错了、那个权限位就兜不住"是同一类错误。
> ⚠️ 而且它**看起来是好的**：路径写对了、脚本也真的跑起来了、日志也漂亮。
> ⇒ 所以这一条必须**当成不变量写下来**，不能靠"我记得当时想清楚了"。

**改正**：安装器把这四份**拷**成 root 拥有的：

```
/usr/local/libexec/hupo/provision-tenant-request.sh   root:root 0755   ← 单元只跑这一份
/usr/local/libexec/hupo/create-tenant-users.sh        root:root 0755
/usr/local/libexec/hupo/create-tenant-pool.sh         root:root 0755
/usr/local/libexec/hupo/tenant-template.conf          root:root 0444
```

> ⚠️ **仓库里的那一份是"源码"，不是"运行的那一份"** —— 这正是今天早些时候
> 栽过三次的那个病（*"改完了"与"生效了"是两件事*）。⇒ 安装器必须提供
> `--check`：**把仓库那份与装着那份逐字节比一遍**，不一样就明说
> "改是改了，但 root 跑的还不是它"。

* 怎么验：`--check` 在**没改**时说明"一致"；改一行仓库里的脚本 ⇒ **必须报不一致**；
  `stat -c '%U %a'` 四份都必须是 `root`；`sudo -u deploy` 改那四份
  ⇒ **`EACCES`**（不是"改成功了"）。

## 四、它怎么跑（一次新号登录的完整路径）

```
① 新手机号登录            handleLogin → users.ensure(phone) → id = u3
② 服务问一句"有没有他那台"  tenantOf('u3') → null
③ 服务**申请**（唯一的新副作用）写 /run/hupo-provision/3.req（空文件）
④ 状态照实说             /api/space → state:'provisioning'，assigned ✔
⑤ systemd 看见了          hupo-provision.path（DirectoryNotEmpty）拉起 oneshot
⑥ 特权侧（root，几十行）   校验 n → 调现成的两个脚本（**模板只有那一处**）→ 删申请
⑦ 容器起来了              它连回 /run/hupo-channel/hupo-t3/channel.sock
⑧ 状态照实说             /api/space → state:'ready'，三步全 ✔
```

⚠️ **③ 是这一整套里唯一新增的副作用** —— 所以它是 review 的重点：
它写的是**一个空文件，名字是一个整数**。

### 4.1 状态机（`/api/space` 的 `state`）

| state | 什么时候 | 三步 | 客户端说 |
|---|---|---|---|
| `local` | 主人（本机那一份） | — | 直接进 |
| `provisioning` | **申请已受理**，特权侧还没建完 | `assigned` ✔ | "正在给你开一台" |
| `starting` | 那台**已经在跑**（单元活着），隧道还没连上 | `assigned` ✔ | 同现在 |
| `ready` | 隧道通了 | 三步全 ✔ | 进填钥匙 / 聊天 |
| `full` | **超过上限**，不会再开了 | 一条都不勾 | 🔴 **必须明说满员**，不许再让人无限等 |

🔴 **`full` 是这次新增里最要紧的一条**：现在的 `queued` 就是"永远等"，
而屏幕上没有任何一个字说它会永远等 —— 那是**项目最忌的"看着在动、其实到不了"**。

> ⚠️ 老客户端不认识 `provisioning` / `full`：`SpaceInfo.fromJson` 对**认不出的
> `state` 一律当"没就绪"** ⇒ 它们会停在等待屏（**行为逐字不变**，不会误进聊天）。

## 五、验（判据 · 每条都带负向对照）

| # | 判据 | 负向对照（**不能省**） | 现在 |
|---|---|---|---|
| 1 | 合法申请 ⇒ 那台真的被建出来、容器起来、隧道通 | 不写申请 ⇒ 什么都不发生 | ⏳ **没验**（要装了单元之后） |
| 2 | 文件名里塞 `../`、`;`、`$()`、空、超上限 ⇒ **全拒**、目录里没多出东西 | 同一个位置放合法 `n` ⇒ 建 | ✅ 全过（判据脚本 ②） |
| 3 | 符号链接冒充申请 ⇒ 拒，而且**链接指的地方没被动过** | 普通文件 ⇒ 建 | ✅ 全过（③） |
| 4 | 内容是一串命令 ⇒ **一个字都没执行** | 同一份内容换个合法文件名 ⇒ 照常处理 | ✅ 全过（⑤） |
| 5 | 服务侧推出来的租户名 **与** shell 侧推出来的**逐字相同** | 故意把两边改得不一致 ⇒ 闸红 | ✅ 两边读**同一个** `tenant-template.conf`（`test/provision.test.js` 钉着） |
| 6 | 装完之后 `deploy` 的身份三条**与装之前逐字相同** | —— | ⏳ **没验**（要装了之后） |
| 7 | 超上限 / 没装助手 ⇒ 状态是 `full`（**不是**永远 `queued`） | 上限之内 ⇒ `provisioning` | ✅ 隔离启动实测（见 §5.1） |
| 8 | 同一个 `n` 申请 5 次 ⇒ 只建一次、容器重启 0 次 | 换一个 `n` ⇒ 建 | ⏳ 真建那一半没验；"只投一次"✅ 单测钉了 |
| 9 | 模板被换成坏值 ⇒ **一台都不建**（A2/A9 的纵深防御） | 好模板 ⇒ 认 | ✅ 全过（⑦） |
| 10 | 非 root 跑 ⇒ 拒 | root 跑 ⇒ 认 | ✅ 全过（⑧） |

⚠️ **第 1 / 6 / 8 条必须在本机真的走一遍**（真建一个 `hupo-t3`），
但**要在主人签字装单元之后**。
⇒ 这是这一篇的诚实边界：**没签字之前，验不全。**

### 5.1 已经真验过的那几档（2026-09-21，隔离数据目录里跑的）

```
① 判据脚本：sudo bash scripts/check-provision-refusals.sh
   ⇒ ✅ 全过（23 条）—— 而且它自己**一台租户都没建**（最后那条盯着这件事）

② 隔离启动（HUPO_DATA 指向临时目录）里真登录三个新号：
   u1（**在静态表里** u1=hupo-a） → state=starting      申请目录：**空的**
   u2（推出来的 hupo-t2）         → state=provisioning  申请目录：2.req（**0 字节**）
   u3（推出来的 hupo-t3）         → state=provisioning  申请目录：3.req（**0 字节**）
   ⇒ 三件事同时成立：**表优先**没被破坏 · 推出来的那两台**真去申请了** ·
     而且申请**真的是空的**（A1 在真实路径上成立，不只是单测里）

③ 助手没装（申请目录不存在）⇒ 新号拿到 state:full / why:no-helper，
   日志里有一句人话 —— 不是让他对着一个永远不动的屏
```

⚠️ **② 里第一个号拿到 `starting` 不是巧合**：它落在了静态表的 `u1` 上
（那台已经建好在跑）—— 这正是"表优先"那条规则在真实路径上的样子。

### 5.2 ⚠️ 我在这件事里犯的一次错（如实记）

第一次"隔离启动"我写的是 `HUPO_DATA_DIR=…`，而**真正的变量叫 `HUPO_DATA`**
（`config.js:50`）⇒ 那次"隔离"启动**其实开的是真数据目录**，
于是它动了线上那两个文件：`data/.crashloop.json`、`data/status.json`。

* 影响：**没有造成假通知**（写进去的是 `clean:true`，不会触发"上次没善终"那条），
  线上服务也一直活着（PID 1006196，`/api/health` 正常）；`status.json` 是心跳，本来就会被重写。
* 但这是一次**真的副作用**，不能因为"没出事"就不写。
* ⇒ 纪律补一条：**"隔离"要验它真的隔离开了** —— 横幅里那行 `数据 <路径>`
  就是那条判据；不看那一行，"隔离启动"这四个字只是我自己说的。

## 六、代价（如实写，不藏）

| 代价 | 说明 |
|---|---|
| **公开口能烧资源** | 临时码现在开着（主人点名要的）⇒ 谁都能用任意手机号进来 ⇒ 谁都能触发申请。**上限 + 最短间隔 + 每条留痕**是唯一的护栏；最坏情况是"机器上多出 N 台空容器" |
| **linger 的面变大** | 每多一个租户就多一份"没登录也留在机器上"的进程（`create-tenant-users.sh` 文件头已经写过这一条） |
| **特权侧是 root** | 那一份脚本写错了就是 root 级的错。所以它**必须小**：只做"校验一个整数 + 调两个现成脚本 + 删文件"，**不许**长功能 |
| **磁盘** | 镜像每人一份（约 385M/人）+ 卷 ⇒ 上限**按磁盘算**，不是一个好看的整数 |
| **仍然不是"秒开"** | 镜像要 load 进他自己那份存储 ⇒ 第一次要几十秒。等待屏那三步照旧如实报 |
| 🔴 **镜像本身是 `deploy` 造的** | 容器跑的那个镜像是 `deploy` 用 `build-tenant-image.sh` 建出来的，**住在 `deploy` 的 rootless 存储里**。⇒ 一个被攻陷的 `deploy` **可以往镜像里塞东西**（而这台机器上每台新容器都用它）。**这一条这次没有解，也不假装解了**：uid 那道边界挡的是"甲读乙的卷"「`deploy` 读别人的卷」，**不是**"`deploy` 决定容器里装什么"。要真解它得让镜像由**第三方**（root 或另一个 uid）构建 + 内容寻址钉住 —— 那是另一件事，单独排 |

## 七、谁来装（一句话方案，给主人）

```bash
sudo bash scripts/install-provision-helper.sh --yes     # ← 一条命令（助手写、主人跑）
```

它会：① 装三个 systemd 单元（`.path` + `.service` + tmpfiles）
② 建 `/run/hupo-provision`（`1733 root:deploy`）
③ **什么都不建**（第一台容器要等真有申请）。

⚠️ 撤销也是一条命令：`sudo bash scripts/install-provision-helper.sh --uninstall`。

## 八、与既有文档的关系

* 它**取代** `create-tenant-pool.sh` / `create-tenant-users.sh` 文件头里那句
  "为什么要有池（而不是来一个人现建一个）" —— 那两句在当时是**对的**
  （服务没有特权，所以只能事先建好）；现在**多了一条受控的申请路**，
  **池子照旧有用**（它仍然是"怎么建"的唯一模板，只是名单不再是写死的两行）。
* 模板参数化之后，**加第三个租户**与**自动开一台**走的是**同一段代码** ——
  这正是我们要的：自动那条路**不许**自己长出一套平行的建法。
