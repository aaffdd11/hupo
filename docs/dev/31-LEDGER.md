### 三·补二 ✅ "动手前先读的那两处"读了（2026-09-21，实测）

| # | 上一节写的 | 实测 |
|---|---|---|
| 1 | profile 在 **`/root/.dsh/profiles/**`** | 实际是 **`/home/deploy/.dsh/profiles/{sdk,web}/`**（服务跑在 `deploy` 下）。sdk 的 bundle = `dsh-base` + `dsh-sdk-app`；两个 profile 的 `cordis.yml` / `cordis.patch.yml` **今天都还是空的 `[]`** |

**探针怎么做的**（可复现；**没碰仓库、也没碰真 profile**）：把 `~/.dsh/profiles` 复制到
`/tmp/dsh-probe/profiles`，然后
`DSH_HOME=/tmp/dsh-probe dsh --profile sdk --patch <临时 patch> --dump-config`。
⚠️ `--dump-config` 走的是**和真正启动同一套** patch 语义（`dsh-app-boot` 的 `applyEntryPatches`），

### 7.1 能力层挂在哪：**仓库自己的一份 patch**，一次都不碰 strict profile

| 形态 | **`- insert: [ … ]`** —— ⚠️ 实测：写成 `- id: <新id>` 会被当成"改一个**已存在**的条目" ⇒ stderr `patch: entry "…" not found` 且树里没有它（§三·补二） |
| 挂法 | `agent-runtime` spawn 时传**两次** `--patch`（人格 + 能力）。`dsh --patch` **可重复**（`--help` 原文） |
| `command` | **绝对路径**（本机没有系统 node；用 `process.execPath` 那一套，`integrity.js` 已有先例） |

⚠️ **两处实测更正**（写契约时还不知道，实现时撞上的）：

* `dsh --dump-config` **不代换 `!!js`**（它的原文就是"booting or **evaluating** `!!js`"**之外**那一半）
  ⇒ 它原样把 `!!js process.env.HUPO_NODE_BIN` 打出来。
  ⇒ 所以"代换有没有真的发生"**不能靠 dump 证明**，要靠**真启动**：

### 7.2 MCP 服务器怎么落到账本：**Unix domain socket**

core 侧在 `<dataDir>/ledger.sock` 上听（**0600**）；MCP 服务器连它。

* **为什么不是 loopback HTTP + 令牌**：MCP 配置里唯一的传值口是 `env`，而 DSH 会把父环境里
  匹配 `/KEY|PASSWORD|SECRET|TOKEN/i` 的名字和所有 `DSH_*` **清洗掉**（README「环境清洗」）
  ⇒ 剩下的唯一办法是**把令牌写进那份 patch** —— **而那份 patch 在仓库里** ⇒ 破"秘密不进文件"的纪律。
* **为什么不是让 MCP 进程直接 import `store.js`**：会出现**第二个写入者**，
  取号 / fsync / 审计在上面分叉。
* 准入靠**文件权限**（0600，同一个用户）。协议：**一行一条 JSON**（`{op,…}` → `{ok,…}`）。
* ⚠️ **socket 连不上 ⇒ 工具调用明确失败**，不许"先记下来等会再写"（那正是说假话的形状）。

### 7.3 「不确认不写」（D6.5）= **两个工具**

| 工具（模型看到的名字） | 干什么 | 写不写 |
|---|---|---|
| `mcp__ledger__ledger_propose` | 校验 6 个字段 + **回显**（缺哪项、哪项没听准） | **不写** |
| `mcp__ledger__ledger_write` | **再校验一遍**（宿主是权威）+ 追加一条 | 写 |

* 字段是**它自己**从主人那句话里抽的（v1 §三「甲」）；**回显给主人确认之后**才调 `ledger_write`。
* ⚠️ `ledger_write` **不信任模型报上来的字段**：6 项逐项校验（类型、范围、单位、日期是不是真的那一天）；
  不过 ⇒ **不写**，并**说清哪一项**（不是笼统"格式不对"）。
  ⚠️ **但要说实话**：宿主能验的只有**形状**，验不了"原话里到底说没说过这个数"（那是理解，不是校验）
  —— 所以 **D6.5 的"回显确认"那一步不能省**，它才是"出处"真正的闸。契约不假装宿主能验出处。
* ⚠️ **删账那一层按"人说得出的那几项"找，不按内部身份**（实现时定的，2026-09-21）：
  `ledger_delete` 收 `date` + `kind`（可选 `qty` / `unit`），**不收 `entryId`**。
  理由两条：① `entryId` 是**内部身份**，列表那段文字里根本没有它，
  模型**拿不到**（第一版写成收 `entryId`，那个工具当时**用不了**）；
  ② 就算拿得到，也不该把它念给主人听（内部词上屏 = 缺陷）。
  ⇒ 身份那一层留 `Ledger.find()` 解决。**对得上好几笔 ⇒ 不猜**，把候选念回去让主人挑
  （认错一笔 = 删错账，这是这一批最贵的一类错）。
* ⚠️ 两个工具**都只经 socket 到 core**，宿主是唯一写入者。

### 7.4 账本的单条删：**与 ⑲ 同语义**（30 天 · 可恢复 · 真删压实）

* **同一个 TTL 常量**（`trash.js` 的 `TRASH_TTL_MS`，import 用，**不许抄一份数**）。
* 墓碑形状与 `turn/*` 一致：`ledger/deleted` · `ledger/restored` · `ledger/purged`（都带 `entryIds`）。
* ⚠️ **唯一的一处不同**：`restore` **不重发内容**。
  理由：⑲ 之所以要重发，是因为**客户端有游标**（用户删掉时清了本机缓存，重连只补比游标新的）；
  账本**没有客户端游标这一层**（它不吃补发窗口），重发只会让同一个 `entryId` 在盘上出现两份 ——
  而账本要算**合计** ⇒ 会算重。**这条差异要有一条测试钉住**（恢复之后合计不变）。
* ⚠️ **任何删除都必须先落墓碑** —— "说删就删"的口子一个都不许开。

### 7.5 存储与去重

* **日志**：`<dataDir>/ledger.jsonl`（**新的一条 append-only 日志**，不塞 `main.jsonl`）；
  走同一个 `Store` + 一个 `Timeline('ledger')`（**一条日志一个取号器**，与可见时间线互不干扰）。
* **条目形状** = 信封 + 6 个冻结字段：

  ```
  { type:'ledger/entry', seq, at, entryId,
    kind, qty, unit, unitPrice|null, tax: true|false|'unknown', date,
    said }
  ```

  * `kind / qty / unit / unitPrice / tax / date` = §一 §4.5 那 **6 个冻结字段**（语义不许改，改 = 新增字段）；
  * `entryId` = 这条账目的**稳定身份**（删 / 恢复 / 去重都用它，**不复用 seq**）；
  * `said` = 主人**原话**（这就是 D6.4 要的**出处**："无出处不写"靠它）。
  * ⚠️ 信封字段（`seq/at/entryId/said`）**不算"改字段"** —— 它们是身份与出处，不是被记的那件事。
