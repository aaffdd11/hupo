# 141 · **"加载历史聊天记录出现过载"** —— 首屏只给最近一段存量历史

> **主人 2026-09-29 原话**：*「加载历史聊天记录出现过载。应该是只抓取一部分存量历史记录。」*
> 追问之后他点的：**产品那个聊天页**（`w.stalkerai.cn`）· 症状是**页面卡住/转圈很久**。

---

## 一、先量：卡的是**客户端**，不是网络（真浏览器读数）

⚠️ 先说明**为什么能量到**：主人自己那一份历史**很小**（主对话 129 条 / 24KB）——
他不可能在那上面看到卡。所以这一条只能**造一份大历史**来量：

> 起一台**临时实例**（`HUPO_DATA=<临时目录>` · 端口 8099 · 网页产物指向同一份
> `v2/services/core/web`）——**不碰线上那个单元、也不碰他的数据**。
> 临时目录里放一份**合成的** 15000 条历史（3000 轮），然后拿**同一个浏览器**
> 量"首屏主线程一帧隔多久"（页内 `requestAnimationFrame` 的间隔，180 帧）。

| 存量历史 | 首屏帧间隔（中位） | 最差一帧 | JS 堆 | 首屏推过来多少帧 |
|---|---|---|---|---|
| 131 条（**线上那一份**） | **16.7 ms** ＝ 60fps | 62 ms | 27 MB | 131 |
| 15000 条（**修前**） | 🔴 **128.5 ms** ＝ ≈8fps | 139 ms | 74 MB | 15002 |
| 15000 条（**修后**） | ✅ **16.7 ms** ＝ 60fps | 40 ms | 30 MB | **202** |

⇒ **病根不是带宽**（3MB 一会儿就传完）：是**客户端要一条一条地建、一帧一帧地画**。
首次打开时服务端把**整条历史**按帧推过去（`planResume`：`sinceSeq === 0` ⇒ 全量），
而客户端**每收一帧就 `notifyListeners()`**，那一屏又要按"整条时间线"重排一次
（`Timeline.items` 每次都 `where + sort`）⇒ 收 N 条的代价是 **O(N²)** 那一档。
历史越长，每一条越贵 —— 于是"页面卡住"。

---

## 二、改法（改了**一处**：首次打开那条推多少）

`src/resume.js` 的 `planResume()`：

```
sinceSeq === 0（首次打开）  ⇒ **只给最近 FIRST_OPEN_MAX 条**（一段连续的尾巴）
sinceSeq  > 0（断线重连）   ⇒ **一个字都不截**（原样）
```

* 新增常量 **`FIRST_OPEN_MAX`**（**数值住代码** · 手册纪律 1；量级与"客户端本地缓存上限"
  和"服务端一页"同一个档）；
* 返回值多一个 **`truncated`**（只给服务端自己看／记 —— **协议字段冻结**，
  不给客户端加字段）；
* 更早的那些**本来就有出口**：客户端往上翻会走 `/api/timeline?before=&limit=`
  （`planBackfill`，一页一页取）—— 那条路与服务端这一刀**都没新写**，
  只是以前"首屏已经全给了"，那条路**根本用不上**。

🔴 **为什么只截"首次打开"**：那条的语义是"这是历史"。
**断线重连那条补发带着"你不在的时候发生了什么"** —— 截了中间那一段，
界面上会**看起来是连着的**（那是说假话，比慢更坏）。

## 三、判据

| # | 判据 | 在哪 | 反例（变红的样子） |
|---|---|---|---|
| H1 | 🔴 首次打开 + 历史远超上限 ⇒ 只回 **`FIRST_OPEN_MAX`** 条 | `test/resume.test.js` | 又整条推（⇒ 真机上回到 8fps） |
| H2 | 🔴 给的是**最近**那一段（最后一条 = 最新那条），而且是**连续**的一段 | 同上 | 抽稀 / 给最老那一段（界面上会缺话而看不出来） |
| H3 | 🔴 **重连那条补发不许截**（`sinceSeq > 0` 原样） | 同上 | 顺手一起截 ⇒ 中间那段看起来是连着的 |
| H4 | 恰好等于上限 ⇒ 原样（不标截断、第一条就是最老的） | 同上 | 边界上多丢一条 |
| H5 | `catchUp` / `reset` / `maxSeq` 的语义**一个字没变**（P-h 照旧） | 同上（既有的那几条照旧绿） | 顺手把 `catchUp` 也改了 |
| H6 | 🔴 **真浏览器**：15000 条存量 ⇒ 首屏中位帧间隔 ≈ 60fps | 探针（见 §四） | 修前是 ≈8fps |
| H7 | 🔴 **往上翻仍然拿得到更早的**（那一刀不能把老消息变没） | 探针（见 §四） | 首屏之外的老话再也取不到 |

🔴 **真读数（临时实例 · 同一个浏览器 · 只有历史长度不同）**：见 §一那张表。
另有一条**"老话还拿得到"**的读数（H7）：

```
展开浮窗后，语义树里最老那一句 = 「第 2996 句话」（= 首屏那段 200 条的头上）

   ⇒ 客户端真的又取了一页更早的（`/api/timeline?before=…`）✓
```

## 四、这场探针怎么复现（**别在生产上造大历史**）

```bash
# ① 造一份**合成**大历史 + 一份能验令牌的 auth.json（临时目录，用完全删掉）
mkdir -p v2/services/core/data/_perfcheck
install -m 600 v2/services/core/data/auth.json v2/services/core/data/_perfcheck/auth.json
python3 - <<'PY'   # 3000 轮 = 15000 条事件（形状照抄线上真实事件：user/echo + start + text×2 + end）
...
PY

# ② 起一台临时实例（**另一个端口** · 不动线上那个单元 / 它的数据）
HUPO_DATA=…/_perfcheck HUPO_PORT=8099 HUPO_WEB=…/v2/services/core/web \
  node v2/services/core/src/serve.js

# ③ 量"首屏主线程一帧隔多久"（页内 rAF 间隔 180 帧）
HUPO_TOKEN=<现发的 owner 令牌> node scripts/check-web-browser.mjs \
  --url http://127.0.0.1:8099/ --eval '<rAF-gap 那段>' --wait 20000

# ④ 收工：kill 那台临时实例 + rm -rf 那个临时目录（**别留在 data/ 里**）
```

⚠️ 探针里那两个键要**成对**看：`medianGapMs`（一帧隔多久 ⇒ 流畅度）与
`收到的帧`（首屏推了多少 ⇒ 那一刀到底有没有生效）。
⚠️ 线上那个 `owner` 的历史很小，**在线上量不出这个病** ——
"在线上量不出来"不等于"没有这个病"（它随账龄长）。

## 五、没做的（**明说**）

* **没动客户端**：它的"往上翻取更早的"那条路本来就够用（H7 量过）。
  ✅ **2026-09-30 还了这一笔的一半**（`docs/dev/143-DEBT-PAYDOWN.md` §四）：
  `Timeline.items` 那份视图**按版本缓存**了（原来每次访问都 `where + sort` 一遍，
  一次 build 读十几次）—— 版本号做进容器自己（`_VersionedList`/`_VersionedSet`），
  **结构上不可能漏作废**（5 条判据在 `test/unit/timeline_test.dart`）。
  ⚠️ **还剩一半**：`ChatController.items`（三个列表一拼）**每调一次仍新建一份**；
  `_findMessage` 仍是线性找。
* **没给客户端加"上面还有更早的"这种**新字段**（协议冻结；往上翻就是那条出口）。
* **没截断线重连那条补发**（理由见 §二）。
* **没动 `/api/export`**（导出本来就是"把整份给我"，与首屏不是一回事）。
* **安卓真机没验**（这一刀在服务端，两端的表现应当一致；真机读数仍欠着）。
