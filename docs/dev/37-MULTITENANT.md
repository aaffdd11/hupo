## 三、身份与路由（**手册没写、这里定死**）

### 3.1 手机号 = 账号；`sub` = userId

* 令牌**已经带 `sub`**（`auth.js:313`），今天只有一处硬写死：**`server.js:356` `auth.issue({ sub: 'owner' })`**
  ⇒ 那处改成"登录时算出的 userId"。
* 🔴 **调度器不许有"当前用户"全局**：身份**只能靠参数传**。
  （服务席的原话：*"一个 `currentUser` 全局加一次 `await`，就是 A 的请求写进 B 的账本。"*）
* 会话 → 用户：`Map<sessionId, userId>`，**与 `#agents` 同生共死**；
  且 `sessionId` 由 userId 派生（`${userId}/${随机}`），**不许**出现"两个用户的会话撞同一个键"。

### 3.2 容器里那个 agent **不许知道 userId**

它只拿两样东西：`DSH_HOME` + `HUPO_LEDGER_SOCKET`（`agent-runtime.js:311,320`）。
**身份藏在路径里，不藏在参数里** —— 把 userId 当参数递进去，等于给它一个**伪造的把手**。

### 3.3 浏览器怎么走到"他那台容器"

```
浏览器 ──► 调度器（8020，只听 127.0.0.1）──► 那台容器里的 dsh
                    ▲
                    └─ 身份 = 令牌里的 sub ⇒ 查 userId ⇒ 查容器
```
⚠️ 调度器**只做路由，不做内容**：它转发的字节**不落盘、不进日志**（那是用户的对话）。

## 四、容器的形状（**实测过的那些约束**）

| 项 | 定下来的 |
|---|---|
| OS 用户 | `hupo-a` / `hupo-b`（uid 2001/2002），各自一段 subuid/subgid |
| 起法 | `sudo -u hupo-a podman run …` ⇒ **容器 root → 2001**（**绝不许映射到 1001**） |
| 卷 | `/home/hupo-a/tenant`（属主 `2001:2001`，**0700**）→ 容器内 `/data`；`/home/hupo-a/.dsh` 同 |
| 容器内布局 | 按 §2.1：`/data/main` · `/data/workspaces/<名>` · `/data/hupo/{memory,apps,audit}` |
| ⚠️ **workspace root** | **绝不许是 home、也绝不许包含 `workspaces/`**（§2.2 规则 1、2）—— 否则那个 agent 读得到**用户自己的 key**，还能写 `.bashrc` |
| `DSH_HOME` | 每用户一份，而且**容器内路径每用户不同**（N21：键是绝对路径） |
| 镜像 | ⚠️ 无根镜像在各自 `~/.local/share/containers` ⇒ **共享不了**，只能各自 load 同一个只读 tar |
| 网络 | 实测：容器**够不着**宿主 `127.0.0.1`（8020 安全）；但**够得着**宿主 `0.0.0.0` 的服务（这台机器上有 `:22` `:80` `:6001` `:8000`）⇒ **要给容器定网络策略**，不能默认全通 |

## 五、网页终端（**②那条路的落法**）

* 形态：用户在自己那台容器里得到一个 **tty**，自己跑 dsh 的配置命令把 key 写进
  容器内的 `~/.dsh/.credentials.yaml`。
* 🔴 **key 不经过调度器**：终端是**字节流转发**，我们的进程**不解析、不落盘、不进日志**。
* 🔴 **终端绝不许以调度器的身份开**（那等于把 `deploy` 的 shell 递给用户）⇒
  必须 `sudo -u hupo-a podman exec`，而**能不能 `sudo -u` 到某个用户，本身就是那道边界**。
* ⚠️ 终端 = "能执行任意命令"的入口 —— 但那是**他自己的容器**，所以是**允许**的（§2.3：盒子里的 root 给）。
  代价要认：**他能在自己那台里做任何事，包括把 key 泄给他自己** —— 那是他的选择。

### 8.1 ⚠️ 跑这几条时踩到的三件事（**都不是理论，是当场撞的**）

| # | 坑 | 现象 / 修法 |
|---|---|---|
| 1 | **`sudo -u` 保留当前目录** | 从仓库目录里跑 ⇒ `cannot chdir to /home/deploy/proj/hupo: Permission denied`，然后 `Error: setting up the process`。**看着像 podman 坏了，其实是 cwd** ⇒ **先 `cd /tmp`** |

## 九、注销账户 ⇒ 连容器一起删（主人 2026-09-21 追加）

> 主人原话：**"用户注销账户，docker 也会随着被删除。"**
> 这一条**方向没问题**，但它撞上三个硬东西，**都得先定**。

### 9.1 要删干净，一共**六处**（实测列出来的，少一处就是"假删除"）

| # | 删什么 | 备注 |
|---|---|---|
| 1 | **容器** | `podman rm -f`（以租户身份，见 11.2） |
| 2 | **卷** `/home/<u>/tenant` + `/home/<u>/.dsh` | 🔴 **数据真正在这里**（对话、账本、**他自己的 key**） |
| 3 | **租户的镜像存储** `~/.local/share/containers` | 实测 `hupo-a` 那份 **2.4M**（无根镜像不共享 ⇒ 每户一份） |
| 4 | **OS 用户** | `userdel` |
| 5 | 🔴 **`/etc/subuid` 与 `/etc/subgid` 里那两行** | ⚠️ 实测：`userdel` **不会**自动清（这两个文件在 man 里只出现在 SEE ALSO） |
| 6 | 🔴 **调度器侧那张映射表**（手机号 → userId → 容器） | **它本身也是个人信息**；而且"注销"之后它还留着，就是**说假话** |

### 9.2 🔴 今天**做不到**：服务没法以租户身份干活（实测）

```
$ sudo -n -u hupo-a true
sudo: a password is required
```

⇒ **服务（`deploy`）不能免密变成租户** ⇒ **起容器、进容器、删容器，它一件都做不了**。
这不是小问题，是**整条多租户链路的拦路虎**（网页终端那条路也一样要它）。三条路：

| 路 | 代价 |
|---|---|
| **(甲) systemd 模板单元** `hupo-tenant@.service`（`User=%i`） | 起停由 systemd **以该用户身份**做；服务只发 `systemctl start/stop`（要配 polkit 或一条**窄**规则）。**推荐**：systemd 本来就在，且它管 cgroup ⇒ 顺带把 §8.2 的资源上限那条也解决了 |
| (乙) 一个 root 的小助手（窄口径、只做几件事） | 多一个要审计的组件 |
| (丙) 给 `deploy` 开 `NOPASSWD` 白名单 | ⚠️ **不推荐**：手册 `23-DEV-VS-DEPLOY.md` §五 自己分析过 —— **白名单里放一个助手能改的东西 = 实际上还是 root**，它的价值只是留痕 |

### 9.3 🔴 注销**必须先给"导出一份"**（不是洁癖，是手册原话）

`01-PROJECT.md` persona 07 的原话：

> **"删除账号"有入口、"导出"没有 ⇒ 这个不对称直接触发信任问题。**

⇒ 注销流程必须是：**先给他一段能拿走的文字**（我们刚做完的 `导出` 正是那个形态）→ **再**二次确认 → **才**删。
⚠️ 而且要说清一件我们已经**还不了**的东西：**他的 API key 在容器里，是他自己填的，我们连看都没看过**
（§5 那条路）⇒ **删了就是真没了，我们还不出来**。这一句必须写在确认页上。

### 9.4 ⚠️ "删了"到底是什么意思（不许说假话）

* `rm -rf` 删掉的是**目录项**，**磁盘块还在**。手册对"真删"的定义是"内容真的不在盘上"（`28-DELETE.md` 的压实）。
* ⇒ 两条路，选一条并**如实说**：(甲) 承认这是**逻辑删除**（不假装安全擦除）·(乙) 走擦除（贵、慢）。
* ⇒ **还有一条必须明说**：**我们（你/调度器）保不保留备份？** 保留 ⇒ **"注销"就是假话**（手册最恨这个）。

### 9.5 判据（可执行 + 负向对照）

| # | 判据 | 对照 |
|---|---|---|
| 1 | 注销**前**：容器在、卷在、用户在、subuid 行在 | ⚠️ **不能省** —— 没有它，"注销后都没了"可能只是**从来没建过** |
| 2 | 注销**后**：11.1 那**六处**逐个查，全没了；`getent passwd hupo-a` 空；`/etc/subuid` 里没有那一行 | —— |
| 3 | 🔴 **再登录同一手机号 ⇒ 是一台全新的空容器**（不是回到旧数据） | 对照：注销前同一手机号登录 ⇒ 看得到旧数据 |
| 4 | 注销前**导出拿到了东西** | 对照：空账户导出 ⇒ 给的是那句实话，不是一个空框 |

### 9.6 要主人定的两条

1. **注销要不要冷静期**（手册的删除语义是"删掉进回收站 30 天、可恢复"）—— 我建议**要**（比如 7 天），
   否则一次手滑 = 用户全部数据没了；
2. **11.2 走哪条路**（甲 systemd 模板单元 / 乙 root 小助手 / 丙 白名单）—— 我建议**甲**，
   它顺带把 §8.2 的资源上限也解决掉。

## 十二、⚠️ **两把 key 不许混**（主人 2026-09-21 问出来的）

### 12.1 容器起来的顺序（照主人说的）

```
① 容器起来 —— 是个**空壳**（没有 key、没有用户数据）
② 里面那个**服务先等**（它就是个"配置入口"，还不干正事）
③ 用户在网页上填**自己的** key ⇒ 中心当**管道**送进那个入口
④ 入口把 key 放到该在的地方 ⇒ **这才启动真正那套服务**
⑤ 用户开始聊
```

⇒ 这一步解决了"**空壳先跑、有 key 才干活**"，不需要在镜像里预置任何人的 key。

### 12.2 一个仍然要主人选的（同一个问题的两种做法）

| | 简单：key 放在 agent 读得到的地方 | 稳一点：key 放 agent 读不到的地方，agent 经**本地代理**用它 |
|---|---|---|
| 代价 | 无额外东西 | 多一个小代理 + 一条本地口 |
| 风险 | **agent 被注入时能把用户的 key 读出来发走**（那是用户的钱） | agent 拿不到明文，照样能调模型 |
| 依据 | —— | userns 的 root 有 `CAP_DAC_OVERRIDE`：**agent 若是 root，任何权限位都拦不住它读** ⇒ 要拦就得让 agent 不是 root + key 在它范围外 |

### 12.3 DSH 自己怎么做的（2026-09-21 去它安装树里查证过）

主人问过：*"DeepSeek Harness 是怎么解决'服务能拿到 key 但 agent 看不到明文'的？"* ⇒ **答案在 `39-PERMISSIONS.md` §六**，这里只留结论：

* DSH 做的是**四件**：配置里存**引用名**（`credentialRef`）、**到用时才 `resolve`**（在 provider 内部）、
  `describe` **只回 `{configured, writable}` 不回值**、文件 **`0600` + 启动时拒绝**（"readable beyond its owner"）。
* 🔴 **但"agent 看不见"这一半它没做**：工具层**零处**提到凭据文件；沙箱是 `readOnly: ["/"]` —— **整个文件系统可读，只是不可写**；
  同 uid 的属主**读得到**自己的 `0600`。⇒ 根因是 **DSH 里 agent 与 harness 同 uid**，它的前提是"agent 可信"。
* ⇒ **多租户里那个前提不成立**（agent 伺候的是别人）⇒ 所以 §12.2 右边那一列（**代理 + uid 边界**）**不是"更讲究的做法"，是必需品**。
* ✅ 盒内那条边界的判据（uid 1000 读 `creds.yaml` ⇒ **`Permission denied`，不是 `No such file`**）**已在真容器里实测通过**，见 `39-PERMISSIONS.md` §5.6。
