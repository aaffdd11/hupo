## 一、A：**上下文有界**（会话太长就翻一页）

**判据是"上一轮真的用了多少"**（上游回来的 usage），不是文件大小那种近似：

```
一轮里 `assistant/message` 带的 usage
  ⇒ promptTokensOf() = uncachedInput + cacheRead        ← 这一轮的上下文有多大
  ⇒ 超过 SESSION_ROTATE_PROMPT_TOKENS（**12 万**）
  ⇒ 下一次开口**之前**：① 卸掉这一条 agent  ② 会话映射指到下一条新的
     （`main` → `main.1` → `main.2` …；**旧的那条文件一个字节都不动**）
```

* **"接得上"靠原来的那套**：新实例第一次投递时照样把那段时间线（最近 40 句）喂回去
  —— 与"重启之后接着聊"走的是同一条路（`Session.deliver` 的 `needsRecap`）。
* 🔴 **重启之后也要认得出"这一间已经很大了"**：`#promptTokens` 是内存里的 ⇒ 一重启就归零，
  而会话没变小。⇒ 加了一步 `#seedPromptTokensOnce()`：从那条日志上**最后一条 `turn/usage`**
  把上一轮的用量读回来（一个进程只读一次）。⚠️ 那一笔是**一轮里几次调用的合计** ⇒ 会**偏大**
  ⇒ 只会**更早**翻页，不会更晚（另一个方向才是"该翻没翻、他还是慢"）。
* 🔴 **失败不许一声不响**：翻页没成 ⇒ 记进 `#lastError` ＋ **冷却 5 分钟**再试
  （不然每一轮都去撞同一件坏事）。
* **留痕**：`tenant/audit.log` 一行 `session-rotate`（哪一间、上一轮多大、从哪条换到哪条）。
  ⚠️ **它不上屏**：翻页这事**不打扰他**（他是按"它怎么突然不记得了"事后才可能问到，
  那一行就是答案）。

### 那一处"换名字"的规矩（`rotateSessionFor`）

| 规矩 | 为什么 |
|---|---|
| 新 id = 旧的**第几页加一**（`x.1` → `x.2`；没有那一段 ⇒ `x` → `x.1`） | 🔴 拿一个**盘上已有**的 id 去开，DSH 会**接着那条旧的** —— 那不是翻页，是原地打转 |
| **不许撞上别间正在用的 id** | 撞了 = 两间的话并进一条对话 |
| **旧的那条原样留着** | 它是档（要查、要回都在），不是垃圾 |
| 调用方**先卸 agent 再换映射**（`AgentRuntime.rotateSession()` 把两步包好了） | 只换映射 ⇒ 那条老进程还在往旧会话里写 |

## 二、B：**把 agent 提前拉起来**（省掉那 3.2 秒）

`Dispatcher.setFocus()` 里多一下：**他打开哪一间，就把那一间的 agent 预热起来**
（`Session.warmAgent()` → `agent.start()`）。

* 只**起进程**：不投话、不动时间线、**不花模型的钱**；
* **一声不响**：起不来什么都不说（他真开口那一下会照旧如实说）；
* 已经在跑的（`ready`）⇒ 直接返回（`start()` 本来就幂等）；
* ⚠️ 它会占进程池一格（上限 4）—— 池子那套淘汰规则照旧（只淘汰空闲的、先收口再卸）。
