# 42 · 开空间要**能被用户看见进度**

> 主人 2026-09-21：*"创建 docker 空间要能够对用户展示进度。"*

## 一、🔴 先说清楚"进度"在这里是什么意思

项目有一条**硬规矩**：**不许假进度**（`38` §8.3 点名过 —— 没有百分比、没有"看着在动、
其实不知道到哪"）。主人要"看得见进度"，而这条规矩**不冲突**：

> **进度 = 把服务端真的知道的那几件事，如实摆给他看。**

所以我们**没有**做进度条、**一个百分号都没有**（判据在 `space_test.dart` 里，专门扫这个）。

## 二、那三步（**每一条都是真事实**）

| 步 | 名字 | 服务端凭什么知道 | 界面上那句话 |
|---|---|---|---|
| 1 | `assigned` | 租户表里有他（`tenantOf(userId)`） | 给你留好一台，只属于你 |
| 2 | `starting` | **那一台连上来了没有**（`channel.hasTunnel()` 真的知道） | 把它开起来 |
| 3 | `ready` | 同上（语义上是"可以用"） | 马上就好 |

界面：`✓ 做完了` / `… 正在做` / `· 还没轮到` —— **三个符号就够，没有数字**。

⚠️ **不给百分比的理由**：我们**不知道**"还要多久"（那取决于容器什么时候连上来）。
编一个数字就是"看着在动、其实不知道到哪"，**比诚实的一句更坏**。

## 三、顺手修掉的一条**安全相关**的判定

`SpaceInfo.fromJson` 原来把**认不出的 `state`** 当成 `ready`：

```dart
state: state == 'preparing' ? 'preparing' : 'ready',   // ❌ 别的一律当就绪
```

⇒ 新加的 `queued` / `starting` 会被当成**就绪** ⇒ **把人送进一个还没准备好的世界**。

改成**两条不同的路**（新的判据在 `space_test.dart`）：

| 情况 | 结果 | 为什么 |
|---|---|---|
| **缺 `state`**（老服务端） | **就绪** | 兼容那条纪律：不许把老用户挡在门外 |
| **给了 `state` 但不认识** | **不就绪** | 把人送进没准备好的世界更坏 |

## 四、还有一件**如实说**的

池子只有两台（`hupo-a`/`hupo-b`）⇒ 第 3 个号**没分到**。那不是"正在开"：

* 服务端回 `state: 'queued'`（**不是** `preparing`）；
* 界面说的是 **"前面还有人，得等一下：我们这边地方有限。"**

⚠️ 要放更多人 ⇒ **先把池子做大**（`scripts/create-tenant-pool.sh` 里加用户）。
这一条与 `41-SPECIAL-CODE.md` §四 是同一件事。

## 七、🔴 第一次真用就卡住了：`hupo-b` 那条隧道**从来没连上**（2026-09-21）

主人报"已经非常久了" ⇒ 上后台一查：

| 人 | 读数 | 判断 |
|---|---|---|
| `owner` | `local` | 正常 |
| `u1`（→ `hupo-a`） | `ready`，三步全 ✓ | 正常 |
| 🔴 `u2`（→ `hupo-b`） | **`starting`**，卡在第二步 | **他那台的隧道一直没连上** |

**两台容器都是 `Up`** ⇒ 不是容器死了，是**容器连不出来**。

### 7.1 根因：**改了模板，已落盘的那份没跟着改**

我之前把通道从"**一个文件**"改成"**一个目录**"（§…"套接字 inode"那条），
但**只改了 `hupo-a` 那一个单元文件**（用手敲的 `sed`）。
⇒ `hupo-b` 的单元还挂着**旧的 `-v` 形式**（挂文件）⇒ 宿主重启换 inode 之后
**永远连不上** —— 而**单元自己不报错**（`ExecStartPre` 只是在等一个不会出现的套接字，
容器照常 `Up`）。

🔴 **更根本的那个**：池子脚本原来是"**单元文件已存在就跳过**" ⇒
**模板改了、已经落盘的那份永远不会更新**。这类缺陷的表现就是
"**某一台看着好好的、其实连不上**"，而且**没有任何东西会响**。

### 7.2 改法（脚本层面，不是手敲）

`scripts/create-tenant-pool.sh` 改成：

* **每次都按模板重写**单元（内容一样 = 幂等；不一样 = 它该更新了）；
* 重写前留一份 `.bak`，**比一下**：变了就 `daemon-reload` + `rm -f` 旧容器 + **重启那一台**
  （不然跑着的还是旧的）。

### 7.3 判据（改完实测）

| # | 判据 | 读数 |
|---|---|---|
| 1 | 跑一次脚本，**两台都报"单元变了"** | ✅ 说明"按模板核对"这条路真的在起作用（不是只认 hupo-a） |
| 2 | 两台容器 | ✅ `Up` |
| 3 | **两条隧道** | ✅ `✓ hupo-a 的隧道通了` · `✓ hupo-b 的隧道通了` |
| 4 | 🔴 `u2` 的 `space` | ✅ **`ready`，三步全 ✓**（原来卡在 `starting`） |
| 5 | **负向对照**：`u1` 没有因此被弄坏 | ✅ 仍然 `ready` |

⚠️ **教训**：**手敲的 `sed` 修不了第二台** —— 模板改了要改**模板**，
而且要让"已经落盘的那些"**能被核对出来**（"存在就跳过"就是没有核对）。

## 八、🔴 主人"一登录就看见一句吓人的话"（2026-09-21）

主人报：*"进去以后，它说，你刚才说的那条我还没做好"* —— 而**他刚登录、什么都没说**。

### 8.1 查到的是哪一条

他那个号绑在 `owner` 上 ⇒ 直接进本机那份。那份时间线末尾：

```
84-86  message/*  你好，我是助手……
87     notice  kind=crash  text="刚才出了点事，我已经重来了"
```

⇒ 是**崩溃那一条通知**，不是"他没做完主人的事"。

### 8.2 为什么会出现（**是我的锅**）

我修 bug / 部署时**反复硬重启**（有几次还是被我自己弄挂的）⇒ `boot.uncleanLastRun = true`
⇒ 下一次开机就写了那条 —— **而当时并没有任何没收口的话**（`reconciled.total === 0`）。

🔴 **触发条件原来只看了"上次没善终"，没看"到底有没有事情被耽误"**：

```js
if (boot.uncleanLastRun && reconciled.told === 0) { ... }   // ❌ 无事也报
```

这违反项目自己的 **R1.2「通知疲劳」**：**没有被打断的事，就不该打扰人。**

### 8.3 改法

```js
if (boot.uncleanLastRun && reconciled.told === 0 && reconciled.total > 0) { ... }
```

* **真的打断了**（`total > 0`）时：对账那一路本来就会说（`told > 0`），
  这一条只在"有东西没收口、但对账没来得及说"时**补位**；
* **什么都没在飞**时：**一声不吭**（原来那句会让用户以为"是自己做的事没被做完"）。

✅ 改完**先在隔离目录跑过**（`npm test` 546 全绿 + 一次真启动），再重启线上。

### 8.4 ⚠️ 另一件要记住的（同一个根）

那句话**读起来**像"我没做好你的事"，因为失败分类器**今天不存在**
（`notice.js` `FAILED_LINES` 里写着：*"上游不通 / OOM 两个都认不出来"*）⇒
认不出来只能兜底成"这件事它没做完"。

⇒ 而**用户最可能遇到的那一类恰恰是"上游不通"** —— 比如 **他还没填钥匙**
（`space.hasKey === false` 时，模型那条路**真的不通**）。分类器落地之后，
那句话才会真的是人话。**这条仍然欠着**（不小，单独立一项）。
