## 三、设计：**墓碑 + 保留编号的压实**

⚠️ 两个不变量夹着这件事：**N22**（编号 = 已落盘最大 + 1，**只增不减**；一条可见时间线 = 一条日志）
与"**真删要真的不在盘上**"。

⇒ 取法（两段，各解决一半）：

| 段 | 做什么 | 为什么这样 |
|---|---|---|
| **删掉**（进回收站） | 落一条**墓碑**事件 `turn/deleted {messageIds}`（**取号、落盘**），客户端据此把它**藏起来** | 不挖洞 ⇒ N22 不受影响；内容**还在盘上**，所以 30 天内能恢复 |
| **真删**（到期或手动） | **压实**：把这些事件**逐条换成最小占位**，**保留各自的 `seq`**（占位里**不留 id、不留内容**） | 内容**真的不在盘上**了；而**号一个不跳**（客户端 `sinceSeq` 补发逻辑不受影响） |

⇒ 恢复 = 落一条 `turn/restored {messageIds}`；两段都**只追加**，
除了「真删」那一次**原子重写**（见 §9.1）之外**永远不原地改日志行**。

## 三·补 🔴 实测更正：**键不是「轮号」，是 `messageId`**（2026-09-21）

写服务端时核了真日志（`data/main.jsonl`，78 条），结果是：

```
落盘的字段：user/echo → messageId · message/start|text|end → messageId
            ⚠️ **没有 turn**（只有 task/mutated 有，而它只在"动过东西"时才落）
message/start.re → **一直是 []**（预留字段，从没填过）
```

⇒ **"按轮删"在服务端无从下手**：轮号是**瞬态**的（`message/status` / `step/*` 上的），
只有正在跑的那一轮才有，**盘上留不下**。

⇒ 改口径（**只改键，不改已拍板的语义**）：

| | 原来说的 | 改成 |
|---|---|---|
| 删的单位 | 一轮（`turn`） | **一轮**（不变） |
| 线上用什么键 | `{turn}` | **`{messageIds:[...]}`** —— 一轮 = **一条用户的话 + 它的回答**，由**客户端**给出这两个 id |
| 谁来做分组 | 服务端猜 | **客户端**（它本来就知道哪两条画成一次问答；且缓存那一屏与实时走**同一条渲染路径**） |

⚠️ 为什么这样最好：`messageId` **从第一条事件就有** ⇒ **连存量的 78 条也删得掉**，
不用数据迁移、不用改既有事件的字段（协议冻结那条也得住）。

📌 **顺带记一笔（小、以后做）**：`message/start.re` 是**预留的回跳指针**（X2/N23 要求"字段现在就留"），
把它填上（`re:[用户那条的 messageId]`）以后**服务端自己就能分组**，不再依赖客户端。
**这一件不做**，明记在这里。

## 四、"删干净"的定义（**这一节是这一件的核心**）

清单**必须从 §4.7 状态清单推出来**，不是手写几句话 —— 手写的一定漏，
而漏一项 = 屏幕上说"删掉了"却没删干净（**说假话**）。

| §4.7 那一项 | 删得掉吗 | 怎么删 |
|---|---|---|
| 可见时间线（`data/main.jsonl`） | ✅ **真删** | 「真删」那段压实掉内容 |
| `$DSH_HOME/sessions/`（**记忆本体**） | ⚠️ **做不到按轮抽掉** | 见 §五 —— **必须写进清单** |
| `$DSH_HOME/storages/`（投影/检查点） | ⚠️ 同上 | 同上 |
| **客户端本机缓存**（`timeline_store` 那一屏 + `draft_store` 草稿） | ✅ 要删 | ⚠️ 见下 |
| `.credentials.yaml` | ❌ **不属用户内容** | 不在清单里（列出来反而是噪音） |

### 🔴 v2 独有的一条（手册没写到，但它是这一件最容易做错的地方）

**服务端删干净了，客户端本机还留着一屏缓存** ⇒ 屏幕会**继续显示"已经删掉的话"**。
这正是本仓库反复栽的"页面在说假话"。
⇒ **本机那份必须跟着清**，而且**清完之后屏幕上不许再出现那一轮的任何字**（有闸）。

## 五、⚠️ 诚实的边界：**记忆那一层做不到按轮删**

实测（`07-TIMEOUT.md` §6.6 / `prune.js`）：`$DSH_HOME/sessions/` 是**按会话整份**存的
（`sessions/<项目>-<组>/<一条记录>/session.v3.jsonl.zstd`），**一轮的话进了那份记录之后没法单独抽出来**。

⇒ 三条路，我选 ②：

| # | 做法 | 为什么不行 / 行 |
|---|---|---|
| ① | 假装删掉了 | ❌ **说假话**（屏幕上说删了，它还记得） |
| ② | **如实写进清单**："可见的那一轮已经删掉了；**它在记忆里的那一段，要等这段对话的记忆被重建才会消失**" + 给一个**更彻底的可选动作**："**连整段记忆一起清掉**"（那样这段对话它就**全不记得**了） | ✅ 与 N10（沉默优于编造）+ "不许说假话"一致。而且**清单本来就要列"会删什么"**，那"这一处删不掉"也**必须列出来** |
| ③ | 去重写 DSH 的会话记录文件 | ❌ 那是别人的格式；重写等于替 DSH 实现"按轮删记忆"，风险与收益不成比例 |

⚠️ **② 的那句话必须出现在屏幕上**（清单里），否则这一件就又变成"页面在说假话"。

## 六、切法（两半，各自能独立验收）

| 半 | 做什么 | 判据 |
|---|---|---|
| **服务端** | `turn/deleted` / `turn/restored` / `turn/purged` 三种事件 + 回收站（30 天、到期、提前一周告）+ **清单**（从状态清单推）+ 压实 | 真 `kill -9` 之后**重启还记得**墓碑；**压实后盘上 grep 不到那一段的任何字**，且**号一个不跳**（`seq` 连号断言） |
| **客户端** | 气泡长按 → 删掉（**先弹清单**）+ 回收站页（恢复 / 彻底删）+ **本机缓存与草稿跟着清** | **删完之后屏幕上不许再出现那一轮的任何字**（含冷启动那一屏）· 四档/可访问性既有闸全绿 |

⚠️ **两半合成一件收尾**（§5.0 那四件）。**别在中间部署/推**：
服务端那半单独上线对用户**没有任何可见变化**（客户端还没接），推了只会让两边版本错开。

* **注销账号立刻清空**：v2 没有"注销账号"这条路（只有退出登录）⇒ 等真有账号注销时再说。

## 八、线上协议（**冻结，两半照这个对齐**）

### 8.1 事件（**三种都取号、都落盘**——不然重启就忘了谁被删过）

```jsonc
// ⚠️ 键是 messageIds（见 §三·补）：一轮 = 一条用户的话 + 它的回答
{"type":"turn/deleted", "messageIds":["u_x","m_y"], "at":1758400000000}
{"type":"turn/restored","messageIds":["u_x","m_y"]}
{"type":"turn/purged",  "messageIds":["u_x","m_y"]}
```

⚠️ 它们**不改既有字段的语义**（新事件、新字段，不动 `message/*` 上任何已上线的字段）。
⚠️ 事件名沿用 `turn/*`（业主已经认过这个叫法），但**载荷里是 `messageIds`** —— 别把名字当键用。

### 8.2 HTTP（都要令牌，`Authorization: Bearer`）

| 方法 | 路径 | 请求 | 回来 |
|---|---|---|---|
| `POST` | `/api/trash/plan` | `{messageIds:[...]}` | `{messageIds, items:[{what,where,verdict:"delete"|"cannot",note}], purgeAt, ttlDays}` ← **删前那份清单** |
| `POST` | `/api/trash/remove` | `{messageIds:[...], confirm:true}` | `{ok:true, messageIds, purgeAt}` |
| `GET` | `/api/trash` | —— | `{items:[{messageIds,at,purgeAt,preview}]}` |
| `POST` | `/api/trash/restore` | `{messageIds:[...]}` | `{ok:true}` |
| `POST` | `/api/trash/purge` | `{messageIds:[...], confirm:true}` | `{ok:true, freedBytes}` |

⚠️ `confirm:true` 是**必须的**（少它就 400）：删是破坏性动作，**不许一个手滑的请求就能触发**。
⚠️ `/api/trash/plan` **不给 `confirm` 也能调**——它是**只读**的（"先看清单"这一步不许有门槛）。

### 8.3 客户端收到这三种事件要做什么

| 事件 | 客户端 |
|---|---|
| `turn/deleted` | 把**这几个 `messageId` 的条目藏起来**（**屏幕上不许再出现它们的一个字**）+ **清本机缓存里那一屏与相关草稿**；**不销毁**（恢复要能立刻回来） |
| `turn/restored` | 取消隐藏。⚠️ **服务端会紧接着把这一轮的内容重发一遍（新号、`at` 保留原值）** —— 理由见下 |
| `turn/purged` | 把这几个 `messageId` 的内容**从内存里丢掉**（服务端已压实，永远不会再补发） |

⚠️ **隐藏而不是销毁**是有意的：恢复要**立刻**、且不许再要一次网络（网络断了也得能恢复）。

### 8.4 ⚠️ 恢复为什么要重发（**两半交界处实测出来的缝**）

客户端"删掉"时按 §四**把本机缓存里那几条清了**；而它重连只补"比自己 `lastSeq` 更新的"
⇒ **冷启动之后再恢复**，光靠"盘上还留着"**回不来**（那些号比它的游标旧，补发窗口不含它们）。

⇒ 服务端 `restore` 的三步：① 落 `turn/restored` ② **把内容事件重新追加一遍（新号）** ③ 移出回收站。

⚠️ **代价必须两边一起认**：同一个 `messageId` 的内容在日志里会有**两份**（旧号 + 新号）。
⇒ **客户端必须按 `(messageId, block, seqInBlock)` 去重**（`seqInBlock` 是事件上本来就有的字段），
否则同一段字会被印两遍。**这条闸在客户端那一侧**（`test/unit`：重发不翻倍 + 冷启动恢复只出现一次）。
