## 一、为什么先建它

手册里 **S1 + S9** 被列为"今天就该修"，理由是**它是唯一会永久丢数据的根**。
而既然代码是**全新建立**，这四件就不是"去旧代码里改"，而是"**在新代码里从一开始就对**"——

⇒ **先建这条管道本身**。别的模块（协议层、WS、agent 运行时、界面）**全都坐在它上面**：
如果落盘语义错了，上面写多少都是建在流沙上。

| 手册条目 | 在新实现里怎么落 |
|---|---|
| **S1** 落盘失败上抛 + 落盘成功才推 | `store.append` 抛；`timeline.emit` 先落盘后推 |
| **S9** 上抛之后**谁接** | `process-guard.js`（进程级兜底 + 瞬态通知） |
| **S8** 瞬态事件不占号 | `timeline.emitTransient`：不取号、不落盘 |
| **P-l 甲** 一条可见时间线 = 一条日志 | `store.pathFor(timelineId)`：一条线一个 `.jsonl` |
| **P-g** "不占号" = "不上时间线" | 瞬态事件不产生 `TimelineItem`，也不进日志 |
| **N22** 编号只增不减、磁盘无空洞 | 单一取号点 + 失败退号 + `verifyMonotonic` |
| **N19** 挂起必有收尾 | `Timeline` 强制"同一时刻最多一条未收口" |
| **协议 R11** 每事件有时间戳 | `emit`/`emitTransient` 统一盖 `at` |

## 二、四个模块与它们的契约

### 2.1 `store.js` —— 落盘

| 契约 | 说明 |
|---|---|
| **失败必须上抛** | 绝不 `catch {}`。这是**整个地基存在的理由** |
| **append-only** | 一条一行 JSON；不原地改、不重写文件 |
| **fsync 后才算落盘** | 可用 `fsync: false` 换速度，但那就只是"写进页缓存" |
| **先落盘、后推** | 本模块只负责"落"，"推"在 `timeline.js` —— **顺序由调用方保证** |
| **坏记录要抛** | 默默跳过等于隐瞒数据损坏 |

`close` 失败**不许掩盖**写失败的原因——掩盖了，调用方会以为是"关文件失败"，
从而错过"盘满了"这个事实。这条有专门的测试。

### 2.2 `timeline.js` —— 取号与推送的唯一入口

```
┌ 事件种类 ┬ 取号 ┬ 落盘 ┬ 上时间线 ┐
│ 持久事件 │  ✅  │  ✅  │    ✅    │
│ 控制帧   │  ❌  │  ❌  │    ❌    │
│ UI 状态  │  ❌  │  ❌  │    ❌    │
└──────────┴─────┴─────┴──────────┘
```

- **只有一个取号函数**（`#nextSeq`）。全模块再无第二处 `++seq`。
  旧实现有三处（`emit` / `emitTransient` / `restore`），那是矛盾的来源。
- **落盘失败 ⇒ 退号**：盘上没留下东西，号就不该前进；
  否则下一个事件在盘上就是跳号的（违反 N22）。
- **订阅者抛错不拖垮时间线，但必须报出来**（`onSubscriberError`）——
  静默吞掉就是手册反复骂的"系统什么都不说"。

### 2.3 `message-writer.js` —— 一条消息

- `start → text* → end`；没 `start` 就 `chunk` 会自动补
- ⚠️ **`chunk()` 先查 `ended`，越界直接抛**。
  旧实现（`conversation.js:204`）不查 ⇒ **谁攥着旧 writer，谁就能把内容写回已收口的消息里**，
  用户看到"时间倒流"。这就是事故"消息不许交叉"的成因。
- **`end()` 幂等**；**`end` 带最终来源**（协议 R8：覆盖 `start` 上带的）

### 2.4 `process-guard.js` —— 出事谁接

| 层 | 做什么 |
|---|---|
| 1 调用点 | **不逐处 try**（旧实现 18 个 `emit` 调用点，逐处 try 必漏） |
| 2 `emit` | 落盘失败就抛，订阅者一条都不推（在 `timeline.js`） |
| 3 **进程级** | 接住 → **用瞬态通道**说一句人话 → **有界退出** |

> ⚠️ **为什么必须用瞬态通道**：它**不写盘**，所以**盘满时它仍然发得出去**。
> 用普通通道报"盘满了"，那条消息自己就写不进去。

另含 **崩溃环判定**（手册 §11.1）：窗口内启动数 ≥ 阈值 **且** 上次有 OOM ⇒ 降级；
降级期间**不续做、只服务对话**，且**必须对用户说那句话**——静默降级等于骗人。

## 三、⚠️ 建的过程中抓到的第一个 bug（值得记）

写测试时，`start()` 的落盘失败用例**当场抓到一个真 bug**：

```
start() 原写法：
  beginMessage(this)      ← 先把"未收口"登记下去
  emit(message/start)     ← 再落盘；这里抛了
  #started = true
```

⇒ 落盘失败后，时间线上**永久留着一个"未收口"的幽灵**，
**之后每一条消息都开不了口**——而现场看起来只是"**它不理我了**"。

**它的形状和手册里那个 `turns` 键的 bug 一模一样**：
**状态先写下去，失败时忘了收回来**。
⇒ 修法：`emit` 失败时**撤销登记**（`endMessage(this)`）。

> 这条正好验证了手册 `07-APPENDIX.md` §一 的说法：
> N7「**不拿不真实的状态污染记录**」——写进记录前先问"**这条一直是假的怎么办**"。
