## 一、这一批在防什么

手册 `05-DECISIONS.md` 把威胁写得很清楚，**不是"它干一次坏事"**（那能收拾）：

> 它读到一段看不见的网页内容 → 被诱导写进自己的配置 →
> **从今往后每轮开机都读那一段** → 而表面上一切正常。

⇒ 所以判据不是"它有没有权限"，而是：**"还有没有一条路径，能让它的写入变成下次开机自动读的东西"**（P1.2）。
只要还剩一条，就没摘够。

## 二、P1：开机完整性清单

`integrity.js` 把"开机自动读"的东西分三类列出来，**每条都要写清为什么**：

| 类 | 例子 | 为什么算 |
|---|---|---|
| ① **会被执行的** | `v2/services/core/src/**`、`scripts/**` | 开机就执行 / 主人会手动跑 |
| ② **开机自动喂给 agent 的** | `hupo-persona.yml`、`AGENTS.md`、`~/.dsh/profiles/**`、`settings.yaml` | 每开一个 agent 喂一遍；`cordis.patch.yml` 改一行就改掉它的自我认知 |
| ③ **判据本身** | `docs/handbook/**` | 能随手改判据，任何闸都白设 |

`~/.dsh/profiles/sdk/cordis.patch.yml` 是这一类里最要紧的一个：
**它就是"agent 每轮开机读到的那段东西"**。

### 2.1 三种状态，三种说法

| 状态 | 怎么做 | 为什么 |
|---|---|---|
| `ok` | 起 | —— |
| `tampered`（`strict` 对不上） | **拒绝启动**（`serve.js` 走 `problems` → `exit 2`） | 手册 P1.4 明写"拒绝启动 + 报警" |
| `absent`（清单不在） | **起**，但**大声说"这条保护还没启用"** | 悄悄过去 = "看起来有闸、其实没有"。**那比不设闸更坏** |

⚠️ `absent` 那一条是**刻意**的：本机现在就是这个状态（清单要 root 才能建，见 §六）。
每次开机的第一行和横幅都会说出来：

```
  ⚠️ 开机清单还没建（/etc/hupo/integrity.json 不在）⇒ **P1 那条保护还没启用**。
  完整性   ⚠️ **还没启用**（清单不在，见上面那条提示）
```

### 2.2 两个容易做错的地方

**① 清单路径写死，不走环境变量。**
服务是**助手自己重启**的（`scripts/restart-core.sh`）。闸要是能靠环境变量关掉，
助手只要 `HUPO_INTEGRITY= scripts/restart-core.sh` 就把它整个绕了 —— **那就等于给它一个关闸开关**。
⇒ 路径写死 `/etc/hupo/integrity.json`；`--baseline` 那种开关只属于**主人手上的那个工具**，
服务本体不认。

**② `mode` 住在清单文件里，不在代码里。**
`strict`（拦）还是 `report`（只报）写在**那份 root 所有的清单**里
⇒ 助手**改不了自己那一档**。有一条测试专门证明这件事成立。
`report` 用在"**本来就该变**的安全数据"上（口令、撤销表、DSH 的 storages）：
换口令是主人的正常动作，不该因此起不来——但**要知道它动过**。

**③ 空清单不是"全都对"，是"什么都没查"。** ⇒ 算 `tampered`。
（一份空文件就能绕过去的闸，等于没有。）

## 三、P2：两把工具

```
助手产出：proposals/xxx.patch          ← 主人看的就是**这一个文件**
主人跑：  scripts/apply-change.sh proposals/xxx.patch
          sudo node scripts/verify-integrity.mjs --build     ← 认下新基线
          scripts/restart-core.sh                            ← 等它说完话再重启
出事时：  scripts/rollback.sh            ← 一句话，不需要助手参与
```

| 纪律 | 落在哪 |
|---|---|
| 补丁**只能**从 `proposals/` 来（`realpath` 判断，软链/`..` 都绕不过） | `apply-change.sh` |
| 工作树必须干净（否则"回退一次"≠"退回这一步"），`--allow-dirty` 是主人显式签字 | 同上 |
| 先 `git apply --check` 再 apply；check 失败时**什么都没改** | 同上 |
| **留下一个 commit**（V9），并把补丁本身归档进同一个 commit | 同上 |
| **`rollback.sh` 不读任何助手产出的文件**（P1.5：出问题时助手可能就是出问题的那个） | `rollback.sh` 只信 git |
| **回退用 `git revert`，不是 `HEAD~1`** | 同上 + §13.2 第 3 条的闸 |

### 3.1 一个"判断相反"的地方（**apply 不重启，rollback 才重启**）

手册 `04-ROADMAP.md` 那一行写的是"先 `git apply` 再 `commit` 再 **restart**"。
但 `06-OPERATIONS.md` **§8.3** 说：**不要直接重启**——那会把正在说话的那一轮连同回答一起杀掉，
用户看到话说一半没了。

⇒ 这一批取的是 §8.3：**`apply-change.sh` 不重启**，只把"接下来做什么"打印成三行，由主人自己决定。
而 `rollback.sh` **可以**重启：回退几乎总是"服务已经坏了要救回来"，
坏掉的服务没有"正在说的话"可保（§8.1 的顺序也是 revert → 重启 → 确认存活）。

**这两条互相矛盾的手册条目，§8.3 那条更具体、理由更硬** ⇒ 按它做，并把偏差记在这里。

## 六、⚠️ 本机做不到的（**必须由主人在生产机上做一次**）

| # | 事 | 为什么本机做不到 |
|---|---|---|
| 1 | **建那份清单**（`sudo node scripts/verify-integrity.mjs --build`） | 清单**必须 root 所有**（`root:root 0444`），否则助手自己就能改它——那这道闸就没有意义。而本机 `sudo` **要密码**（`AGENTS.md` §一），**而那正是 P2 安全性的来源** |
| 2 | 报警的**推送**渠道 | v2 现在没有通知渠道（那是批 3「系统通知」）。今天"报警"=`拒绝启动` + 日志一行 + 横幅一行 + 脚本非 0 退出码 |

⇒ **在主人跑那一条 `sudo` 之前，"P1 的保护"是没启用的**（服务照跑，横幅每次都这么说）。
**这一条不许说成"P1 已落地"**——机制到位了，**保护还没启用**。
