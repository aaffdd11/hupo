## 一、这一批在防什么

手册 `05-DECISIONS.md` 把威胁写得很清楚，**不是"它干一次坏事"**（那能收拾）：

> 它读到一段看不见的网页内容 → 被诱导写进自己的配置 →
> **从今往后每轮开机都读那一段** → 而表面上一切正常。

⇒ 所以判据不是"它有没有权限"，而是：**"还有没有一条路径，能让它的写入变成下次开机自动读的东西"**（P1.2）。
只要还剩一条，就没摘够。

## 二、P1：开机完整性清单

`integrity.js` 把"开机自动读"的东西分三类列出来，**每条都要写清为什么**：

| 类 | 例子 | 为什么算 | 今天这一档 |
|---|---|---|---|
| ① **会被执行的** | `v2/services/core/src/**`、`scripts/**` | 开机就执行 / 主人会手动跑 | ⚠️ **`report`**（见下） |
| ② **开机自动喂给 agent 的** | `hupo-persona.yml`、`AGENTS.md`、`~/.dsh/profiles/*/cordis.yml` + `cordis.patch.yml` | 每开一个 agent 喂一遍；`cordis.patch.yml` 改一行就改掉它的自我认知 | **`strict`** |
| ③ **判据本身** | `docs/handbook/**` | 能随手改判据，任何闸都白设 | **`strict`** |

### 2.0 ⚠️ 主人定的那一档（2026-09-21）

**"只挡最危险那几样"**：②③ 是 `strict`（对不上**拒绝启动**），① 是 `report`（**只报不拦**）。

⚠️ **而且 strict 那一档要"精确"，不能"整层"**——否则它会**无故把服务拦在门外**：

| 文件 | 档 | 为什么 |
|---|---|---|
| `~/.dsh/profiles/*/cordis.yml`、`cordis.patch.yml` | **strict** | 它们**就是喂给 agent 的那条指令** |
| `~/.dsh/profiles/*/package.json`、`pnpm-workspace.yaml` | **不扫** | 安装产物：一次正常 `pnpm install` 就会改写它们 |
| `~/.dsh/settings.yaml` | **report** | 运行时会被写（比如它记住"那个提示看过了"） |
| `~/.dsh/.credentials.yaml` | **report** | 里面的令牌**会自己续期** ⇒ 拿它当 strict = 某天开机无故起不来 |
| `~/.dsh/storages/**` | **不在清单里** | 运行时数据（决策 **C1**）：agent 每轮都在写 ⇒ `strict` = 天天拒绝启动；`report` = 每次都响的报警（等于没有报警）。**代价**：这条路没被覆盖（见 §七 第 5 条） |

理由是一个**取舍**，不是"本来就该这样"：开发期代码天天改，
`src/` 要是也 strict，助手每改一行主人就得补一条 `sudo`，否则下次重启服务会拒绝启动。
⇒ **先只报，等收口了再收紧**。

⚠️ **这是一处刻意的让步**：手册 **P1.2** 的判据（"一条路径都不许剩"）
在 `src/` 与 `scripts/` 上**今天没有满足**。
⇒ 有一条测试**把这个状态钉住**（`主人定的那一档…`），
免得下一个人以为它是 strict，从而在别处放松。
⇒ 而且 **`AGENTS.md` 与 `docs/handbook/**` 是 strict**：**助手改这两个文件要主人补一条 `sudo`**
——所以助手**不许把进度数字写在 `AGENTS.md` 里**（那些数字每批都变）。
数字现在只住在 `docs/dev/00-PROGRESS.md`。

`~/.dsh/profiles/sdk/cordis.patch.yml` 是这一类里最要紧的一个：
**它就是"agent 每轮开机读到的那段东西"**。

### 2.1 三种状态，三种说法

| 状态 | 怎么做 | 为什么 |
|---|---|---|
| `ok` | 起 | —— |
| `tampered`（`strict` 对不上） | **拒绝启动**（`serve.js` 走 `problems` → `exit 2`） | 手册 P1.4 明写"拒绝启动 + 报警" |
| `absent`（清单不在） | **起**，但**大声说"这条保护还没启用"** | 悄悄过去 = "看起来有闸、其实没有"。**那比不设闸更坏** |

⚠️ `absent` 那一条是**刻意**的：本机现在就是这个状态（清单要 root 才能建，见 §六）。
每次开机的第一行和横幅都会说出来：

```
  ⚠️ 开机清单还没建（/etc/hupo/integrity.json 不在）⇒ **P1 那条保护还没启用**。
  完整性   ⚠️ **还没启用**（清单不在，见上面那条提示）
```

### 2.2 两个容易做错的地方

**① 清单路径写死，不走环境变量。**
服务是**助手自己重启**的（`scripts/restart-core.sh`）。闸要是能靠环境变量关掉，
助手只要 `HUPO_INTEGRITY= scripts/restart-core.sh` 就把它整个绕了 —— **那就等于给它一个关闸开关**。
⇒ 路径写死 `/etc/hupo/integrity.json`；`--baseline` 那种开关只属于**主人手上的那个工具**，
服务本体不认。

**② `mode` 住在清单文件里，不在代码里。**
`strict`（拦）还是 `report`（只报）写在**那份 root 所有的清单**里
⇒ 助手**改不了自己那一档**。有一条测试专门证明这件事成立。
`report` 用在"**本来就该变**的安全数据"上（口令、撤销表、DSH 的 storages）：
换口令是主人的正常动作，不该因此起不来——但**要知道它动过**。

**③ 空清单不是"全都对"，是"什么都没查"。** ⇒ 算 `tampered`。
（一份空文件就能绕过去的闸，等于没有。）

## 三、P2：两把工具

```
助手产出：proposals/xxx.patch          ← 主人看的就是**这一个文件**
主人跑：  scripts/apply-change.sh proposals/xxx.patch
          sudo node scripts/verify-integrity.mjs --build     ← 认下新基线
          scripts/restart-core.sh                            ← 等它说完话再重启
出事时：  scripts/rollback.sh            ← 一句话，不需要助手参与
```

| 纪律 | 落在哪 |
|---|---|
| 补丁**只能**从 `proposals/` 来（`realpath` 判断，软链/`..` 都绕不过） | `apply-change.sh` |
| 工作树必须干净（否则"回退一次"≠"退回这一步"），`--allow-dirty` 是主人显式签字 | 同上 |
| 先 `git apply --check` 再 apply；check 失败时**什么都没改** | 同上 |
| **留下一个 commit**（V9），并把补丁本身归档进同一个 commit | 同上 |
| **`rollback.sh` 不读任何助手产出的文件**（P1.5：出问题时助手可能就是出问题的那个） | `rollback.sh` 只信 git |
| **回退用 `git revert`，不是 `HEAD~1`** | 同上 + §13.2 第 3 条的闸 |

### 3.1 一个"判断相反"的地方（**apply 不重启，rollback 才重启**）

手册 `04-ROADMAP.md` 那一行写的是"先 `git apply` 再 `commit` 再 **restart**"。
但 `06-OPERATIONS.md` **§8.3** 说：**不要直接重启**——那会把正在说话的那一轮连同回答一起杀掉，
用户看到话说一半没了。

⇒ 这一批取的是 §8.3：**`apply-change.sh` 不重启**，只把"接下来做什么"打印成三行，由主人自己决定。
而 `rollback.sh` **可以**重启：回退几乎总是"服务已经坏了要救回来"，
坏掉的服务没有"正在说的话"可保（§8.1 的顺序也是 revert → 重启 → 确认存活）。

**这两条互相矛盾的手册条目，§8.3 那条更具体、理由更硬** ⇒ 按它做，并把偏差记在这里。

## 八、⚠️⚠️ 2026-09-21 实测：**那条保护漏了整整一类**（已修）

> 这一节记的是**这道闸自己出过的一次静默失效**。它比任何一次"某个文件被改动"都严重：
> **招牌上写着有闸，而其中最要紧的那三条从来没被核对过。**

### 8.1 怎么发现的

批 4 落地后按惯例请主人补一次清单重建（`--build`）。建完打印出来的**覆盖清单**里有这几行：

```
· /root/.dsh/profiles          [strict]  agent 的 profile 与补丁
· /root/.dsh/settings.yaml     [report]
· /root/.dsh/.credentials.yaml [report]
```

⚠️ **`/root`** —— 而这个服务跑在 `deploy` 下，它真正读的是 **`/home/deploy/.dsh/**`**。

### 8.2 根因（两步，各自都很安静）

1. **清单是主人用 `sudo` 建的**，而 `sudo` 下 `os.homedir()` 是 **`/root`**
   ⇒ `protectedPaths()` 把那三条算成了 `/root/.dsh/**`。
2. `/root/.dsh/` 下**一个文件都没有**，而 `buildBaseline()` 对"读不到的文件"是
   **`continue`（静静跳过）** ⇒ **这三条一个条目都没进清单**。

⇒ 于是：**`~/.dsh/profiles/*/cordis*.yml` 这三条最核心的保护（"改它就能改自己每轮读到的东西"）
从来没生效过**，而开机横幅一直写着「完整性 对上了」。

> ⚠️ 为什么 `verifyBaseline()` 抓不到：它是**按清单里已有的条目**核对的。
> **清单里没有的东西，它永远看不见** —— 这正是"看起来有闸、其实没有"那一类。

### 8.3 修法（三处，缺一处就会再犯）

| # | 改什么 | 为什么这一处不可省 |
|---|---|---|
| 1 | **清单按"仓库属主"的 home 算**（`resolveServiceHome()`：`stat(repo).uid` → `/etc/passwd` 取 home）。**不是**按"现在跑这条命令的人" | `sudo` 不改变仓库属主 ⇒ 两边从此算的是同一个 home |
| 2 | **加一次反向查**：`coverageGaps()` —— "声明要保护的路径、盘上有文件、而清单里一个条目都没有"的，有几条 | `verifyBaseline()` 结构上看不见这一类；没有它，第 1 条修好之后**下一个人照样能再漏一次** |
| 3 | **漏掉的算不算拦**：`strict` 的漏 ⇒ **拒绝启动**；`report` 的漏 ⇒ 只提醒。`--build` 建完**当场喊**，有漏就退出码 2 | "写着有闸、其实没在核对"比不设更坏 —— 它让人**以为**被保护着 |

### 8.4 验证（都是真跑过的）

| 验的是什么 | 结果 |
|---|---|
| 重建后的覆盖 | **64 个文件**（原来 58）——多出来的正是 `~/.dsh/profiles/{sdk,web}/{cordis.yml,cordis.patch.yml}` + `settings.yaml` + `.credentials.yaml` |
| 建完立刻核 | ✅ 对上了；**一条都没漏** |
| ⚠️ **strict 会不会误杀**（`dsh` 每次启动都会重写 `cordis.yml`） | 真起一次 `dsh --profile sdk --dump-config`：摘要 **`c300dcf2…` → `c300dcf2…`（一个字节都没变）** ⇒ 这条 strict 是站得住的 |
| 🔴 **真红演练** | 往 `~/.dsh/profiles/sdk/cordis.patch.yml` 追加一行 ⇒ 核对 **1 处会拒绝启动**、开机报告 `problems: 1` 并点名那个文件；还原 ⇒ ✅ 对上 |
| 服务重启 | 横幅 **「完整性 对上了」**（这一次是**真的**"对上了"：64 个文件里包含那三条） |
| 变异验证 | `coverageGaps` 改成永远说"没漏" ⇒ 3 条红；home 改回 `os.homedir()` ⇒ 1 条红 |

### 8.5 留给下一个人的两句
