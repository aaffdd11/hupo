## 二、19.6 秒是怎么花的（`main.jsonl` ＋ `pending.jsonl` ＋ 用量账拼出来的）

```
23:14:01.168  他的话进来（user/echo）
23:14:01.257  work/open  state=waiting      ← 等那个 agent 空出来
23:14:04.498  system/prompt                +3.3s
23:14:04.403  work/open  state=running      +3.2s（等 agent 就绪这一段）
23:14:11.006  notice work-started           +9.8s
23:14:20.786  message/start（第一个字）      +19.6s
23:14:20.794  message/text                  ← 第一次模型调用**到这里才回来**
23:14:20.869  tool/result
23:14:30.529  message/text（第二段）
23:14:30.545  message/end                   +29.4s（这一轮走完）
```

**那 16.4 秒（04.4 → 20.8）是第一次模型调用**。它为什么 16 秒 —— 用量账那两笔说得最清楚：

| 那一轮的两次调用 | 读数 | 说明 |
|---|---|---|
| 第 1 次 | `uncachedInput **480,440**` · `cacheRead 8,960` · `output 953` | 🔴 **这一跳几乎全是"冷写"**：约 **49 万 token 的上下文**要现传 |
| 第 2 次 | `uncachedInput 957` · `cacheRead **490,240**` · `output 588` | 同一条上下文，**吃了缓存** ⇒ 只用 ~10 秒 |

**为什么第 1 次是冷的**：上一轮是 **20:51**（隔了 **2 小时 23 分**）—— 上游的 prompt 缓存早就过期了
（缓存是按前缀命中的，隔久了就作废）。

**为什么上下文有 49 万 token**：主对话那条 DSH 会话
（`owner/main.muh5qpmooajv.1`）压缩后 **2.5 MB**、解开 **8.4 MB / 1679 行**
（261 条 assistant 消息 · 216 次工具调用 · 73 轮）—— 而我们每一轮都 `resume` **同一条会话**
⇒ **整条历史每一轮都重发一遍**。⇒ **聊得越久，第一段字越慢。**

## 三、还有一半是"观感"：**它不是逐字给的**

`message/text`（那一轮就 **2 帧**，正好对应 2 次模型调用）。
⇒ 屏幕上**要么不出、要么一次出一整段**。

⇒ **今天 DSH 那一侧不给增量**，"逐字冒出来"这条路**现在做不了**（不是我们没接，是没有东西可接）。
