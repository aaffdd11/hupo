## 一、主人定的形状（原话）

> 「**浮窗喊一声，时间线留住 + 撤销（浮窗里也能有撤销按钮，但时间线里那条必须有）**」

落成四条**不许破**：

| # | 约束 | 依据 |
|---|---|---|
| 1 | **浮窗是 overlay**：浮在内容上面，**不许挤动下面的东西** | **D4.8**：新增助手消息触发的**高度变化必须 = 0px**——"每说一句每收一句桌面就被抹掉一次"是平板用户的主要放弃点 |
| 2 | **时间线里必须有那一条**（浮窗只是"喊一声"，它会自己消失） | 通知要经得起"**你不在**" |
| 3 | **撤销有两份**：浮窗里一个 + **时间线里必须有** | 破坏性动作的撤销窗口**不能随浮窗一起消失**（N11 + 命中区 ≥44 那条硬闸） |
| 4 | 文案过禁用词闸；**不承诺时间** | D7.1 / D7.2 同一条纪律 |

## 三、✅ 两处已拍板（2026-09-21）

> 两处都是**冲突裁决**，不是实现细节 —— 记下原话，别让下一个人以为可以随手改。

### ① 崩溃那条通知：它**落不了盘**，可你要求"时间线里必须有"

P-k 说进程级兜底那条人话要**走不落盘通道**（盘满时它才发得出去）；而你的约束 2 说**时间线里必须有那一条**。这两个在"盘满"这一种情况下**直接冲突**——那一条**物理上写不进时间线**。

**我提议**（默认满足你那句，只有一种例外，而且例外时**明说**）：

| 投递 | 什么时候用 | 时间线里有吗 |
|---|---|---|
| **持久通知**（落盘，取号） | **默认**。续做、回收站到期、失败分类…… | ✅ 有（浮窗喊一声 + 时间线留一条 + 两处撤销） |
| **瞬态通知**（不落盘） | **只有一种**：写盘本身失败（盘满 / 崩坏环） | ❌ 没有 —— 但那条**必须自己说清**："盘满了，这条我没能写进时间线" |

⇒ **"时间线里必须有"变成"默认必须有"。✅ 主人 2026-09-21 认可这一点**（"例外时就明说"）。
⚠️ 所以 `notice/urgent` **只准用于这一种情形**：写盘本身失败。拿它当"省事的快捷通道"就是破这条裁决。
⚠️ 而且那句话**取实质、不许出现"时间线"**（禁用词）：实际文案是「**盘满了，这条我没能记下来**」。

### ② 上面 §二 那个"职责分开"的口径，你认不认

换一种可能是**更狠的合并**：把"它正在做…"（应声）也搬进通知通道，彻底废掉 `message/status`。
⚠️ 那会**动 ⑰ 刚做完的东西**（四档的第一档就建在 `message/status` 上），我不建议。
⇒ 我的提议是**分工**，不是搬家。**✅ 主人 2026-09-21 认了这个分工。**

⚠️ 落地时的判据（两条都要有闸）：
* **"它正在做"永远只走 `message/status` / `step/*`**（⑰ 那四档就建在上面）；
* **通知只用于三类**：①替你做的决定 ②出事了 ③你不在时发生的事；
* ⇒ 同一个 `(turn, kind)` **不许同时出现**一条 status 和一条通知。

## 五、线上形状（**冻结** —— 两半照这个对齐）

```jsonc
// 持久（取号、落盘）—— 时间线里那一条
{"type":"notice", "kind":"resumed|not-resumed|expiring|crash|failed", "text":"…", "at":1758400000000,
 "undo": {"label":"拿回来", "action":"trash/restore", "messageIds":["u_x","m_y"]}}

// 瞬态（不落盘）—— 只在写盘失败时用
{"type":"notice/urgent", "kind":"disk-full", "text":"盘满了，这条我没能记下来"}   // ⚠️ 不许出现"时间线"（禁用词）
```

* `undo` **可以没有**（续做那条就没有）；有的话，**浮窗与时间线两处都渲染它**（约束 3）。
* **文案由服务端给**（它知道发生了什么），客户端**照抄** —— 和 `28-DELETE.md` 那张清单同一条规矩。
* ⚠️ **限频**：同一 `kind` + 同一主体在短时间内只喊一次（R1.2 的"通知疲劳"）。

### 5.1 五个来源 → 事件（**这是两半的接口**）

| 来源 | `kind` | `text`（人话，服务端给） | `undo` |
|---|---|---|---|
| 续做（D10.1 自动重来） | `resumed` | 「你被打断的那件事，我重新做一遍」⚠️ **不许写成「做了一遍」**：它在**决定那一刻**发，投递失败就没做过 | 无 |
| 续做（只通知不重来） | `not-resumed` | 「那件事可能改过东西，我没有自己做 —— **你看一眼，要不要再做一遍**」⚠️ 后半句**不许丢**（只通知的意义就是让主人自己决定） | 无 |
| 回收站到期前一周 | `expiring` | 「有一条过几天会彻底删掉」 | ✅ `trash/restore` |
| 崩溃 / 报警（P-k · #22） | `crash` | 「刚才出了点事，我已经重来了」 | 无 |
| 失败五类里"只通知"那一类 | `failed` | （按那一类给） | 无 |

⚠️ `text` **一律由服务端给、客户端照抄**（和 `28-DELETE.md` 那张清单同一条规矩）——
文案要进禁用词闸，所以**它必须住在一个能被扫到的地方**（客户端那份表 + 服务端这份表都要）。

## 九、🔴 补一条判据：**首屏那段历史也不许弹浮窗**（2026-09-22 主人报的）

### 9.1 现象（主人的原话）

> *"登录后，出现刚才出了点事，我已经重来了。但是其他手机的并没有出现这段话。"*

### 9.2 查下来是**两边各说各话**

| 谁 | 它认为 | 结果 |
|---|---|---|
| **服务端**（决策 P-h，`resume.js`） | `sinceSeq == 0`（第一次打开）是"**历史本身**"，不是补发 ⇒ **故意不打** `catchUp` | 那批帧**没有**"补发"标记 |
| **客户端**（`chat_controller`） | 规则写成"**没有 `catchUp` 就是现在发生的**" | ⇒ **冷启动整段历史都被喊了一遍** |

⇒ 后果：那条**很久以前**的崩溃通知，**每一次登录都弹一次浮窗**。
那既是**骚扰**（R1.2 通知疲劳），也是**假话**（"刚才出了点事"其实不是刚才）。

⚠️ 有意思的是：客户端那句注释**早就预言了这个 bug** ——
"冷启动一屏历史通知会一条条往外弹（那是骚扰，也是假话）"，
只是当时的闸只挡了 `catchUp` 那一种历史。

### 9.3 修法（不动协议）

服务端的顺序是"**先把补发那段发完，再发 `client/hello`，然后才订阅实时**"（`server.js` 那一段就是保证）。
⇒ 客户端拿它当**边界**：

```
stream.dart     收到 client/hello ⇒ 给上层一条内部帧 __caught_up__
chat_controller 收到 __caught_up__ ⇒ _readingHistory = false
                浮窗条件 = shouldPopNotice(catchUp:, readingHistory:)   // models/notice.dart
```

⚠️ **`__caught_up__` 是客户端内部帧，不是协议字段**（协议一旦上线就冻结）；
`__reset__` 已经开了这个先例。
⚠️ **时间线那一条照样留着** —— 通知要经得起"你不在"（约束 2）；只是**不喊**。

### 9.4 判据（都在，且带负向对照）
