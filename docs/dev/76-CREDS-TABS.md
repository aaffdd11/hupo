## 三、钥匙文件长什么样（向后兼容）

`<HUPO_DATA>/creds.yaml`（他那一台容器里 `/data/creds.yaml`，root 0600），**一行一个 `名字: 值`**：

```
HUPO_MODEL_KEY: sk-…        ← 老格式，一行；今天之前就只有这一行
HUPO_IMAGE_KEY: …
HUPO_VIDEO_KEY: …
HUPO_VOICE_APPID: …
HUPO_VOICE_SECRET_ID: …
HUPO_VOICE_SECRET_KEY: …
```

🔴 **一条规则只住一处**：名字表、解析、合并、状态全在 `src/creds.mjs`（纯函数，`test/creds.test.js` 钉着）。
**写入一律是"合并"**（`mergeCreds`）：只动点名的那个字段，**别的行原样留着** ——
两把钥匙分两次填，谁也不会把谁抹掉（判据里有一条负向对照专门盯这个）。

## 五、🔴 顺手拆掉的一个真陷阱：`parseKey` 会**挑错钥匙**

`model-proxy.mjs` 的 `parseKey` 原来那条规矩是"取名字里带 `KEY/TOKEN/SECRET` 的**第一条**"。
这份文件从今天起**不止一把钥匙** ⇒ 只填了图片那把时，它会**拿图片的 key 当语言钥匙**发给上游
（现象是"模型鉴权失败"，而真正原因是**挑错了钥匙** —— 最难查的那一类）。

**修法**：`parseKey(text, want)` —— 指名要哪一把时**只认那一个名字**，
**找不到就 `null`**（代理如实回 503「这一台还没有配好模型凭据」）。
判据：`test/model-proxy.test.js` 里那条 `🔴 只填了图片那把 ⇒ 不许拿它当语言钥匙`（负向对照）。

## 七、⚠️ 已知欠着 / 明说砍了的

1. **图片/视频/语音三条"干活的路"没有**（见 §一）—— 接它要另起一批：用哪条接口、多久、
   结果怎么给他看（图片要渲染、视频要播）都得先定。

   两处并存是**过渡态**：要么将来把识别也改成按人取，要么把这三格收回去。
3. **主人自己那一份**（`owner` 本机账号）不走容器 ⇒ 这一页四个 tab 都只说
   "你自己这一份就在这台机器上 —— 钥匙不在这页填"，**不给表单**（与原来那条规矩一致）。
4. **一次连接只写得动一把**钥匙 ⇒ 四把一起填时，容器每重连一圈送一把（最坏约半分钟到齐；
   期间可能重复送同一把，同值合并、无害）。
