## 二、根因：**两处**（都在"那一包钥匙有没有到、到了读不读得到"这条线上）

### ① 推送的**触发**：只有带 `model` 的那一拍才推（已修 · 已部署）

配置页是**一屏一次提交**（聊天 / 语音 / 图片 / 视频各一屏），而 `/api/creds` **永远由中心处理**
（它不在 `server.js` 的 `TENANT_ROUTES` 里 —— 那是有意的："填 key 是中心的事"）：

```
配置页「语音」那一屏 ──POST /api/creds──▶ 中心 setCreds()
                                            ├─ writeUserCreds(中心那份存档)   ✅ 存下了（页面也回报"有"）
                                            └─ 推给他的盒子？              ❌ 只有"这一包里带 model"才推
```

⇒ 在「语音」那一屏填的三样**一次都没被推过**：中心有、页面说"有"、
**盒子里那份 `creds.yaml` 里没有**。

**修**（`serve.js` ＋ `creds-store.js` ＋ `tenant-channel.mjs`，见 §三）：

- `setCreds()` 末尾：**只要这个人是租户，任何一次改动都推那一整包**
  （中心存的那几样 ＋ 宿主内存里有就带上的模型那一把）；
- 通道新增 `credsFor(tenant)`：**盒子每次连上来**（它每 5 秒重连一次、一直守着）都顺手给它一份
  —— "用户填了、可那会儿盒子不在"就靠这一拍补上；盒子那边是**合并**写，抹不掉别的几把。

### ② 盒子里的**读法**：`credsFor` 的 `env` 没传下去 ⇒ 单文件的兜底路**从来没走过**（已修 · **未发布**）

钥匙推进盒子之后，盒子里那条识别路要能读出来 —— 它读的是 `asr-creds.js` 的 `voiceCredsFor`，
而那一支：

```js
// asr-creds.js（修之前）
const mine = who ? credsFor({ dataDir, sub: who }).values : {};   // ← 没传 env
```

`credsFor` 里"**盒子里读那份单文件** `/data/creds.yaml`"那一支**只在 `env.HUPO_ROLE === 'tenant'` 时**才走
（`creds-store.js` 的 `credsFor({ …, env = {} })` —— 默认是**空对象**，不是 `process.env`）
⇒ **不传 `env` = 那条兜底路一次都没执行过**：文件里明明有那三样，识别路照样回「没配凭据」。

🔴 **这是"判据打在另一侧"那一族**：`test/creds-box.test.js` 直接调 `credsFor` 时
**显式**给了 `env: {HUPO_ROLE:'tenant'}`（所以那条一直是绿的），而**产品这条路上没人给**。

**同一个坑还有第二处**：`image-use.js` 的画图也这么调（`credsFor({dataDir, sub})`）⇒
盒子里"在聊天里让它画"也一直说"没有钥匙"（⇒ 页面那句边界话**是对的**，见 §五）。

**修**：两处都把 `env`（和 `fs`）传下去 ＋ 判据打在**产品那一侧**（`voiceCredsFor` / `makeDrawImage`，
反做一下就红 —— 见 §四）。

## 三、怎么修（一处一行）

| 文件 | 改了什么 | 生不生效 |
|---|---|---|
| `v2/services/core/src/creds-store.js` | 新 `tenantCredsPack({dataDir, sub, model})`：**现合**"中心存的那几样 ＋（内存里有就带上）模型那一把"；一样都没有 ⇒ `null`（**不发空推**） | ✅ 已部署（`restart-core.sh`） |
| `v2/services/core/src/serve.js` | `setCreds()` 末尾：租户 ⇒ **任何一次改动都推那一整包** | ✅ 已部署 |
| `v2/services/core/src/serve.js` | 通道加 `credsFor(tenant)`：盒子一连上来就给它那一包 | ✅ 已部署 |
| `v2/services/core/src/tenant-channel.mjs` | `#readyPayload()` / `readyFrameOf()`：`ready` 帧可以**只有 `creds` 没有 `key`**；一样都没有 ⇒ `waiting`；`credsFor` 抛了也不许把通道带倒 | ✅ 已部署 |
| `v2/services/core/src/asr-creds.js` | `credsFor({ dataDir, sub: who, env, fs })` —— **把 `env` 传下去** | 🚧 **要发布产品层**（盒子里那台跑的是旧的一版） |
| `v2/services/core/src/image-use.js` | `credsFor({ dataDir, sub: userId, env })` | 🚧 **同上** |

**协议一个字节没改**：还是那条通道、还是 `{state, key?, creds?}` 三档 ——
老盒子（不认 `creds`）照旧走 `key` 那条路，新盒子合并写。

⚠️ **老形状 `key` 是一次"整份重写"**（`writeKeyFile`，只写模型那一行）：所以只要宿主手里的模型钥匙
与盒子里那份**不一致**（例如宿主刚重启、内存里那把是别人刚填的），一次 `key` 推送就会把盒子里
**别的几把抹掉**（这次取证时我自己就撞上过一次：盒子的图片钥匙被抹掉，靠备份还原）。
⇒ 新代码**总是把那一包一起带上**（盒子优先认 `creds`、走合并），这条风险只在"只有 `key` 可给"时还在。

## 四、读数（都是实测）

### 4.1 修 ① 之前：语音那一屏**根本没推**


盒子日志 `✓ 拿到凭据了` ＋ `creds.yaml` 里模型/图片/**语音三样**齐全（图片那把**没被抹掉** ⇒ 合并写是真的）。

⇒ 结论：缺的**只是触发**。

```
⇒ 盒子 /data/creds.yaml：HUPO_MODEL_KEY ＋ HUPO_IMAGE_KEY ＋ HUPO_VOICE_APPID/SECRET_ID/SECRET_KEY
```

⇒ 这一下把 **②** 顶出来了（推到了、读不到）—— 两处缺一不可。
