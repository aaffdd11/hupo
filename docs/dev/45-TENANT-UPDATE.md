# 45 · 容器怎么更新（镜像劈成「运行层 + 产品层」）

> 主人 2026-09-21：*"现在 docker 里面的系统，是镜像。但是，我核心功能，其实是 docker
> 里面的系统。所以，你觉得应该如何更新它？"*
>
> **问题的形状**：产品（调度器 + 人格 + 能力层 + agent 本体）**住在镜像里**。
> ⇒ 「改进产品」= 重造 404 MB 镜像 + root 导出/load 进每一台 + 每台重建容器。
> 而且容器**不知道自己跑的是哪一版**（镜像没给 `HUPO_BUILD_ID` ⇒ `buildId` 是 `dev`）
> ⇒ 一台可以**静默地**在旧代码上跑几个月。

**主人拍板**：**甲**（劈成两层）· 产品层目录**归 `deploy`**（我能自己翻转，但**每次都记账**）。

---

## 一、劈成三层（按"多久变一次"分）

| 层 | 装什么 | 住在哪 | 多久变 | 谁动它 |
|---|---|---|---|---|
| **运行层** | node + 它的动态库 + **dsh 本体** + `/etc` + 入口 `entry.mjs` | **镜像**（只读） | 只有 dsh/node 升级时 | root（`create-tenant-pool.sh`），罕见 |
| **产品层** | `src/` + `package.json` + 人格 + 能力 + 代理 patch | **宿主上一个目录**（`/srv/hupo/tenant-code/<指纹>/`），**建容器时 `:ro` 挂进 `/app/code`** | 每次改进产品 | `deploy`（`build-tenant-code.sh`），**每次翻转记账** |
| **用户层** | `/data`（卷） | 租户家里（`0700` 他自己） | 用户自己 | 不动 |

**为什么这样劈**：`dsh` 是 **305 MB**，产品代码是 **596 KB** —— 差 **500 倍**。
而"改一行代码"要搬的是那 596 KB。把两者绑在同一层里，是这整件事唯一的浪费来源。

⚠️ **`-v` 必须在建容器时就声明** ⇒ 已经跑着的那几台**要各重建一次**（一次性迁移，见 §七）。
好在 `create-tenant-pool.sh` 本来就会"发现单元变了就重启那一台"，迁移 = 改模板 + 跑一次。

## 二、指纹（没有它，一切都是"看着在跑"）

**一个地方算**：`scripts/build-tenant-code.sh`。
**算法**：产品层那几样输入，按**路径排序**；每个文件先算一个 `sha256`（内容是"相对路径 + 文件字节"），
再把那些 **32 字节摘要**依次喂进一个总 `sha256`，取前 12 位十六进制。
（⚠️ 不是"路径和内容直接拼"：内容里出现分隔符时理论上能撞 —— 摘要定长就没这个问题。）
**为什么是"内容"不是"提交号"**：提交号会变（rebase / 空白），而且**工作区脏着的时候它不反映真实内容**。
**哪些文件算**：`src/**` + `package.json` + 人格 + 能力 + 代理 patch（名单只有脚本里那一处）。
⚠️ **测试不进产品层**（容器不跑测试），所以加测试**不会**换指纹。

**住在哪**：`<目录>/manifest.json`（`fingerprint` / `builtAt` / `gitRev` / `inputs`）。

**谁看得到**：

| 谁 | 怎么看到 |
|---|---|
| 容器自己 | 入口读 `manifest.json` ⇒ 塞进 `HUPO_BUILD_ID` ⇒ **`/api/version` 如实报** |
| 宿主 | 容器连上来时在 `tunnel-ready` 里带上 ⇒ 宿主记下来 |
| 界面 | 宿主知道"这一台是哪一版"之后才能如实说（这一批先只把事实打通，界面另说） |

🔴 **不相同时要大声说**，不许当作没事 —— 这正是这个项目栽过两次的那个病
（`3.req.cancel` 与"仓库根算错一级"：**两处产物不一致，而两边单测都是绿的**）。

## 三、一次更新，经过哪几步

```
① bash scripts/build-tenant-code.sh              # 造产品层（不碰任何运行中的东西）
② bash scripts/build-tenant-code.sh --verify     # 拿一次性容器真跑一遍：要它自己报这个指纹
③ bash scripts/build-tenant-code.sh --publish    # 翻 current（记账一行）
④ 容器自己在空闲时退一下，systemd 把它拉起来 ⇒ 新代码生效
```

* **②那一关非有不可**：翻转之前**先证明这一版起得来**。
  没有它，一次手滑就是**所有租户的助手一起起不来** —— 我 2026-09-21 已经把自己
  的服务这样送死过两次（改完手册没重建清单就部署）。
* **③是 `deploy` 做的，不需要 root**。它**只改一个软链**，别的一律不碰。
* **④不需要 root、也不需要重建容器**：`Restart=always` + 容器自己 `exit(0)`。

### 3.1 为什么是「容器自己退」而不是「宿主去重启它」

宿主（`deploy`）**没有**资格去动别人的 systemd 单元 —— 那正是这套设计一直守住的那条线。
⇒ 宿主只能**经已有的那条通道说一句话**，退不退由容器自己决定。

⚠️ 那句话**不带任何内容**（`{"v":1,"type":"reload"}`）。它**不是一个远程执行口**：
宿主本来就已经决定容器跑什么代码（**镜像就是 `deploy` 造的**），
所以"叫它重开"**没有新增任何能力**，而"带载荷的重开"会新增 —— **所以不带**。

### 3.2 空闲才退

容器里那个服务**本来就在写** `/data/status.json`（`turn-status.js`，每秒一次，忙才写）。
⇒ 重开之前读它：

| 它说 | 怎么办 |
|---|---|
| 不忙（或文件陈了/不在） | 立刻退 |
| 忙 | 等（每秒再看一眼），**最多等一个上限**；到点**照样退**并把这件事说出来 |

上限那条理由和 `restart-core.sh` 一字不差：**等一个卡住的服务，比切一轮话更坏**。

## 四、安全模型（谁写产品层 = 谁决定所有租户跑什么）

**主人拍板：归 `deploy`，每次翻转记账。** 事实与边界如下：

| 问题 | 答案 |
|---|---|
| 这是不是**新**权力？ | **不是**。`build-tenant-image.sh` **本来就以 `deploy` 身份造整个租户程序**。root 那一步从来只是**分发**（把镜像 load 进每台存储），不是内容审查 |
| 那它改变了什么？ | 去掉了"改一行代码"到"所有用户都在跑"之间的**一层人工步骤**。⇒ 所以**必须留痕**（主人点名的那一条） |
| **谁能读** | 全机器可读（`0755`）—— ⚠️ 里面**没有任何秘密**（`key` 是运行时才进容器 tmpfs 的，不在产品层） |
| **谁能写** | 只有 `deploy`（目录 `0755`，属主 `deploy`）。**容器里的 agent（uid 1000）写不到**：它挂到的是 `:ro`，而且宿主侧那目录也不是它的 |
| **不许做的事** | 产品层**不许**放进任何按人不同的东西（那会把"一份代码"变成"每台一份"，于是"改一次"变成"改 N 次"，而且**没有一处能看全**） |

⚠️ **挂载表仍然是边界**（和 `37-MULTITENANT.md` §12.1、`39-PERMISSIONS.md` §5.7 同一件事）：
产品层是**共享**的（所有租户挂同一份，只读）—— 这是**刻意**的：
它里面**没有任何租户数据**，所以"看得见别人的产品层"看见的只是**公开的代码**。

## 五、回滚

`--publish` 之前那个指纹**留在原地**（不删）。回滚 = 把 `current` 翻回去 + 让容器重开：

```bash
bash scripts/build-tenant-code.sh --list              # 有哪些版本、现在是哪个
bash scripts/build-tenant-code.sh --rollback <指纹>   # 翻回去（也记账一行）
```

⚠️ **删是显式动作**（`--prune`），不许"顺便清一下"——
把旧版本删掉的那一刻，回滚这条路就没了。

## 六、判据（`scripts/check-tenant-update.sh`）

每一条都带**负向对照**（这个项目的规矩：只验"该过的过"是假安全）。

| # | 验什么 | 负向对照 |
|---|---|---|
| 1 | 指纹只由内容决定：同一份内容两次算**同一个**指纹 | 改一个字节 ⇒ 指纹**必须变** |
| 2 | 指纹与"路径顺序/时间/提交号"无关 | 换个说法/动一下 mtime ⇒ 指纹**不变** |
| 3 | 造出来的产品层里**有人格、能力、`src/`，且没有 key** | 塞一个假 key ⇒ 判据**必须红** |
| 4 | 入口**认** `HUPO_CODE_DIR`：真跑一个容器，`/api/version` 报的**就是**那个指纹 | 不给 `HUPO_CODE_DIR` ⇒ 报的不是它（回落到镜像里那份） |
| 5 | 产品层挂进去是**只读**的 | 在容器里往 `/app/code` 写 ⇒ 必须 `EROFS`/`EACCES`（**不许**是"路径不存在"） |
| 6 | 宿主侧那句 `reload` **不带载荷** | 给它加一个字段 ⇒ 判据**必须红** |
| 7 | 宿主发现"容器报的指纹 ≠ 当前指纹"时**要说话** | 把比较那行注释掉 ⇒ 判据**必须红** |
| 8 | 翻转**留痕**（`ledger.jsonl` 多一行，且写清 from/to） | 删掉记账那行 ⇒ 判据**必须红** |

## 七、迁移（一次性 · 要 root）

已经跑着的 `hupo-a`/`hupo-b` 的单元里**没有那个 `-v`** ⇒ 各重建一次：

```bash
sudo bash scripts/create-tenant-pool.sh --yes     # 单元变了就重启那一台（脚本本来就会）
```

* 数据**不丢**（`/data` 是卷，`podman rm -f` 不动卷）。
* ⚠️ **镜像里**暂时**仍然带着** `src/` 那一份（当**兜底**）：
  新入口**优先**认 `HUPO_CODE_DIR`，认不到才回落到镜像里那份（那时 `buildId` 会是 `dev`）。
  理由：`podman load` 换掉的是**存储里的 tag**，而**跑着的那台**还是创建那一刻的镜像 ——
  万一某台在"单元还没更新"的窗口里重启，有兜底它**照样起得来**。
  ⇒ 这一步是**过渡**，判据第 4 条会**如实报**哪几台还在兜底上；
  等两台都迁移完、判据全绿，**下一次重造镜像就把 `src/` 拿掉**（明确的一步，不是"以后再说"）。

## 七·补、✅ 2026-09-22 真机迁移做完了（两台都在产品层上）

实际跑的那几段：建目录（root）→ `build-tenant-code.sh` → `--verify` → `--publish`（**deploy 身份**）
→ 重装 root 侧助手（`create-tenant-pool.sh` 变了）→ `create-tenant-pool.sh --yes`（root，两台各重建一次容器）。

| 读到的东西 | 值 |
|---|---|
| 当前产品层 | `824b2eadaa99`（`current` 软链 → 同一版） |
| 两台容器挂的 | `/srv/hupo/tenant-code/current`（**软链**，不是某个指纹 —— 见下面那个 bug） |
| 宿主横幅 | `产品层 824b2eadaa99（413eb54 · …）` |
| 每台自报 | `· hupo-a：这一台跑的就是当前那一版（824b2eadaa99）` |
| 清掉的死镜像 | `deploy` 存储 **10.22 GB → 405.7 MB**；两台租户各自也清到 ~451 MB |

### 7.5 🔴 **翻一版之后，容器真的是"自己"去拿的**（这是这条路唯一值得信的证据）

实测走了一遍**不重启宿主**的翻转：把 `current` 翻到新的一版 ⇒

```
⚠️ hupo-b：这一台跑的是 7fd0e6ea39d3，当前是 824b2eadaa99 —— 叫它重开一次
⚠️ hupo-a：这一台跑的是 7fd0e6ea39d3，当前是 824b2eadaa99 —— 叫它重开一次
· hupo-a：这一台跑的就是当前那一版（824b2eadaa99）     ← 它自己退了一下、回来了
· hupo-b：这一台跑的就是当前那一版（824b2eadaa99）
```

⇒ **没有 root、没有重造镜像、没有 `podman load`、没有重建容器、没有重启宿主。**

## 八、代价（如实写，不藏）

| 代价 | 说明 |
|---|---|
| 一次性重建每台容器 | 一台一次，秒级；数据不丢 |
| 产品层是共享只读的 | 一台的代码坏了 = 所有租户一起坏 ⇒ 所以 §三 ② 那一关非有不可 |
| "翻转"不再需要 root | 这是**换来的**：少了一层人工步骤，多了一条"每次记账"的义务 |
| 镜像里暂时还有 `src/` | 过渡期的兜底，见 §七；下一次重造镜像时拿掉 |

## 九、顺手发现的一笔账

`deploy` 自己那份 rootless 存储里**堆了 30 个镜像、9.8 GB，100% 可回收**
（每次 `buildah commit` 的旧镜像都还在，`<none>` 标签）。每台租户那边同理。
⇒ **2026-09-22 真做了**：`deploy` 存储 **10.22 GB → 405.7 MB**（31 个 → 2 个），
两台租户各自也清到 **~451 MB**。用的是 `podman image prune -f`（**只清 dangling**），
三处都做了，跑完两台容器照旧 `Up`。

## 十、🔴 真机实测抓到的三个 bug（每一个都是"看着像对的"）

**这三个都不是单测能抓到的** —— 它们的共同形状是"两端各自都对，合起来不收敛"。
⇒ 这也是为什么 §三 ② 那一关（发布前真跑一个容器）和这次真机走一遍**都要有**。

### 10.1 账本写成了"装着 JSON 的字符串"（判据抓的）

`flip()` 里"内层 node 打出 JSON 字符串、外层再 `JSON.stringify` 一次" ⇒ 账本里存的是
`"{\"at\":…}"`。**人看着像、程序全读不出来**。
⇒ 一次 `node` 调用写一行真 JSON。**判据第八条**就是抓它的。

### 10.2 单元里挂的是**解引用后的指纹**，不是软链 ⇒ 死循环（真机抓的）

我一开始把 `current` 用 `readlink -f` 解成真目录写进单元（理由是"确定性"）。
⇒ **翻 `current` 对在跑的容器一点用都没有**：宿主看见它永远是旧版 ⇒ 一直叫它重开 ⇒
它重开还是旧版 ⇒ **来回退**。实测现象：两台容器被反复重启到 `activating (auto-restart)`。
⇒ 单元里挂**软链本身**（容器是创建那一刻解析它的，而 `--replace` 每次重启都会重建容器）；
解引用后的路径**只用来比对和打印**。
⇒ 判据第十条加了负向对照：**挂指纹那种写法必须红**。

⚠️ 同一件事还有个连带的坑：死循环会把单元打到 systemd 的**启动限速**上 ⇒
光 `restart` 会被挡住（现象是"模板又写坏了"）⇒ 重启前先 `reset-failed`。

### 10.3 `onBuild` 用的是**开机时缓存的那一版** ⇒ 也不收敛（真机抓的）

`const productLayer = readProductLayer()` 是**模块级**的（给横幅用），而我在
"要不要叫它重开"那里也用了它 ⇒ 翻完 `current` 它就**变成一句假话**：
容器拿到新的一版报上来，宿主拿**旧的**当前版去比 ⇒ 又叫它重开 ⇒ 死循环。
⇒ 规矩：**"当前是哪一版"永远现读**（一次 `readlink` + 一个小文件，便宜到不用想），
**不许缓存**。判据第七条加了负向对照。

### 10.4 顺带：一条闸自己也有"只在某个状态下成立"的假设

`check-provision-install.sh` 原来用 `git diff --quiet` 判"变异收干净了" ⇒
**工作区本来就有未提交改动时它一定报红**（假警报）。
⇒ 改成比"动手之前那份的**内容指纹**"。**假警报的下场就是下一个人把闸关掉。**

### 10.5 还有一条：那个单元模板**自己从来没被验过**

它只能在"以 root 跑一次、再去别人家里看结果"这个形状下被验 —— 于是里面
**不带引号的 heredoc** 把注释里的反引号当命令执行、把写出去的注释**挖空**了，
而**功能没坏**（所以谁都没发现，`43` §11.1 记过同一个坑，我又踩了一次）。
⇒ 把渲染抽成**纯函数**（`create-tenant-pool.sh --render` 写 stdout），判据直接对它跑
`systemd-analyze verify` + 逐词检查注释还在不在（**也加了"不带引号的 heredoc"那道闸，
而且把名单盖全到 root 侧那五份** —— 原来只盯两份，`create-tenant-pool.sh` 一直没人看）。
