# 173 · 那个用户的助手"经常卡住、只能做小片段" —— 查出来的两条根因

> **主人 2026-10-04 要求**：*"检查一下，用户 dsh 经常卡住，只能执行小片段任务。
> 你找一下聊天记录进行分析。"*
>
> **读的是哪一份**：那台盒子里**服务端自己落的那本流水**
> `/home/hupo-b/tenant/main.jsonl`（8595 条事件 · 375 轮 · 全部可解析，**没有坏行**）。
> ⚠️ 读它要 root（`/home/hupo-b/tenant` 是 `drwx--x--x`）。
> ⚠️ 这一页**只记形状与计数**，**不抄用户说过的话**。

---

## 一、结论（两条根因，都有读数）

### 🔴 根因 A：**单轮 180 秒硬上限** —— 一到就"卡住"

`src/dispatcher.js` 的 `TURN_DEADLINE_MS = 180_000`（`HUPO_TURN_DEADLINE_MS` 可配）：
一轮从用户那句到最后收口，**超过 3 分钟就被硬收口**成 `timeout`。

| 读数 | |
|---|---|
| 375 轮里 | **11 轮 timeout** · 19 轮 failed · 343 轮 completed |
| 11 轮 timeout 的耗时 | **160–179 秒**（对着 180 秒那条线） |
| 最近的轮次 | **10-01：1/1 超时 · 10-03：4/6 超时 · 10-04：1/1 超时** |
| 用户看到的那句话 | *「这条我卡住了，后面没说完。你可以让我接着说。」*（`DEADLINE_PARTIAL_LINE`，服务端补的） |
| 长活那条线 | 286 条"我去做，做完叫你" · 193 条"做完了" · **22 条"那件事我没做完"** |

**它卡在哪（超时前最后几个动作）**：多轮的最后一步是 **`job_output`（等后台）**
或一条长 `bash`。有一轮**轮内累计申请了 230 秒的等待**（`job_output` 的
`timeout_ms` 加起来），比整轮的 180 秒预算还长 ⇒ **必被砍**。

⇒ 一个"扒 33 篇原文 + 转换 + 拼页面"这种活，第一轮一定撞线；下一轮从头再来一遍，
再撞线 —— 用户看到的就是**"只能做一小片"**。

### 🔴 根因 B：**容器只有 768 MB，而且不能 swap** —— 内核直接杀

盒子的容器是 `podman run … --memory=768m --memory-swap=768m`。

| 读数（内核日志） | |
|---|---|
| 容器 cgroup 的 OOM kill | **9-25：58 次 · 9-26：52 次 · 10-02：2 次**（共 **112 次**） |
| 被杀的都是 | `MainThread`（**盒里那个 agent 进程**，uid 297607） |
| 其中一次的现场 | `anon-rss:415292kB` 被杀 —— 那一刻整个 cgroup 已经到顶 |
| 这次开机以来的峰值 | `memory.peak = 589 MB / 768 MB`（**77%**）· 本轮 `oom_kill=0` |

⇒ 9-25 / 9-26 那两天正是用得最狠的两天（那两天 312 轮、约 2000 次工具调用），
**两天里被杀了 110 次**：一轮干到一半，进程凭空没了，用户看到的就是"做一半没了"。

### 说明白：**不是这两样**（免得往错的方向修）

| 猜的方向 | 读数 | 结论 |
|---|---|---|
| 工具链坏了 | 2805 条工具结果里 **只有 15 条真的失败**（11 FsError · 2 WebError · 2 ToolTimeoutError） | ❌ 不是 |
| 上游限流（429） | 日志里搜到的"429 / rate"**全是随机 id 里的数字**，没有一条真限流 | ❌ 不是 |
| 磁盘满 | 没有一条 `ENOSPC` | ❌ 不是 |

### 放大器（不是根因，但让它更容易撞线）

- **结果被截断 207 次**：它手上的数据量大（几千道题、几十篇原文）⇒ 只能一小片一小片读写
  ⇒ 同样的活要更多轮，而每轮只有 3 分钟。
- **人格里没告诉它有时间预算**：`hupo-persona.yml` 里搜不到 180 秒/时限这类字。
  它不知道"这一轮只剩 3 分钟"，于是不会主动"先交后台、下轮再收"。
- **没有并发上限**：一轮里最多开了 **71 个 subagent**（9-26 那轮），
  每个都是一棵新的 agent 进程 —— 在 768 MB 里这就是 OOM 的配方。

## 二、能怎么改（**哪几条要主人点头**）

| # | 做什么 | 代价 / 风险 | 要谁点头 |
|---|---|---|---|
| 1 | **给盒子加内存**（768 MB → 1.5 GB 上下） | 宿主内存够（每一层都是 `max`）；一台盒子多占几百 MB | 主人（这是"给用户用"的那一套） |
| 2 | **被 OOM 杀掉时如实说清**（现在只说"那件事我没做完"） | 一条文案 ＋ 一处判定；不改行为 | 助手可做 |
| 3 | **轮内禁止长 wait**（或"等后台"不计入单轮预算） | 改的是 agent 的干活方式 ＋ 一处判定 | 助手可做（要判据） |
| 4 | **把时间预算写进人格**（"这一轮大约三分钟，长活先交后台"） | 人格是 `strict` ⇒ 要重建开机清单 | 助手可做 |
| 5 | **放宽 180 秒**（或对后台的活不设上限） | ⚠️ 这条**动的是安全网**：手册事故一那行"还有件事在处理"挂了 68 分钟，就是它防的 | 主人 |
| 6 | **给 subagent 并发设个上限** | 改行为；上限值要定 | 主人（定几个） |

> **我建议的顺序**：先 **2 ＋ 3 ＋ 4**（都是"让真相看得见 / 别再撞线"，
> 而且不需要动那条安全网），再看 **1**（加内存）—— 1 是唯一能根治 9-25/9-26 那种
> 110 次 OOM 的一条；**5** 留到最后再说。
