## 一、三个人各自的一句话结论

| 视角 | 一句话 |
|---|---|
| **内核/隔离** | 「一人一容器」在内核层成立的**条件只有一条**：**每租户一个 OS 用户 + 一段独占 subuid + 一个 0700 卷**，且**容器 root 只映射到该租户自己的 uid**。缺一条，两个容器在宿主上就是**同一个人** |
| **服务/应用** | 调度器**不该记住**身份、只该**算出**身份：`sub` 是唯一真相；容器只继承**布局**，**不继承身份参数** |
| **安全/治理** | ⏳ 仍在作答（§六） |

## 二、⚠️ 他们最先撞上的同一堵墙（**这是这一节最要紧的**）

**内核视角实测**：`podman info` 的 UIDMap = `[{0→1001,1},{1→165536,65536}]`
⇒ **无根容器里的 uid 0，在宿主上就是 `deploy`(1001)**。

**服务视角换了个角度说同一件事**：

> `0600` 只挡**其他 OS 用户**；而调度器与容器里**都是 `deploy`** ⇒
> 它拦不住**同一个 OS 用户内的交叉读** —— 那是**准入的错觉**。

⇒ **结论：今天这套"每人一份 data 目录 + 0600"的方案，一点用都没有。**
（我自己复核过：`data/` 775、`auth.json` 600、`main.jsonl` 664、`ledger.sock` 600、`~/.dsh` 700 —— 全部 `deploy:deploy`。）

### 2.1 内核视角另外两刀

* **`V1` 绿 ≠ 隔离成立**：V1 之所以过，是 **PID namespace** 让 `/proc/1` 变成了容器的 init，
  **不是 uid 隔离**。"拿 V1 绿当'隔离已成立'是最大的错觉。"（这一刀直接砍在 `34-CONTAINER.md` 的结论上，**砍得对**。）
* **`podman unshare` / `podman exec` 是真后门**：命名空间的**主人**本来就能进去
  ⇒ **谁拥有那段 subuid，谁就是那个租户的 root**。

## 四、三个人互相指出的漏洞（**这部分最值钱**）

| 谁指出 | 指谁 | 说了什么 |
|---|---|---|
| 服务 | 内核 | **漏了"容器内路径 ≠ 宿主路径"**：内核按宿主路径设计隔离，而**键用的是容器内看到的路径** ⇒ 挂载点一改，**隔离对了、历史断了** |
| 内核 | 服务 | **漏了 N21 在容器内的含义**：`DSH_HOME` 在**容器内**也必须是每租户不同的绝对路径（都写 `/data/.dsh` 的话，搬家把两份卷摆一起就**撞账号**） |
| 服务 | 安全 | **漏了"agent 不该知道 userId"**：把身份当**参数**传进容器 = 给了它一个**伪造的把手** |
| 内核 | 安全 | **V1 绿是 PID namespace 的功劳**，别当成隔离已成立 |
| 安全 | 两位 | ⏳ 待补 |

## 五、收敛出来的方案（**三方一致的部分 + 我加的核验**）

### 5.1 形状

1. **每租户一个 OS 用户**：`hupo-a`(2001) / `hupo-b`(2002)（**建用户要 root ⇒ P2：助手提申请、主人跑**）；
   各加 `subuid`/`subgid`；起法 `sudo -u hupo-a podman run` ⇒ **容器 root → 2001**，**绝不许映射到 1001**。
2. **一人一份 0700 卷**：`/home/<u>/tenant`（属主 `2001:2001` 0700）· `/home/<u>/.dsh`（同）。
   ⚠️ **属主必须等于容器 root 映射到的宿主 uid**：无根 userns 里 uid 0 **没有跨 uid 的 DAC override**
   ⇒ `deploy` 属主的目录在映射到 2001 的容器里显示 `nobody` ⇒ EACCES。
   这正是"**bind 宿主 `data/` 等于把凭据交出去**"的原因。
3. **共享的只有只读的**：代码 `root:root 0555` 或 `bind :ro`。
   ⚠️ **镜像共享不了**：无根镜像在各自 `~/.local/share/containers` ⇒ 只能各自 load 同一个只读 tar。
4. **身份藏在路径里，不藏在参数里**：容器只拿 `DSH_HOME` + `HUPO_LEDGER_SOCKET`
   （`agent-runtime.js:311,320`）——**agent 不该知道 `userId`**（知道了就能伪造）。
   调度器侧：`sub` 是唯一真相，**禁止任何 `currentUser` 全局**（"一次 `await` 就是串号"）。

### 5.2 🔴 第一用户的迁移：**搬所有权、不搬路径**

因为**会话记录里嵌着绝对路径**（§三 已证）：
* 改目录名/换路径 ⇒ **换账号**（N21 的原注：`换路径 = 换账号`）；
* ⇒ **第一用户的容器要把 workspace 与 `DSH_HOME` bind 回原来的绝对路径**
  （`--userns=keep-id`），**容器内路径不变 ⇒ 会话键不变 ⇒ 历史接得上**；
* ⇒ 只有**新用户**才用干净的布局。

**代价**：第一用户**拿不到干净布局**（换布局 = 接受断代）。这一条要主人选（§七）。

### 5.3 可执行判据（**含负向对照**，对齐 `08-SPEC.md` §13.4）

**① "两人交叉读不到对方"**（内核视角给的，我照抄；镜像本地已有）：

```bash
sudo -u hupo-a podman run --rm -v /home/hupo-a/tenant:/w localhost/hupo-base sh -c 'echo A > /w/s'
sudo -u hupo-a podman run --rm -v /home/hupo-a/tenant:/w localhost/hupo-base cat /w/s  # 对照：须打印 A
sudo -u hupo-b cat /home/hupo-a/tenant/s                                                # 须 EACCES
sudo -u hupo-b podman run --rm -v /home/hupo-a/tenant:/w localhost/hupo-base cat /w/s   # 须非 0 退出
```

⚠️ **失败必须是 `Permission denied`；`No such file` 不算**（那只说明路径写错了）。
⚠️ **第二行的对照不能省** —— 没有它，"读不到"可能只是容器根本没跑起来。

**② "搬家前后逐字节一致"**（`13.4` 第三道台阶）：

```bash
ls ~/.dsh/sessions/--home-deploy-hupo-workspace--/ | wc -l   # 搬前 = 搬后
```
**负向对照（服务视角给的，很聪明）**：**故意**把 workspace 挂到别处 ⇒
同一个会话 resume **必须接不上**。**要是竟然接上了，说明"键=路径"这条判断错了，
那就得回头改手册**（而不是庆祝）。

## 七、要主人拍板的（**现在就能定的四条**）

| # | 问题 | 选项 | 建议 |
|---|---|---|---|
| ① | 准不准**新建两个 OS 用户** `hupo-a`/`hupo-b`（要 root） | 建 / 先不建 | **建** —— 这是"内核能分开"的**唯一**前提；⚠️ 与 `welkin` 无关，**不碰别人的账号** |
| ② | 第一用户**保原路径**（保住历史）还是**换干净布局**（接受断代） | 保 / 换 | **保**（`13.4` 的"逐字节一致"才有可能过） |
| ③ | **服务进程 `deploy` 还能不能读租户卷** | 能 / 不能 | **不能**（否则它就是特权方，②③两条判据一起作废）；替代：租户数据**只经域套接字回传**，`deploy` 不落盘读 —— ⚠️ 但这对"调度器要读时间线来渲染"是个**真冲突**，得先想清 |
| ④ | `sub` 扩成真 userId 之后，**旧令牌作不作废** | 作废重发 / 保留 | **作废重发**（旧令牌恒 `owner`，留着就等于"别人的"） |

⚠️ 另：**供给上限必须与容器同批**（`02-ARCHITECTURE.md:422`）——
`06-OPERATIONS.md` §4.1 的账：2 用户 ×（1 焦点 + 1 监视）× 195MB + 调度器 80MB = **860MB > 640MB 软限**。
